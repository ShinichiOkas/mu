# L6 — 学習の層（Learner）設計書

合意033 フェーズ C の成果物。**測定（B / B2 / B3・計216判断）に接地した構成設計**であり、
実装は 034 以降。ここに書くのは「構成」だけ——規範文（learner の対策文）は実走の
誤診観測から足す（[[role-structure-by-design-norms-by-failure]]）。

## 何を解くか（層の落差）

> **L5 は目的を完遂できる ↔ 同じ失敗を次の走でも繰り返す。**

L6 は L5 の走を D として使い、その外側に「**この走から何を学ぶか**」の判断を足す
（再帰同一構造は不変）。目的は自己成長（師匠 2026-08-13）:

> 今回のような制御ループを自己発見的にスキルに追加できるようになること。
> 失敗モードから学びをスキルやロールにフィードバックすることが L6。

成長指標は3つ（師匠の宣言・すべて台帳のビュー）:

1. **同じ失敗を繰り返す頻度を下げる**
2. **失敗に対するアプローチの手段を増やす**
3. **失敗がなくなったら、より少ない手数で同じ成果を出す**（失敗ゼロにゲートされる——辞書式順序）

「いつ回すか」（定期・タスク後・git 差分）は**ループエンジニアリングの領域**（師匠）であり
L6 の外——監視系のツール＋skill として別スプリントで扱う。

## 測定が確定させた設計判断（5つ）

### 1. 診断は分解する——モードごとの独立二値判定 × コード集約

「1判断でモードを1つ選ぶ」は実ログに対して**不良設定**（B2 で実測）。実走の記録には複数の
実在パターンが併存し、単一選択は最も目立つ現象に吸われ、否定形の答えを構造的に不利にする。

| 形式 | gold 検知 | 正直な「該当なし」 |
|---|---|---|
| 1判断1モード（B2） | 8/16 | 0/32 |
| **モード別二値（B3）** | **7/9** | コードが導出 |

これは mu 自身が verdict で通った道（017: 総合判定を書かせず、項目ごとの二値＋集約はコード）の
再演である。**L6 の C（check）は、台帳の各モードへの独立した「出たか？」判定の列**になる。

### 2. 発生と原因は別——診断は二段

B3 の「偽陽性」精読で判明: 検知の問いは「そのモードが**出たか**」を正しく答えるが、
「その走を**壊したのは**どれか」とは別の問いである。quantifier-weakening は 6/7 の走で
**実在の証拠つきで**発火した——∀→∃ の弱化は事件ではなく**系の常態**だった（発見）。

- **一段目 detect**: モードごとの二値（LLM）× 集約（コード）→ 検知集合
- **二段目 attribute**: 走が失敗していれば、**検知集合の中から**結果を壊したものを特定
  （候補が絞られた小さな判断。開いた診断ではない）

### 3. 否定形はコードが導出する

032 の no-op・033 の new_mode——「否定形の答えは規範で書いても選ばれない」が2度実測された。
知識で作れないもの（契約に無い結果の種類）は構造が持つ:

- **new_mode** ＝ 全モード no ∧ 走に失敗が実在 → コードが導出。そのときだけ開いた診断
  （機構の記述）が走り、成果物は **draft の台帳エントリ**になる
- **学びなし** ＝ 全モード no ∧ 走は成功 → **L6 の第一級の正常な結果**（何も書かない）

### 4. 台帳が唯一の状態

走を跨ぐ状態は失敗モード台帳（`ledger/*.md`）**だけ**。層は無状態のまま
（三原則「状態・記憶の少なさ」と衝突しない）。台帳の契約 v2:

```
---
name: <slug>
description: <素性1行。検知・照合の材料>
maturity: draft | confirmed     # 系が書けるのは draft まで。confirmed は人間
kind: incident | chronic        # 事象（特定の走で発火）/ 常態（系の性質。ほぼ毎走出る）★new
---
症状: … / 機構: …
## detect      ← 検知の問い（必須★new）。操作的に——何と何を突き合わせるかまで書く
## 観測        ← どの走で出たか（L6 が追記していく＝指標1の生データ）
## 対処と効果  ← 何を当てて効いたか（skill/role/構造。＝指標2の生データ）
```

- `kind: chronic` の運用: 検知は続ける（観測に積む＝再発頻度の計測）が、**毎走の報告からは
  外す**。常態の発見そのものは一度だけ**構造の不足として escalate**（quantifier がその実例）
- 検知の問いの効きは実測済み——「走が自分の基準では成功していても該当しうる」の一文で
  quantifier の検知が 0/4 → 1/1（誤発火 0/9）に反転した。**問いの質が検知の質**
  （[[selection-judgment-lives-in-catalog-data]] の診断版）

### 5. 書き戻しは draft まで——人間の門は3つの出口すべてに立つ

| L6 の出口 | 形 | 効き始めるのは |
|---|---|---|
| skill 提案 | draft の skill ファイル | 人間が `maturity: confirmed` にしたとき（029 の門がそのまま効く） |
| role 提案 | 定義書への**提案差分**（適用しない） | 人間が定義書を編集したとき |
| 構造の不足 | escalate（報告のみ） | 人間が実装したとき |
| 台帳の新モード | draft のエントリ | 人間が confirmed にしたとき（それまで検知列に載らない） |

**自動 confirm・自動適用は作らない（絶対ルール）。** 029「skill は権限を持たない」と同根——
誤診（実例: 私の「∀ の退化解」）が知識として固定される経路を、構造で塞ぐ。

## 構成

### 座とファイル

- **`mu/l6.py` — `Learner`（層）**: 判断の列を持つ。無状態。台帳のパス・記録・モデルは
  呼び出し側が規定
- **`mu/ledger_kb.py` — facility**: 台帳の読み書き（load / detect 節の取り出し / 観測の追記 /
  draft エントリの生成）。probe_learning の `load_ledger` を昇格。**データの形だけが契約**
  （role_kb / skill_kb と同型）
- **`roles/learner.md` — カタログ級定義書**（実装済み・実測で調整済み）: `## detect-one` に
  加え、二段目 `## attribute`・新モード記述 `## describe` の節を足す
- 材料整形（優先度充填 `materials`）も facility へ——[[truncate-in-purpose-order]] の実装形

### D（何を読むか）

**完了した走の結果契約＋記録テキスト。** 記録の出所は呼び出し側が規定する（観測は CLI
合成点の持ち物——合意003 の観測方針のまま。**L0〜L5 は無変更**）。

### 判断の列（1周）

```
detect   : 台帳の confirmed モードそれぞれに「出たか？」二値 ×N     ← LLM（分解済み）
集約     : 検知集合・new_mode・学びなし の導出                      ← コード
attribute: 走が失敗していれば、検知集合から「壊したもの」を特定      ← LLM（候補は絞済み）
propose  : モードの「対処と効果」を見て次の一手を提案
           （未対処→skill/role 案・対処済みなのに再発→効いていない報告・
             chronic→構造 escalate）                                ← LLM＋コードの床
記録     : 観測の追記・draft の生成                                  ← コード
```

### 結果契約（案）

```json
{
  "detected":  ["mode", ...],          // 検知集合（証拠つき）
  "caused":    "mode" | "",            // 走を壊したもの（失敗時のみ）
  "new_mode":  {"mechanism", "evidence"} | null,   // コードが導出した時のみ
  "proposals": [{"target": "skill|role|structure", "mode", "draft_path"}],
  "nothing":   true | false            // 学びなし＝第一級の正常
}
```

### コスト（正直に）

1周 ＝ confirmed モード数 × 1判断 ＋ attribute ＋ propose ≈ **モード10件で12〜15判断/走**。
台帳が育つほど線形に増える。当面は許容し（B3 の実測: 80判断で約25分・エラー0）、
増えたら chronic の間引き・モードの群化を**測ってから**入れる。

## 032 の落差との対応（v2 で訂正——3つの別物を混ぜない）

v1 は「実行系の no-op と責務/目的の分離はトリガー側（ループエンジニアリング）に残る」と
書いたが、**師匠の指摘（2026-08-13）で訂正**:

> no-op の追加はループとは別問題じゃない？
> 僕が思ったループエンジニアリングはトリガーによって繰り返しループが起動する。
> そのループを作ることでエージェントに的確に仕事をさせるという話です。
> 現在はループ自体は手順という形で非決定性にスキルの一部として提供されているという認識。

整理し直すと**3つの別物**がある:

| | 何か | 性質 |
|---|---|---|
| **ループエンジニアリング** | トリガー（定期・タスク後・git 差分）で繰り返しループを**起動する機械**。外側の while | 判断を持たない。純粋な機械 |
| **責務の座**（将来の層の候補） | ループの**1周の中身**: 責務＋観測 → 差分の判定 → **no-op（第一級の契約）** または 目的を生成して L5 へ | **契約と判断の問題**。032 の落差（no-op・責務/目的の分離）はここに住む——ループの機械の問題ではない |
| **L6 学習（本設計）** | 完了した走から学ぶ。どの走にも事後に付く | 本設計のとおり |

**現状の認識（師匠）**: ループ自体はいま**手順という形で、非決定的に、skill の一部として**
提供されている——032 の `maintenance-is-a-control-loop`（観測→差分→差分だけ作用、を散文で
指示）がまさにその実物で、散文のループは確率的にしか回らなかった（no-op に到達できなかった）。

ループエンジニアリングとは、これを**構造に持ち上げる**話である。mu は既にこれを内側で
やってきた——L2 の Reflect ループも L4 のタスクループも**コードのループ**であり、判断だけを
LLM に切り出している。同じ流儀（決定論の床はコード・判断は LLM）を**最外周の繰り返し**にも
適用する。

北極星「継続する責務」への到達に要るのは **ループエンジニアリング（外側の while）＋
責務の座（1周の中身と no-op の契約）**。L6（学習）は別軸の柱——3指標を通じて
その全体を磨き続けるための層である。

## やらないこと

- 自動 confirm・提案の自動適用（**絶対ルール**）
- トリガー・監視（ループエンジニアリング・別スプリント）
- 指標3（手数の最適化）——失敗ゼロにゲート
- 台帳の自動剪定・モード統合（人間の承認事項）
