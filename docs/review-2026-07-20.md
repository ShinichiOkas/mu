### A-2. 三原則の「外部依存ゼロ」が自己矛盾

[README.md:20](../README.md#L20) は「依存とコード量 — **外部依存ゼロ**・短いコード」と言うが、決定事項（[README.md:157](../README.md#L157)）は「依存 公式 `ollama` クライアント」。実装は `ollama` + `httpx`（[mu/l0.py:24-25](../mu/l0.py#L24-L25)）に依存する。実装が悪いのではなく**コンセプト文の言い過ぎ**。「依存最小（公式クライアントのみ）」等への修正が実態に合う。なお `httpx` は直接 import しているのに [pyproject.toml:6](../pyproject.toml#L6) で宣言していない（ollama の推移的依存で動いているだけ）。

### A-3. L3 だけ「中断・再開」の対称性が無い

L1・L2 は `step()` を持ち「保存した messages で再開できる」無状態設計だが、L3 は `run()` のみで、plan（units）は run 内のローカル状態（[mu/l3.py:113-160](../mu/l3.py#L113-L160)）。中断（`_Abort`/Ctrl-C）すると計画の進捗（done マーク）が失われる。合意004の形どおりではあるので違反ではないが、「再帰同一構造」を謳うなら L3 にも step 面（または units の入出力）がある方が一貫する。L4 着手時に効いてくる論点。

## B. バグ・脆弱性

### B-1. L0: タイムアウトが実は存在しない（README との齟齬）

README は L0 の責務に「接続の安定化 — …**タイムアウト**・エラー回復」を明記している（[README.md:58](../README.md#L58)）が、実装はタイムアウトを一切設定していない。公式 `ollama.Client` の既定は `timeout=None`（venv 内 `_client.py:86` で確認）。つまり**サーバが接続を受けたままハングすると L0 は永遠にブロック**し、「常に安定して応答が返る」理想化が破れる。`httpx.TimeoutException` を捕まえるコード（[mu/l0.py:144](../mu/l0.py#L144)）はあるが、タイムアウトを課さない限りこの例外は発生しない。ローカル LLM は生成が長いので read は無制限でよく、**connect タイムアウトだけでも設定する**のが最小修正。

### B-2. l1_chat: ループ上限が無い（実証済みの無限ループ経路が開いたまま）

[l1_chat.py:68-71](../l1_chat.py#L68-L71) は `while not done: l1.step(...)` を**無上限**で回す。`ToolLoop.run` には `max_rounds=32` があるのに、CLI は step 直叩きでこれを迂回。qwen の `content_type` 幻覚事件が示したとおり、弱いモデルはツールコールを永遠に続け得る（シグネチャ束縛で当該機序は塞いだが、別の無限ループは可能）。しかも実行中の Ctrl-C は `input()` の外なので**トレースバックで異常終了**する。`l1.run(model, messages, TOOLS, max_rounds=N)` に寄せるか、CLI 側で上限を規定するのが「上限は呼び出し側が規定」の原則にも合う。

### B-3. L0: 自動 pull にリトライが無い

404 → `_pull()` は一発勝負で、pull 中の一時的な接続断（数 GB のダウンロードでは現実的に起きる）で即 `Unreachable`/`ModelUnavailable` になる（[mu/l0.py:169-177](../mu/l0.py#L169-L177)）。chat 本体には指数バックオフがあるのに、pull だけ理想化から漏れている。

### B-4. L3: `max_rounds` が「単位数」を暗黙に制約する

run ループは1周で「1単位実行 or 1回の全体判定」しか進まない（[mu/l3.py:129-152](../mu/l3.py#L129-L152)）。既定 `MAX_ROUNDS=8` では、**単位7個＋全体判定で使い切り**、再計画が1回でも入ると完遂不能になる。Plan プロンプトが「usually 2-3 units」と言っているので実害は出ていないが、承認者（人間）が単位を足す・モデルが多めに刻む、で静かに天井に当たる。上限到達時に「何周でどこまで進んだか」を返り値に含める、または上限を単位数に比例させるのが改善候補。

### B-5. 小さめの問題

- **4xx を一律 `BadRequest`**（[mu/l0.py:157-158](../mu/l0.py#L157-L158)）: 408/429 はリトライ可能な 4xx だが即死扱い。ローカル Ollama では実害はほぼ無いものの「接続の理想化」の小さな穴。
- **L1 の system 二重注入**: 呼び出し側が env preamble を system で持つため、送信時は「ツール system + 環境 system」の2枚になる（[mu/l1.py:87-92](../mu/l1.py#L87-L92)）。多くのモデルテンプレートは先頭1枚の system を想定しており、モデルによっては2枚目が弱く扱われる可能性。実機で動いているので緊急ではないが、1枚に併合する方が安全。
- **L2 の verdict `next` が空のとき**、再投入メッセージが「次にやること: 」（空）になる（[mu/l2.py:100-102](../mu/l2.py#L100-L102)）。スキーマ上 `next` は required だが空文字は通るので、空なら中立指示（unparseable 時と同じ文言）にフォールバックすると steering が安定する。
- **l3.py が l2 の私的ヘルパ `_transcript` を import**（[mu/l3.py:24](../mu/l3.py#L24)）: 層間でプライベート依存。公開名にするか l3 側に持つのが一貫。
