## 総評

コンセプトと実装の整合は高い水準で維持されている。とくに評価すべきは3点。

1. **L0 の境界設定** — 「接続は理想化する、中身は理想化しない」「上位に見せるエラーは4型だけ」は、
   この種のラッパで最も間違えやすい線を一発で正しく引いている。
2. **失敗 → 最小の機構化、という回路** — `_bind_to_signature`（幻覚 kwarg を落とす）、必須引数欠落の
   steering、`_carry_done` の重複 file 防御、`tools.protect()`。どれも実ログ由来で、思いつきの一般化がない。
3. **L3 の overall を LLM 判定から機械照合へ縮めた判断**（合意005）。「偽・完遂」を独立した障害クラスとして

   評価する）は本プロジェクト最大の資産である。

そのうえで、本メモの主題は次の2つ。

- **A. 構造の気づき** — L4 で性質が変わったのは「層の逸脱」ではなく **軸が増えた**ため。

- **B〜D. 実装・実走レビュー** — 難課題セット H1〜H6 の実物から確認できた穴。とくに
  **「決定論の床」が床になっていない**（B）は、二軸の議論とは独立に優先度が高い。

## A. 構造の気づき — 個人軸と組織軸の二軸進化

> **追記（2026-08-02 同日・後続協議）**: 本章の二軸モデルは、続く協議（共通要素の警告 →
> 「組織側は割り付けビューであってリソースアロケーションの管理でしかないのでは」という師匠の還元）で
> **棄却方向に改訂された**。現行の構造理解は
> [合意007 draft](../.pair-agent/agreements/007-capability-and-allocation.md) を参照。
> 本章は経緯の記録としてそのまま残す（A-4 の配線指摘・A-7 のゲート規則は還元後も有効）。

### A-1. 一次元モデルが破綻している場所

README は L0〜L4 を「自律性」という単一軸の入れ子として説明している（層テーブル、
「L4〜 = L3 の承認スロットに立つ層。同じ再帰同一構造」）。しかし実装はそうなっていない。

- `mu/l4.py` は **589行**。`l0.py`+`l1.py`+`l2.py` の合計 **573行**より大きい。
  README 自身の規約「1ファイルに収まらなくなったら『層が厚すぎ』のシグナル」が鳴りっぱなし。
- L4 が持ち込んだ概念は、役割 KB ／ SPEC.md・PROCESS.md・verdict.md という artifact 規約 ／
  `ACHIEVED:` 正規表現プロトコル ／ ファイル名の部分一致による依存伝播 ／ QA タスクの自動付加 —
  **いずれも再帰的でない**。L2→L3 は本当に同じ形（内側ループ→Reflect→続行/停止）だったが、
  L4 はその系列にいない。

診断: **L4 は層を踏み外したのではなく、別の軸の第1段である。**
L3 までが「個人としてのエージェントの能力」、L4 からが「チームとしての能力」。

### A-2. 二軸の定義

| 軸 | 何が育つか | 順序原理 | 入れ子か | 現在地 |
|---|---|---|---|---|
| **個人軸** | 一体のエージェントの能力 | 自律性（深さ）／—（装備） | 深さは入れ子・装備は非入れ子 | L3 まで到達、装備はほぼ手つかず |
| **組織軸** | 複数体を束ねる様式 | **調整失敗のクラス** | 入れ子（組織の組織） | O1（逐次）のみ |

人間の位置も軸ごとに異なる。**個人軸では再帰の底**（最上位の停止）、
**組織軸ではプールの外にいる依頼先**（`mu/l4.py` docstring に既に明記あり: 「人間はモデルプールの外にいる」）。
一次元モデルではこの2つが同じ「最上位」に見えて混ざる。escalate と HITL 承認が別機構である理由もここから出る。

### A-3. 個人軸は一枚岩ではない — 「深さ」と「装備」

専門能力（specialization）は L3 を包まない。デバッグ専門家は L3 より自律的でも、L3 を内側に持つのでもない。
**同じ深さでの分化**である。したがって個人軸は2つの成長モードを持つ:

- **深さ（ループ構造）** — L0..L3。入れ子で、自律性で全順序が引ける。**ほぼ完成している。**
- **装備（道具・知識・規律）** — 専門化。入れ子にならない。同じループが
  **何に触れられるか・何を知っているか**が変わるだけ。

この分割の効用は、専門能力の実装が一意に決まること。専門家とは「別のループを持つ者」ではなく
**「別の道具束と別の規律書を持った同じ L3」**。LONGTERM_TODO の
「role=qa には verdict.md にしか書けない toolset を渡す（役割別ツール制限）」は、
規律違反への対症療法ではなく **専門化の一般機構** として位置づけ直せる。
QA とは「実装できない人」であり、それは道具で定義される。

### A-4. 【重要】専門化が組織軸側に置かれている（配線の混同）

二軸で見ると即座に露呈する。

- `mu/l3.py` に role という概念は**一つも無い**（`{"role": "system"}` の messages キーを除く）。
- 役割定義を読むのは `mu/l4.py:174 load_roles()`、注入するのは `mu/l4.py:290`
  （`roles.get(t["role"], "")` を L3 の system に前置）だけ。

つまり **現在の mu では「専門家を一人動かす」ことができない。PjM を経由しないと専門家になれない。**
専門化（個人軸）を、組織の機能（組織軸）が独占している。

対処の方向: `Orchestrator.run` に `profile`（役割定義＋道具束）を渡せるようにし、L4 はプールから
profile を**選ぶだけ**にする。`l3_chat.py --role qa` が動く状態が目標。
効用は配線の整理ではなく、**役割定義を組織機構抜きで単体検証できる**こと。
現在「QA が自己修正して自己承認した」（LONGTERM_TODO、f1×12b r2）を観測するには L4 を丸ごと回す必要があり、
H セットの実績で1走 2〜13分かかる。二軸に切れば専門能力の検証は L3 単体の実験になる。

### A-5. 組織軸の順序原理は「規模」ではなく「調整失敗のクラス」

軸を立てたら順序原理を決めないと「内側から一枚ずつ」の規律が効かない。人数で並べると capability の
階段にならない（10人でも逐次なら1人の直列と同型）。並べるなら:

| | 分業の様式 | その段が初めて解く失敗 |
|---|---|---|
| **O1**（現状） | 逐次・役割注釈付きタスク列 | 職掌の混線（実装者が判定する等）。**調整問題は無い**（キューだから） |
| **O2** | 並列 | **競合**（共有 artifact への同時書き込み、部分順序、合流） |
| **O3** | 階層（組織の組織） | **委譲による情報損失**（上位が下位の文脈を持たない） |

この見方を採ると、合意006 の「**並列は後から足せる最適化にすぎない**」（006 L80-85, L110）は改訂対象になる。
並列は速度の話ではなく、**O1 には存在しなかった失敗クラス（競合）を持ち込む段**であり、最適化ではなく段そのもの。
006 が正しかったのは「依存グラフを逐次のうちに作っておけば並列化は独立タスクの同時実行だけになる」（006 L126-127）
という**準備の正しさ**であって、並列が軽いという主張ではない。
なお、その依存グラフは今まだ散文への部分一致で推定されている（→ C-2）。逐次では「余計に再実行される」で
済んでいる誤差が、並列では「壊す」に化ける。**O2 の前提条件は `deps` の明示化**である。

### A-6. 人選に「レベル」が要る

現在の PjM の人選は**モデルの割り当て**のみで、メンバーは全員フル L3（`mu/l4.py:293 self._l3.run(...)`）。
QA タスク（SPEC と実物を読んで verdict.md を1枚書く）にも Plan・単位分解・Reflect・verify ゲートが丸ごと動く。
H セットのログでその通りになっており、明らかに過剰。

二軸なら「メンバーの**個人軸上の位置**」も人選の変数になる。QA は L2 で足りる、機械的な整形は L1、設計は L3。
組織軸の設計問題は「誰を雇うか」ではなく **「どの深さの誰をいくらで雇うか」** になり、
予算（→ D-3）とも初めて噛み合う。一次元モデルからは出てこない発想。

### A-7. 二軸のリスク — 二正面

本プロジェクトの強さは「フロンティアが常に一つ」だったこと。二軸にすると前線が2つになり、
両方が半端になる失敗があり得る。歯止めとして軸間のゲート規則を明文化したい。案:

> **組織軸を1段上げてよいのは、個人軸の現在地が「N 体並べても破綻しない程度に安く・確実」になったときだけ。**

現状に当てると: L3 一体が数分〜10分かかり確率的に失敗する以上、O2 に行けば不確実性が掛け算になる。
H4 の escalate も並列では直らない（原因は実装者のスコープ規律と check 文字列の脆さ＝**個人軸の装備側**）。
**当面の前線は組織軸ではなく個人軸の装備**、という結論が二軸モデルから素直に出る。

## B. 【最重要】「決定論の床」が床になっていない

`check = {run, expect(部分一致)}` は**同じ LLM が書いている**。planner が自分の答案の採点基準を自分で書く構造で、
H セットの実物を読むと過半が空振りしていた。

### B-1. 実際に空振りしていた check（H セットの実物）

| 走 | check | 実際の性質 |
|---|---|---|
| deadstock | `Get-ChildItem deadstock_report.csv` → 期待「deadstock_report.csv」 | **同語反復**。ファイル名は必ず出力に出る。中身は無検査 |
| jsonparse | `Get-Content jsonparse.py \| Select-String 'import json', 'from json import'`（expect 無し） | **原理的に落ちない**。Select-String は一致しても不一致でも exit 0。禁止制約は機械検査されていない |
| perf | `Measure-Command { python analyze.py } \| Select -ExpandProperty TotalSeconds`（expect 無し） | 秒数を**出力するだけで比較していない**。3秒要件はゲートを通っていない |

`mu/l3.py:258-263 run_check()` は expect が空なら exit 0 のみで True を返す。上記2件は「常に合格する検査」。
つまり H2 の禁止制約も H6 の性能要件も、実際に担保していたのは QA（LLM）と、事後に人間がログを読んだこと。

**記録の是正**: `runs/2026-08-01-hard/README.md` の H6 評「行数・時間とも実測検証」は、
**測っただけで照合していない**ため一段強すぎる。H1 の「✅ 正解（P007, P010）」も、
機械検査は列名の部分一致までで、正解性は人間の読みが支えている。

### B-2. 根は check DSL の表現力 — 否定と数値比較が無い

`{run, expect}` は「出力に文字列 X を含む」しか書けない。欠落しているのは
**否定（X を含まないこと）** と **数値比較（3.0 以下）** で、これは
H セットが狙った「難しい制約」のクラスそのものである。処方の候補（安い順）:

1. **check の健全性ゲート（コード側・数行）** — `expect` が `run` 文字列の部分列なら不正として弾く。
   これだけで deadstock / jsonparse の同語反復が消える。
2. **check の反証テスト** — 成果物を退避（or 空ファイル）した状態で check を先に走らせ、
   **そこで合格してしまう check は無効**として PjM に差し戻す。「合格する検査」ではなく
   **「不合格になりうる検査」だけを床として数える**。B-1 の3件すべてを捕捉できる。
   費用はコマンド1回。思想（実体で判定する）と完全に同じ向き。
3. **言語の拡張** — `expect_not` ／ `exit`（期待終了コード）／ `max`（数値上限）。①②より重いが、
   性能要件と禁止制約を扱うなら結局必要。

②を入れるまで、「偽・完遂 0」という主張は check ではなく**人間の読みが支えている**と読むべき。

### B-3. 二軸から見た病名 — 検証は本来「個人軸の装備」

検証の床の問題は軸の切り方では直らないが、二軸で見ると病名が変わる:
**「検証は本来 個人軸の装備であるべきなのに、組織軸の役割（QA）に外注されている」。**
自分の主張を自分で反証する能力は、チーム以前に一人が持つべきもの。L2 の Reflect はその萌芽であり、
005 でそれを実体寄りに強化した。その延長に「自分が書いた check を自分で反証してから提出する」を置けば、
QA は**二重化**であって代替ではなくなる。現在は代替になっているため、QA が甘い日に床が消える。

## C. 機構の穴（実走で確認）

### C-1. 「1タスク = 1ファイル」という同一性が実物と合っていない

deadstock の実装タスクは `file: deadstock_report.csv` だが、実際に生成された成果物は
**`calculate_deadstock.py`（3713 bytes）**。これは PROCESS.md に現れず、invalidate の対象にもならず、
`_carry_done` の同一性判定からも見えない。

**成果物がプログラムで、ファイルがその出力**になった瞬間、file を単位の同一性とするモデルは破綻する。
`_carry_done`（l3）・`_invalidate`（l4）はどちらもこの前提の上に立っている。

### C-2. `_invalidate` の伝播が「部分再実行」を実質的に無効化している

deadstock 2周目に実データがある。PjM は最小集合 `invalidate=['deadstock_report.csv']` を**正しく選んだ**のに、
`mu/l4.py:432` の**散文への部分一致**で architect タスク（task 文に "deadstock_report.csv" と書いてある）まで
巻き込まれ、**承認済みの design.md が別物に書き直された**（2970 bytes → 2626 bytes、`deadstock/run.log` L21・L192）。

問題は3点重なっている:

- 伝播が**無向** — 上流の設計タスクへ逆流する。設計書は全成果物に言及するので、design.md がある限り
  「どれか1つの無効化 = 全体再実行」に縮退する。
- 判定が**字句的**（`f in texts`）— ファイル名が普通名詞に近いと誤爆する。
- 再実行が**破壊的** — 前版の artifact が残らない。

対処: 依存は推論せず `deps: [file...]` として PROCESS スキーマに持たせる（A-5 のとおり O2 の前提でもある）。

小さいバグ: `action=rerun` で `invalidate` が空だと **QA だけ再実行**され（`mu/l4.py:440-442` が QA を無条件に落とす）、
同じ verdict が出て1周を捨てる。

### C-3. H3 の診断は正しいが、処方が一段浅い

`runs/2026-08-01-hard/README.md` と LONGTERM_TODO は「PdM に『矛盾を検出したら escalate』を足す（確率的ガード）」で
止まっている。しかし本当の欠落は **どの層にも「与えられたものが間違っている」と言うための出口が無い**こと。

`_SPECIFY_SCHEMA` は `spec` を必須にしており（`mu/l4.py:63`）、壊れた応答は目的の原文にフォールバックする
（`mu/l4.py:502-504`）。つまり **specify は必ず何かを返す**。矛盾を検出した PdM に残された行動は
「退化解を書く」しかなかった。規範の問題ではなく、**スキーマに null チャネルが無い構造の問題**である。

対処: `unsatisfiable: bool` ／ `blocking_questions: []` を `_SPECIFY_SCHEMA` に足し、非空ならコード側で無条件 escalate。
これで「確率的ガード」が「決定論の床」に変わる（本プロジェクトが得意な形の一手）。

補足（TODO 案(b) の配線確認）: `_write_spec` は SPEC.md に「## 目的（人間の入力・原文）」を含めており
（`mu/l4.py:556`）、QA タスクの参照ファイルに SPEC.md が入る（`mu/l4.py:411`）。
つまり **QA は目的の原文を既に読める**。「SPEC が目的の制約を弱めていないか」を `roles/qa.md` に
1行足すだけで済む。安いので (a)(b) 両方やる価値がある。

### C-4. 小さいもの

- `run_check` は **LLM が書いた文字列をそのままシェルに渡す**。`protect()` が execute_command の
  リダイレクトを通さないことも既知（`tools.py:30`）。README の「使い捨てディレクトリで実行」は
  注意書きではなく**設計上の性質**として前面に書くほうが誠実。
- `mu/l4.py:34` が `l3` から `_parse_json` / `_with_env` の**私的名を2つ import** している。
  `transcript` で一度直したのと同じ匂い。JSON サルベージ処理は l2/l3/l4 に散っている。
- `step()` が L1/L2 にしか無く、「中断・再開の対称性」は原則として掲げつつ L3/L4 で成立していない。
  LONGTERM_TODO では優先度:低だが、1ラウンドが10分を超える現在は上げてよい。

## D. 工学的な足回り

### D-1. 再現性がほぼ無い（記録が資産である以上、これは重い）

- `tools.py` が PowerShell 直書き（`tools.py:54`）。Linux でテストを回すと `test_tools.py` の2件が落ちる。
- すべての SPEC/PROCESS の check コマンドが PowerShell 固有。**H セットは著者の1台以外で再現できない。**
- CI 無し（`.github` が存在しない）。
- README の「テスト全体 73 green」は現状（118 件）と乖離。ドキュメント drift は
  [review-2026-07-20.md](review-2026-07-20.md) の A-1 と同じパターンの再発。

experiment 記録と runs/ が価値の中心なのに、検算できる人が一人しかいない。
`sh` バックエンド追加＋live 以外を回す CI は費用対効果が高い。

### D-2. 実験方法論が自己採点になっている

`runs/2026-08-01-hard/README.md` が自ら書いているとおり、課題設計・実行・評価がすべて AI 側。
H3 を自分で摘発したのは立派だが、B-1 と合わせると「6走とも偽・完遂なし」は
**偽・完遂を生む当の系が下した判定**である。
check 言語を直してから同じ6課題を再走させるのが筋で、ついでに**初の回帰コーパス**が手に入る。

### D-3. 予算が「周回数」しかない

`max_rounds` 系は揃っているのに、**文脈量・時間・トークンの予算が無い**。
L2 は同一の `messages` リストに最大 `max_rounds` × `l1_max` 周ぶんを蓄積し続け、剪定も要約もしない
（tool 結果は1件 4000字）。`read_file` の 4000字（`tools.py:24`）と transcript の 6000字（`mu/l2.py:126`）が
別ファイルで独立に決まっているのも、「証拠管理」という概念が無いまま截断だけがある状態を示す。
LONGTERM_TODO の「証拠デッドロック」はこの欠落の一症状で、個別に潰すより概念を1つ足す箇所に見える。
H4 が13分かかったのも同じ根。A-6（人選にレベルを入れる）とここで噛み合う。
