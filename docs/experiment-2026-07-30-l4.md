## F1 × gemma4 — 偽・完遂の機序（3因子の合成）

タイムライン（ログより）:

1. 単位3（selftest 実装）で、selftest を含む完全版の write_file が **path 欠けで2回連続失敗**
   （`error: write_file() missing 1 required positional argument: 'path'`。LONGTERM_TODO 既知の steering 穴）。
2. 旧版に `--selftest` を打って exit=1（引数が無い）→ 書き直し。このとき **生成が途中で切れた断片
   （2346 bytes）** が書き込まれた。断片は 71 行目の `delete_todo` の途中で
   `# Re-writing properly now.` というコメントを残して終わっており、search・undo・selftest・main 呼び出しが無い。
3. その断片に `python todo_app.py --selftest` → **関数定義だけで何も実行しないため exit=0**。
4. L2 Reflect: `[tool execute_command ok | exit=0]` という**本物の fact** を根拠に
   「selftest を実装し実行で検証した」と pass。**facts は真、推論が誤り。**
5. L4 assess: 証拠抜粋（1200字で truncated、truncated 明示あり）の**見えていない部分**を
   「全機能・12件の selftest がある」と外挿して yes。`NEVER guess` ガードは無視された。

### 診断

- **機序②の変種を観測**: 「未書き込みの提案コード」ではなく「**書き込まれたが不完全な実体**」。
  transcript には良品コードが、ディスクには断片がある。構造化 tool 結果の facts（wrote 2346 bytes / exit=0）は
  すべて真で、防御は機能した——**誤ったのは fact からの推論**。
  → **合意005 未決5の解除条件「構造化 tool 結果だけでは防げない事例を観測する」が正式に発火。**
- **no-op exit=0 の穴**: 「exit 0」という criterion は、何も実行しないスクリプトが自明に満たす。
  実行可能な受入条件は「exit code」だけでは足りず、**可視の出力（例: 実行されたテスト数の表示）**を要求する必要がある。
- **証拠の切り詰め**: L4 の `_EVIDENCE_LIMIT`(1200) はファイル後半を見せない。truncated は明示していたが、
  gemma はその先を外挿した。

## モデル切り分け（受入条件「構造限界とモデル限界」）

同じ構造・同じ切れた証拠に対して:

- **qwen3.5** は「抜粋が `load_todos` の途中で切れている。selftest の実装が見えない。判定できない」と
  **見えないものを見えないと言い**、uncertain 側に倒して上げた。
- **gemma4** は見えない部分を楽観外挿して yes と言った。

→ **構造は判定材料を正しく届けている。最後の一線（見えないものを推測しない規律）がモデル依存**。
「プロンプトのガードは確率的にしか効かない」（F1-g2 で実証済み）の再実証であり、
決定的に守りたいなら**コード側**に置くしかない、という既知の結論を L4 でも確認した。

## 課題（対処は師匠と協議してから）

1. **verify スロット化の協議再開** — 未決5の解除条件が発火した。選択肢は合意005 記載の
   (a) L2/L3 に verifier スロット（コード検証器の差し込み口）を足す
   (b) criterion を実行可能コマンドに寄せ既存 tools で検証、の再評価。
   今回の穴に即して言えば「selftest の実行結果を**コードが**確認する」(a) か、
   「criterion に可視出力（テスト数表示）を要求する」プロンプト強化（確率的）の比較になる。
2. **L4 証拠収集の範囲** — units のファイルに加えて、**完了条件が名指しするファイル**と
   **workdir の一覧**を証拠に含める（コード変更・小）。sales × gemma4 はこれだけで受理できた可能性が高い。
3. **証拠切り詰めの扱い** — truncated な証拠で yes と言わせない。
   (a) 判定前に全文読む（文脈コスト増） (b) truncated のとき yes を禁止しコード側で uncertain に落とす
   （機械的・過剰保守の恐れ） (c) 現状維持でモデル規律に任せる。
4. **write_file path 欠け steering**（LONGTERM_TODO 既存項目・優先1）— 今回も偽・完遂の第1因子。
   pi 学びA-1（引数検証エラーに usage＋受領引数をエコー）の実装優先度が上がった。
5. **実行時間** — qwen3.5 は F1 68分・sales 96分。層が増えるほど1タスクが伸びる既知リスクの実測値。
   probe 設計（上限の予算）に効く。
