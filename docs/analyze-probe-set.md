# `_ANALYZE_SYSTEM` 詰め用 — 失敗する題材セットと評価シート

- **日付**: 2026-07-20
- **目的**: L3 の失敗分析プロンプト `_ANALYZE_SYSTEM`（`mu/l3.py`）を **genuine failure** で検証・調整する。
  合意004の積み残し（これまで観測した失敗は判定不能起因の「空 analysis」のみで、本物の失敗を診断した実績がない）。
- **背景**: analysis の `{reason, suggestion}` は再計画（A）の入力。診断が誤ると再計画が盲目リトライに退化する
  （skill: 失敗には分析が伴う）。
- **タスク元**: [../LONGTERM_TODO.md](../LONGTERM_TODO.md)

## 実行方法（共通）

1. **使い捨てディレクトリ**を作り、そこから `l3_chat.py` を起動する（成果物は cwd に生成されるため）:
   ```
   mkdir ..\mu-probe-f1 ; cd ..\mu-probe-f1 ; ..\mu\.venv\Scripts\python.exe ..\mu\l3_chat.py
   ```
2. 各題材の**ゴール（1行）**をそのまま入力する。
3. モデルは **gemma4:12b（既定）→ qwen3.5:9b** の順で両方走らせる（構造限界とモデル限界の切り分け）。
4. 上限は l3_chat の既定のまま（MAX_ROUNDS=8 / L2_MAX=6 / L2_L1_MAX=10）。
5. 記録するもの: **Plan 全文／`[!] UNIT FAILED` の reason・suggestion（＝analysis）／再計画の Plan 全文／最終結果**。
   ターミナル出力をファイルに残す（コピペで可）。

**HITL の原則**: 承認は基本 `y`。ただし各題材の「罠の保持」欄に従い、**罠を先回りして解消する単位が Plan に
現れたら `d N` で削除**して罠を維持する。Plan が罠を自力回避したこと自体も記録する（それは Plan プロンプトの
強さのデータであり、失敗ではない）。

## 題材セット

`_ANALYZE_SYSTEM` の分類語彙（ill-defined / too large / wrong approach / missing dependency）に1対1で対応させる。

### F1 — 大きすぎる単位（too large）

**ゴール（1行）**:
```
todo_app.py 1ファイルだけでCLIのTODO管理アプリを作る。機能: 追加・削除・一覧・完了・期限(YYYY-MM-DD)・優先度・キーワード検索・undo・JSON自動保存。成功条件: python todo_app.py --selftest が全機能を検査して exit 0（セルフテスト12件以上）。todo_app.py 以外のファイルを作らないこと。
```
- **狙い**: 「1ファイルだけ」の制約で分割を封じ、1単位に9機能＋セルフテスト12件を押し込ませる。
- **期待する失敗機序**: L2 が 6 周以内に全機能＋セルフテストを完成できず未達。
- **期待される analysis**: reason=too large。suggestion=同一ファイルへの**段階単位への分割**（core → 機能追加 → selftest 拡充）。
- **罠の保持**: （2026-07-20 更新）file 一意ガード導入後、同一ファイルの複数単位は出ない想定。
  出たらガード違反として記録。分割回避が封じられたため、再走では今度こそ too large が発火する想定。
- **ノブ（失敗しないとき）**: 機能に「タグ・繰り返し期限・CSVエクスポート」を足す／セルフテストを20件以上に。
- **観測ポイント**: ~~再計画が同一ファイルパスの複数単位を出したとき、`_carry_done`（file キー）が未完単位を
  誤って done 扱いしないか~~ → **F1-g で実発火・2026-07-20 修正済み**（プロンプトガード＋`_carry_done` 防御）。
  **F1 は修正後に再走が必要**（初走は偽・完遂で終わったため）。

### F2 — 依存欠け（missing dependency）

**ゴール（1行）**:
```
既にある stats_lib.py の mean と median を import して、data.csv の数値列の平均と中央値を stats_report.txt に書き出す report.py を作る。成功条件: python report.py が exit 0 で stats_report.txt が生成されること。
```
- **狙い**: 「既にある」と偽って存在しない `stats_lib.py`・`data.csv` を前提にさせる（二重の欠落）。
  Plan プロンプトは「ゴールが要求しない単位を足すな」と言っているため、存在確認の単位は立ちにくい。
- **期待する失敗機序**: `python report.py` が ImportError / FileNotFoundError で exit≠0 → 未達。
- **期待される analysis**: reason=missing dependency。suggestion=stats_lib.py（と data.csv）を生成する単位を
  **先行単位として追加**する再計画。
- **罠の保持**: Plan が最初から stats_lib.py / data.csv を作る単位を含めてきたら **`d N` で削除**して罠を維持する。
- **ノブ**: L2 が気を利かせて自分で stats_lib.py を作ってしまう場合 → ゴール末尾に
  「stats_lib.py と data.csv は変更・作成しないこと」を追記。

### F3 — checkable でない基準（ill-defined / not checkable）

**ゴール（1行）**:
```
essay.md に春をテーマにした随筆を書く。成功条件: 人間の審査員が5段階評価で4以上を付けること。
```
- **狙い**: transcript からは決して検証できない成功条件。L2 の Reflect は「検証できなければ pass しない」
  規則なので、証拠の出しようがなく必ず上限まで回る。
- **期待する失敗機序**: L2 が l2_max=6 周を空転して未達（essay.md 自体は書けている）。
- **期待される analysis**: reason=ill-defined / not checkable。suggestion=基準を checkable な形へ**再定義**
  （例: 字数・構成・必須要素）。人間の受け入れが必要なら HITL に上げる、でも可。
- **罠の保持**: 不要（ゴール自体が罠）。
- **観測ポイント**: Reflect が「感動的」を勝手に自己判定して pass させないか（させたら Reflect プロンプトの穴）。

### F4 — 自動検証できない受け入れ境界（wrong approach）

**ゴール（1行）**:
```
tkinter で clock.py を作り、ウィンドウに現在時刻を1秒ごとに更新表示する。成功条件: 画面を目視して時刻が動いて見えること。
```
- **狙い**: 北極星で観測した「GUI＝auto-checkable でない崖」を最小形で再現。目視は transcript に載らない。
  さらに `execute_command` で GUI を起動すると mainloop がブロックし 60 秒タイムアウトで error になる。
- **期待する失敗機序**: 検証不能＋実行タイムアウトで L2 未達。
- **期待される analysis**: reason=wrong approach（自動検証できない受け入れを自律単位にしている）。
  suggestion=検証可能なロジック部分（時刻文字列生成など）と GUI 受け入れ（HITL）への**分離**。
- **罠の保持**: 不要。
- **観測ポイント**: analysis がタイムアウトを「コードのバグ」と誤診しないか（誤診したら詰めどころ）。

### F5（任意）— 達成不能な条件（条件の変更を要する失敗）

**ゴール（1行）**:
```
sort_bench.py を作り、乱数100万件のリストを組み込み sort/sorted を使わず純Pythonのループだけでソートして所要秒数を表示する。成功条件: python sort_bench.py が exit 0 かつ表示された所要時間が0.01秒未満であること。
```
- **狙い**: 実装は正しくできるが**条件が物理的に満たせない**失敗。再計画の3方向（条件/アプローチ/計画）のうち
  「**条件の変更**（または人間への escalation）」を引き出せるかを見る。
- **期待される analysis**: reason=条件が達成不能（wrong approach/condition）。suggestion=条件の緩和を提案するか、
  ゴール自体の変更が必要として上位（人間）へ上げる。**勝手に基準を読み替えて pass させたら重大な穴**。

## 実施記録

### F1-g（2026-07-20 / gemma4:12b / temp/f1）

**経過**: Plan は「1ファイルだけ」制約を **同一ファイル todo_app.py の3単位分割**で合法回避（core → 永続/検索/undo → argparse+selftest）。単位1・2 はコード提示ベースの緩い基準で pass。単位3 が genuine failure（l2_max=6 を使い切り）。

**単位3の失敗機序（複合）**:
1. **証拠デッドロック**: ファイルが 4.7KB に成長し、`read_file` の 4000 字截断＋transcript の 6000 字上限により「全文提示」が**原理的に不可能**。Reflect は「truncated だから検証できない・全文を見せろ」を繰り返し、L1 は read_file を9連発する空転に陥った。
2. **ツール呼び出しの退行**: モデルが `write_file` を **path 欠き**で6回呼び続け（`error: missing 1 required positional argument: 'path'`）、argparse+selftest 入りの完成版を一度もディスクに書けなかった。エラーを受けても自己修正せず。

**analysis の評価（本題）**: reason="wrong approach" は浅い誤診（起きたのは実行系の失敗）。suggestion は「write_file が失敗した」という**症状の記述**で、構造を変える提案なし。再計画は同一3単位の焼き直し＝盲目リトライ相当。→ **合格基準 1・2・3 すべて不合格**。詰めどころ:
- 分類語彙に「実行系の失敗（ツール呼び出し・証拠提示の失敗）」が無い
- suggestion に「計画をどう変えるか」を強制していない

**偽・完遂の機序（重大なハーネス欠陥・本 doc の観測ポイントが実発火）**: `_carry_done` は **file キーのみ**で done を引き継ぐ。単位1・2（done）と失敗した単位3が同じ `todo_app.py` のため、再計画承認後に**3単位すべてが [x] 化**。次周で pending 空 → overall が `[x]`＝実行検証済みと信頼（設計どおり）→ passed=True → **完遂✓**。

**成果物の実状（実行で確認）**: `todo_app.py` に argparse・`--selftest` 分岐・期限・優先度は**一切無い**。`python todo_app.py --selftest` は引数を無視してデモを実行し exit 0（毎回 todos.json に重複タスクが堆積する非冪等）。**ゴールの成功条件は未達＝完遂✓は偽**。

**派生した修正候補（LONGTERM_TODO に登録済み）**:
1. **[重大] `_carry_done` の同一ファイル穴** — ✅ **2026-07-20 修正済み**。Plan/Replan プロンプトに「file はプラン内で一意（同一ファイルの作業は1単位に併合）」を追加し、`_carry_done` は旧計画・新計画のどちらかで file が重複する場合 done を引き継がない防御に（安全側: 済み単位の再実行は取り返せるが、偽 done は overall が信頼するため取り返せない）。TDD で偽・完遂の再現テスト含む3件を追加、全73 green
2. **証拠デッドロック** — 未着手。大きいファイルは内容提示でなく**実行ベースの証拠**へ誘導（Reflect プロンプト）／criterion 側に「機械可読な合格出力（例: `12/12 passed` を印字）」を要求させる（Plan プロンプト）
3. **必須引数欠けエラーの steering** — 未着手。`_invoke` の TypeError 時に usage_text を添えて返す（自己修正の手がかり）

**`_ANALYZE_SYSTEM` の合格基準**（プロンプト調整の完了条件）:

1. **分類の正確さ**: 各題材で reason が仕込んだ失敗モードを言い当てる（gemma4:12b で 4/4。qwen は参照）。
2. **提案の実効性**: suggestion に従った再計画が「分割・単位追加・基準再定義・HITL 送り」など**構造を変える**
   内容になる。同じ単位の焼き直し（盲目リトライ）は不合格。
3. **誤診しない**: タイムアウト→バグ、検証不能→未実装、のような取り違えをしない。
4. **最終到達**: 再計画後に完遂するか、達成不能なもの（F3/F4/F5）は「人間の判断が要る」ことが
   analysis/再計画に明示される。

**調整の進め方**: 不合格が出た題材の transcript を見て `_ANALYZE_SYSTEM` にガード文を足す
（`_PLAN_SYSTEM` に「run だけの単位禁止」を足したのと同じ流儀）。1文足すごとに当該題材を再走し、
他の題材が退行しないことを確認する。プロンプト変更は都度コミットする。

**注意**: 題材が失敗しなかった場合（モデルが完遂してしまった場合）は「ノブ」で難度を上げて再走する。
それでも完遂するなら「そのモードは現行構成では起きにくい」というデータとして記録し、深追いしない。
