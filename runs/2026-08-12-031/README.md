## 3. 並列は実走で発火する（機構の実証）

width p2 のログ: `TASK START poem_a.md` → poem_a 実行中に `TASK START poem_b.md` →
poem_b 完了 → poem_a 完了 → QA。**独立2タスクの同時実行・完了順の逆転・QA バリア**が
実機で観測された。PjM（12b）は幅のある仕様に対して自然に幅のあるプロセス
（独立2タスク＋QA）を編んだ——「幅の促し」の規範なしで。

## 4. 速くなるか — ローカル 12b ではノイズに埋もれる（師匠の予想どおり）

12b の走間ばらつき（同一条件の逐次で 127s〜572s、4.5倍）が、並列の理論利得
（このプロセスでは高々 taskの重なり分）より一桁大きい。**この環境・この題材では
並列の速度利得は観測できない**。フェーズ0の L0 プローブでは並列自体は効いている
（直列2本 1.2s → 並列 0.7s）ので、利得が現れる条件は「タスクが長く・幅が広く・
モデル実行が併走に耐える」場合（クラウドモデル前提の本線と整合）。

## 4b. 追試 — 同じ幅テストを gemma4:31b-cloud で（2026-08-13・師匠の指示）

条件は上の 12b 走と**同一**（同じ `width-spec.json`・同じプール構成 `[gemma4:31b-cloud,
qwen3.5:9b]`・同じ `l4_chat` 経路）で、主モデルだけ差し替え。逐次と並列2を**交互に**
各4走（クラウド側の時間帯ドリフトを条件間で相殺するため）。

| 条件 | 実時間（4走） | 中央値 | 最小 |
|---|---|---|---|
| 逐次 | 43 / 75 / 159 / **895** s | 117s | 43s |
| 並列2 | 58 / 66 / 98 / **395** s | 82s | 58s |

**全8走とも `done`・rounds=1・受入基準2件 ok・verdict yes**（正しさの劣化なし）。
並列4走すべてで `TASK START poem_a` → `TASK START poem_b` の重なりを確認、
うち1走（p2c）は**完了順が逆転**（poem_b → poem_a）——並列は 31b でも正しく発火している。

**速度利得はここでも言えない。理由は前回と違い、特定できた。**
LLM 呼び出しの秒数をフェーズ別に集計すると、ばらつきの出所が**作業フェーズではなく
QA フェーズ**にある:

| フェーズ | 逐次（中央値） | 並列2（中央値） | 走間の幅 |
|---|---|---|---|
| 作業（poem_a / poem_b＝並列化の対象） | 48s | 34s | 16〜89s |
| **QA（バリアの後・原理的に常に逐次）** | 57s | 53s | **20〜812s（40倍）** |

外れ値2件（逐次 895s・並列 395s）は**どちらも QA タスクの空転**で、QA は
`qwen3.5:9b`（ローカル）に人選されている。**条件に依存しない**——逐次でも並列でも同じ確率で
起きる。並列化できない区間が支配的で、そこが最大のばらつき源である以上、
この題材では並列の利得は原理的に埋もれる（Amdahl）。

**分かったこと**: 「ローカル 12b だから利得が見えない」という 4 節の見立ては**不正確**だった。
クラウドに替えると全体は確かに速くなる（最小 43s ／ 12b の逐次 127s）が、**並列利得が
見えない理由は主モデルではなく、(a) 並列化対象の区間が短いこと (b) 直列区間（QA）が
ローカルモデルで大きく揺れること**にある。

**次に測るなら**（未実施・要判断）: QA も含めプール全体をクラウドに寄せる
（`l4_chat ... gemma4:31b-cloud` のみ）と直列区間の揺れが落ち、並列区間の比率が上がる。
題材側を広げる（独立タスクを4〜6本）と並列区間が支配的になる。どちらも**条件を変える**ので
「同テスト」ではなくなる。

生ログ: `width-31b-p1{,b,c,d}.log`（逐次）/ `width-31b-p2{,b,c,d}.log`（並列2）。

## 4c. 追試2 — プール全体をクラウドに寄せて（QA も 31b-cloud・各8走）

4b で「ばらつきの出所は QA フェーズ（ローカル `qwen3.5:9b`）」と特定できたので、
**プールから `qwen3.5:9b` を外すことだけ**を変えて測り直した（spec・経路・交互実行は同じ）。
QA も `gemma4:31b-cloud` に人選される。逐次・並列2とも **n=8**。

| 条件 | 実時間（8走・昇順） | 中央値 | 平均 | 達成 |
|---|---|---|---|---|
| 逐次 | 32 / 33 / 43 / 47 / 49 / 52 / 76 / 102 s | **48s** | 54s | 8/8 |
| 並列2 | 25 / 35 / 35 / 36 / 41 / 41 / 43 / 82 s | **38s** | 42s | 8/8 |

**全16走とも `done`・受入基準2件 ok・verdict yes。** 並列走はすべて重なりを確認。

### 直列区間をクラウドに寄せた効果（4b との比較）

| | 逐次 中央値 | 並列 中央値 | ばらつき（最大/最小・逐次） |
|---|---|---|---|
| QA＝ローカル 9b（4b） | 117s | 82s | **20.8倍** |
| QA＝クラウド 31b（4c） | 48s | 38s | **3.2倍** |

QA を直列区間から取り除いたのではなく、**直列区間の実行体を替えただけ**で、
全体が半分以下・ばらつきが1桁縮んだ。4b で立てた診断は正しかった。

### 並列利得 — 向きは一貫、大きさは理論値どおり。ただし統計的には未確定

- 中央値の比 **0.80x**（n=4 の時点でも 0.78x——n を倍にしても向きと大きさが動かない）
- **差の 10s は、この題材の理論最大とほぼ一致する**: 作業フェーズの LLM 中央値は
  両条件とも 22s（同じ仕事）で、独立2タスクが完全に重なれば節約できるのは高々その半分＝11s。
  観測された中央値差は 48−38＝**10s**
- しかし **Mann-Whitney U 検定（正確法・両側）は p = 0.20 で有意ではない**（U=19.5, n=8/8）。
  残ったばらつき（QA が Reflect を1周多く回す走。呼び出し 20回 → 35回）が
  効果と同じ桁のため、n=8 では分離できない

**結論**: 「クラウドに寄せれば並列が効く」は**示唆されたが、証明されていない**。
向きの一貫性と理論値との一致は強い状況証拠だが、有意差の主張はしない。

**決定的に測るなら**（未実施）: 題材を広げる（独立タスク4〜6本）と並列区間が支配的になり、
効果がばらつきを上回る。n を 20 前後まで積むより安い。

生ログ: `width-cloud-p1*.log`（逐次8本）/ `width-cloud-p2*.log`（並列2・8本）。

   「参照できるファイル: SPEC.md」と実在しないファイルを名指しし、QA が探して空転。
