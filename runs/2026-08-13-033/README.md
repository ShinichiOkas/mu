# 033 実走記録 — 診断精度の単体測定（2026-08-13）

合意 [033](../../.pair-agent/agreements/033-l6-diagnosis-and-design.md) フェーズ B。
L6 の中核能力＝**診断**を、機構ゼロで単体測定した（028「選択のみ精度」と同型）。
学習者（`roles/learner.md`）に生ログの材料を渡し、構造化出力の1判断で診断させ、
台帳（`ledger/`・確定診断10件）と照合する。

- 条件 R: 台帳に正解あり → 正解＝そのモード名（機械照合）
- 条件 N: 台帳から正解を抜く → 正解＝new_mode の正直な申告＋機構の記述
- 材料: thin（ツール列なし）/ thick（あり）。9ケース × R/N × thin/thick × 2反復 ＝ **72判断・エラー0**
- モデル: `gemma4:31b-cloud`。生データ: `matrix.jsonl`（1判断1行）・疎通: `smoke.jsonl`

## 2. 誤答の法医学 — 判断の誤りか、配線（計器）の欠陥か

skill [[mechanical-causes-before-intentional-ones]] / [[verify-what-the-agent-actually-received]]
に従い、誤答ごとに「証拠は材料に実在したか」を機械で確認した。

| ケース | 判定 | 中身 |
|---|---|---|
| qa-self-fix | **計器の欠陥（gold が誤り）** | f1-12b.log には「権限で拒否」が **46行実在**——この走は write_scope ガード**適用後**で、ログが示すのは「自己修正の**試み**が権限で止められた」姿。私はスプリントの物語から gold を貼り、**ログを検証しなかった**。学習者が denied-becomes-an-obstacle と答えて拒否行を引用したのは、実在の証拠を読んだ結果 |
| quantifier | **計器の欠陥（材料に答えが無い）** | 020 runtime.log には**目的の原文が印字されていない**（「必ず」は0回。ログは既に弱化済みの SPEC から始まる）。∀→∃ の検出には目的と仕様の**両方**が要るが、片方しか渡していない——**このログからは原理的に診断不能**。学習者が R で 4回とも「該当なし」と答えたのは正直な挙動 |
| grounding-drop | **gold の曖昧さ（複数モードの併存）** | この走には根因（接地の切り捨て）と近因（write_file 全文再生成→917バイト）が**両方実在**する。学習者は近因を選び、`write_file(...) -> wrote 917 bytes` を正しく引用した。**近因の診断としては正しい**。gold を単一にした私の設計が、複数モード併存の走を想定していなかった |
| checker-overwritten | 切り分け不能（切り捨ての疑い） | 生ログ 229KB → 材料に残ったのは 26%（中央省略）。決定的証拠（check_sources.py の上書きの瞬間）が中央にあった可能性。真の判断ミスと断定できない |
| contract-loss | 判断の誤り（の可能性が高い） | 材料は 54% 残存・ITEM/uncertain の証拠も残っていた。転記の欠落という**時間差の比較**を要するモードは、1枚の記録からは最も見えにくい |
| invented-calls | 判断の誤り（の可能性が高い） | 材料は 86% 残存。発明の瞬間（仕様の中の実在しない呼び出し形式）は残っていたが、学習者は QA の判定に目を取られた |

**正しく機能した側**: protection-escalation **4/4**・regenerate-loss **4/4**（thick はバイト数まで
名指しの完璧な機構診断）・service-guessing 2/4。共通点は**証拠がツール呼び出しの劇的な列**として
材料に丸ごと残っていたこと。

## 3. 計器の欠陥を除いた読み

有効6ケース（計器欠陥3件を除外）の R・thick で見ると **protection 2/2・regenerate 2/2・
service 1/2・checker 0/2・contract 0/2・invented 0/2 ＝ 5/12**。
それでも 028 とは差が大きい。**診断は選択より本質的に難しい**——材料が長く・証拠が疎で・
正解が一意でない。ただしその難しさの内訳は分解できた:

1. **証拠が材料に残ってさえいれば、機構の診断は強い**（write_file のバイト数まで引用）
2. **時間差・比較を要するモード**（転記の欠落・∀→∃）は1枚の記録から見えない——
   **何を突き合わせるかを材料の側が用意する必要がある**
3. **N（該当なしの正直な申告）は 2/36 でほぼ壊滅**。34/36 が既存モードへ無理に寄せた。
   定義書に「無理に寄せるな。正直な new は安い」と明記しても、である。
   032 の no-op と同じ**否定形の答えの選ばれにくさ**——ただし R で quantifier が4回
   「該当なし」を返せている（材料に証拠が無いとき）ので、「絶対に言えない」のではなく
   「もっともらしい候補が見えていると言えない」

## 4. この測定が自分自身に台帳のモードを再演した（メタ観測）

計器の欠陥2件は、**台帳に載っているモードの再演**である:

- gold をログで検証しなかった ＝ [[verify-what-the-agent-actually-received]] の違反
  （032 で学んだ直後に、**答えの側**で同じことをした）
- 材料の中央省略が証拠を落とした（疑い）＝ `grounding-cap-drops-the-subject` と同型
  （位置で切った——診断という目的に接地していない）

**同じ失敗モードは、mu だけでなく計器を作る側（私）にも再発する。** 台帳が観測対象にすべき
なのは走だけではない——これ自体が「再発頻度を下げる」という指標1の生きた標本になった。

## 5. 次（B2 の提案）

結論を C（L6 の構成設計）に持ち込む前に、計器を直して測り直すべき:

1. **gold の全数検証**: 全ケースについて「決定的証拠がログのどの行にあるか」を人間が
   名指しし、ケース定義に記録する（検証済み gold だけで測る）
2. **材料の目的接地**: 中央省略をやめ、purpose・SPEC・検査結果・ツール列を**診断の目的順**で
   残す。比較を要するモードには両側（目的の原文＋仕様）を明示的に渡す
3. **gold の複数化**: 走に併存するモードは集合で持ち、根因/近因を区別して採点する
