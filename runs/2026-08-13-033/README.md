# 033 実走記録 — 診断精度の単体測定（2026-08-13）

合意 [033](../../.pair-agent/agreements/033-l6-diagnosis-and-design.md) フェーズ B。
L6 の中核能力＝**診断**を、機構ゼロで単体測定した（028「選択のみ精度」と同型）。
学習者（`roles/learner.md`）に生ログの材料を渡し、構造化出力の1判断で診断させ、
台帳（`ledger/`・確定診断10件）と照合する。

- 条件 R: 台帳に正解あり → 正解＝そのモード名（機械照合）
- 条件 N: 台帳から正解を抜く → 正解＝new_mode の正直な申告＋機構の記述
- 材料: thin（ツール列なし）/ thick（あり）。9ケース × R/N × thin/thick × 2反復 ＝ **72判断・エラー0**
- モデル: `gemma4:31b-cloud`。生データ: `matrix.jsonl`（1判断1行）・疎通: `smoke.jsonl`

## 2. 誤答の法医学 — 判断の誤りか、配線（計器）の欠陥か

skill [[mechanical-causes-before-intentional-ones]] / [[verify-what-the-agent-actually-received]]
に従い、誤答ごとに「証拠は材料に実在したか」を機械で確認した。

| ケース | 判定 | 中身 |
|---|---|---|
| qa-self-fix | **計器の欠陥（gold が誤り）** | f1-12b.log には「権限で拒否」が **46行実在**——この走は write_scope ガード**適用後**で、ログが示すのは「自己修正の**試み**が権限で止められた」姿。私はスプリントの物語から gold を貼り、**ログを検証しなかった**。学習者が denied-becomes-an-obstacle と答えて拒否行を引用したのは、実在の証拠を読んだ結果 |
| quantifier | **計器の欠陥（材料に答えが無い）** | 020 runtime.log には**目的の原文が印字されていない**（「必ず」は0回。ログは既に弱化済みの SPEC から始まる）。∀→∃ の検出には目的と仕様の**両方**が要るが、片方しか渡していない——**このログからは原理的に診断不能**。学習者が R で 4回とも「該当なし」と答えたのは正直な挙動 |
| grounding-drop | **gold の曖昧さ（複数モードの併存）** | この走には根因（接地の切り捨て）と近因（write_file 全文再生成→917バイト）が**両方実在**する。学習者は近因を選び、`write_file(...) -> wrote 917 bytes` を正しく引用した。**近因の診断としては正しい**。gold を単一にした私の設計が、複数モード併存の走を想定していなかった |
| checker-overwritten | 切り分け不能（切り捨ての疑い） | 生ログ 229KB → 材料に残ったのは 26%（中央省略）。決定的証拠（check_sources.py の上書きの瞬間）が中央にあった可能性。真の判断ミスと断定できない |
| contract-loss | 判断の誤り（の可能性が高い） | 材料は 54% 残存・ITEM/uncertain の証拠も残っていた。転記の欠落という**時間差の比較**を要するモードは、1枚の記録からは最も見えにくい |
| invented-calls | 判断の誤り（の可能性が高い） | 材料は 86% 残存。発明の瞬間（仕様の中の実在しない呼び出し形式）は残っていたが、学習者は QA の判定に目を取られた |

**正しく機能した側**: protection-escalation **4/4**・regenerate-loss **4/4**（thick はバイト数まで
名指しの完璧な機構診断）・service-guessing 2/4。共通点は**証拠がツール呼び出しの劇的な列**として
材料に丸ごと残っていたこと。

## 3. 計器の欠陥を除いた読み

有効6ケース（計器欠陥3件を除外）の R・thick で見ると **protection 2/2・regenerate 2/2・
service 1/2・checker 0/2・contract 0/2・invented 0/2 ＝ 5/12**。
それでも 028 とは差が大きい。**診断は選択より本質的に難しい**——材料が長く・証拠が疎で・
正解が一意でない。ただしその難しさの内訳は分解できた:

1. **証拠が材料に残ってさえいれば、機構の診断は強い**（write_file のバイト数まで引用）
2. **時間差・比較を要するモード**（転記の欠落・∀→∃）は1枚の記録から見えない——
   **何を突き合わせるかを材料の側が用意する必要がある**
3. **N（該当なしの正直な申告）は 2/36 でほぼ壊滅**。34/36 が既存モードへ無理に寄せた。
   定義書に「無理に寄せるな。正直な new は安い」と明記しても、である。
   032 の no-op と同じ**否定形の答えの選ばれにくさ**——ただし R で quantifier が4回
   「該当なし」を返せている（材料に証拠が無いとき）ので、「絶対に言えない」のではなく
   「もっともらしい候補が見えていると言えない」

## 4. この測定が自分自身に台帳のモードを再演した（メタ観測）

計器の欠陥2件は、**台帳に載っているモードの再演**である:

- gold をログで検証しなかった ＝ [[verify-what-the-agent-actually-received]] の違反
  （032 で学んだ直後に、**答えの側**で同じことをした）
- 材料の中央省略が証拠を落とした（疑い）＝ `grounding-cap-drops-the-subject` と同型
  （位置で切った——診断という目的に接地していない）

**同じ失敗モードは、mu だけでなく計器を作る側（私）にも再発する。** 台帳が観測対象にすべき
なのは走だけではない——これ自体が「再発頻度を下げる」という指標1の生きた標本になった。

## 5. 次（B2 の提案）

結論を C（L6 の構成設計）に持ち込む前に、計器を直して測り直すべき:

1. **gold の全数検証**: 全ケースについて「決定的証拠がログのどの行にあるか」を人間が
   名指しし、ケース定義に記録する（検証済み gold だけで測る）
2. **材料の目的接地**: 中央省略をやめ、purpose・SPEC・検査結果・ツール列を**診断の目的順**で
   残す。比較を要するモードには両側（目的の原文＋仕様）を明示的に渡す
3. **gold の複数化**: 走に併存するモードは集合で持ち、根因/近因を区別して採点する

## 6. B2 — 計器を修理して測り直した（師匠の指示）

修理: gold の全数検証（決定的証拠のマーカーを焼き込み、生ログでの実在と材料への生存を
テストで保証）／位置切りをやめ**優先度充填**（制御面 → ツール呼び出し → 結果 → 残り）／
gold の複数化（grounding-drop は根因＋近因の集合）／目的の注入（020 は目的の原文が
ログに無く原理的に診断不能だった）。qa-self-fix はログが gold と食い違うため削除（8ケース）。

### 数字（修理前は同8ケースで比較）

| | 修理前 | 修理後 |
|---|---|---|
| R thin | 4/16 | 5/16 |
| R thick | 6/16 | **8/16** |
| N（正直な new_mode） | 2/32 | **0/32** |

ケース別（R・4判断中）: protection **4/4**・regenerate **4/4**・grounding-drop **3/4**
（複数 gold が正当に効いた）・service 2/4・checker / contract / quantifier / invented **0/4**。

### 残った誤答の中身が、設計の答えだった

4つの 0/4 を精読すると、**全部が実在の証拠を正しく引用している**。幻覚ではない:

- **quantifier → 「失敗は検出されない」×4**: 目的（∀）を注入しても、である。当然だ——
  この走は**自分の（弱められた）基準では正当に成功している**。「何が失敗したか」という
  開いた問いでは、成功した走から失敗は見つからない。**「仕様は目的の量化を保存しているか」
  という特定の問いを立てて初めて見える**
- **checker-overwritten → denied ×4**: 012 のログには QA の権限拒否が**実在する**（007 B1
  適用後）。学習者はそれを正しく引用した。gold の上書き（実装者による）も実在する。
  **1つの走に複数の実在パターンが併存**し、開いた診断は**最も目立つもの**に吸われた
- **contract-loss / invented-calls も同型**: 引用された現象はすべて記録に実在する。
  選ばれなかっただけ

**結論: 「1判断でモードを1つ選ぶ」という診断の形式が、実ログに対して不良設定である。**
実走の記録には複数の実在パターンが併存し、単一選択は (a) 最も目立つ現象に吸われ
(b) 否定形の答え（new_mode）を構造的に不利にする（N が 0/32 に落ちたのはこの帰結）。

### C への含意 — mu が既に通った道と同じ形

この不良設定は、mu 自身が verdict で通った道の再演である。017 で「総合判定（ACHIEVED）を
書かせると壊れる。**受入基準ごとの二値にし、集約はコード**」と確立した。診断も同じ形にする:

1. **台帳エントリに「検知の問い」を持たせる**——そのモードが出たかを判定する操作的な
   質問（何と何を突き合わせるかまで指定。例: quantifier なら「目的の全称表現それぞれに
   ついて、仕様の対応する基準が per-item の検査になっているか」）
2. **診断 = モードごとの独立した二値判定 × コード集約**。「このモードは出たか yes/no ＋
   証拠」を台帳の各モードについて独立に問う
3. **new_mode はコードが導出する**——全モード no ＋ 走に失敗が実在する、の組み合わせ。
   モデルに「どれでもない」と主張させない（否定を判断から消す）
4. 複数モードの併存は**集合として自然に出る**（どれか1つを選ばせない）

## 7. B3 — 診断を「モードごとの独立二値判定＋コード集約」に作り替えた（師匠の指示）

017（総合判定を書かせず、項目ごとの二値＋集約はコード）と同型に作り替え。台帳の全10モードに
**検知の問い**（`## detect`。何と何を突き合わせるかまで操作的に指定）を足し、
1判断＝1モードで問う。**他モードは prompt に一切現れない**——候補どうしの干渉が構造的に消える。

副産物: **N 条件は同じデータから導出できる**（非 gold の判定は台帳一覧の有無に影響されない）。
64判断の別走が不要になり、80判断（8ケース × 10モード）で R も N も得られた。

|---|---|---|
| gold の検知 | 8/16（R thick） | **7/9** |

**B2 で 0/4 だった3ケースが検知できるようになった**——quantifier **1/1（かつ非 gold での
誤発火 0/9）**・checker-overwritten 1/1・invented-calls 1/1。特に quantifier は、検知の問いに
「**走が自分の基準では成功していても該当しうる**」と書いた一文で反転した。

### 「偽陽性 18/71」の精読 — **ほとんどが偽陽性ではなかった**

quantifier-weakening は非 gold の 6/7 ケースで発火した。その根拠を読むと、**すべて実在する
∀ と ∃ を正しく引用している**:

- deadstock: 目的「死に筋商品を特定して」（∀ 該当商品すべて）→ 基準「報告書に **P003** が
  記載されていること」（1商品の存在検査）
- schedule: 目的「3人が**全員**参加でき、**全員**の予定と重ならない枠」→ 基準「予約が存在すること」
- 継続責務: 目的「一致させ**続けよ**」→ 基準「README.md が存在すること」

**これは誤検知ではなく、系統的な事実の発見である。** 032 で「受入基準の語彙（`run`＋`expect` の
部分文字列一致）は存在しか表現できない」と確定した——その必然の帰結として、**∀→∃ の弱化は
例外的な事故ではなく、ほぼ全走で常態的に起きている**。020 と 032 が個別の事件として記録した
ものは、実は**系の常態**だった。診断を分解したことで初めて見えた。

blind-service-trial-and-error の4件も同様に、実在する「同型の失敗の反復」を引用している。

### この測定が露出させた設計の欠落 — **発生と原因は別**

私の gold は「**その走の見出しの失敗を起こしたモード**」でラベルしたが、検知の問いは
「**そのモードが出たか**」を問う。この2つは別物であり、台帳にも診断にもその区別が無い。

- 常態モード（quantifier-weakening）は毎走発火する。**それ自体は正しい**が、
  「今回の走で何が壊れたか」の答えとしては役に立たない
- L6 が「毎走 quantifier-weakening です」と報告し続けたら、それはノイズである
  ——ただし**一度だけは極めて重要な報告**（系の常態の発見）

→ 診断は**二段**に分けるべき: (1) 発生したか（モード別二値・LLM）(2) 結果を壊したか
（原因の特定）。そして台帳のエントリ自身に「**常態 / 事象**」の区別が要る。

### 唯一の完全な取りこぼしと、3つ目の gold の疑い

contract-loss は gold 検知 0/1。学習者の根拠は「判定書の苦戦は実装の誤り（P004 の誤判定）と
ツール使用の誤り（read_file の offset 不整合）によるもので、**契約の要求が失われた形跡ではない**」
——実質的な反論である。019 のログを見ると、契約（ITEM 行の要求）は L3 の単位にも L2 の next にも
**現れている**。B の qa-self-fix と同型の疑い（スプリントの物語から gold を貼った）が3件目として立つ。
**この gold は次に検証すべき対象**であり、現時点では contract-loss を成績に数えるべきでない。
