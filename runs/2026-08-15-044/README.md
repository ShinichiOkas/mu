## 4. しかし盲点は残った——**自己検算は自分の盲点を選べない**

`measure.json` は `{"false_statements": 0, "missing_descriptions": 0}` のまま。
私の監査は同じ状態に**嘘1件**（README「skill 現在10件」／実体11件）を検出している。

選ばれた変異は「ファイル名」と「ファイル数」——**検査器が既に見ている種類**だった。
検査器の `skill` 言及は1箇所のみで、それも `skill_kb.py` というファイル名の正規表現である。
**見ていない種類は、変異の候補にすら上がらない。**

### 偏りは私の skill 文面が作った

skill にこう書いた: 「種類の違う主張を3つ選び（**例: ファイル名の言及・件数の主張・
役割の説明**）」。**この3つは検査器の定義域そのもの**だった。
広げる意図の「種類の違う3つ」が、例示によって**狭める指定**に化けた。

038 で「範囲を限定する語は別の軸に漏れる」と学んだ形が、**今度は私の skill 文面で再発した**。

## 5. 構造の穴が1つ出た

`verify_check.md` は implementer の tray に書かれたまま、**共有空間に発行されていない**。
発行されるのは PjM がタスクの `file` として宣言した出力だけ（合意030 の発行ゲート）で、
検算の記録は宣言されていない。**skill は成果物を要求できるが、成果物の契約はプロセス側にある。**

## 6. この走が確定させたこと

> **自己参照の限界。** 計器の設計者と、検算の対象を選ぶ主体が同じである限り、盲点は保存される。

同型の第2標本は 036 compat-r1（自分で作った golden を疑えず予算切れ）。
断つには**選ぶ主体を離す**しかない——mu には既に**独立 QA**があり、
「作る者と検める者を分ける」は 027 で rnd パッケージに入れた思想でもある。
