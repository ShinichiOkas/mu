## 対照実験 — 知識を抜くと何が起きるか

同じ題材（deadstock）を、役割定義書ありとなしで走らせた。

### 知識なしの PjM は「developer」を1人だけ立てた

```
1. [x] **developer** → analyze_deadstock.ps1
2. [ ] **qa**        → verdict.md     ← コードが補完（床）
```

- **役割が1人に潰れた**。architect も implementer も立てず、`developer` という
  **自分で発明した役割名**が全部を担う。役割名の検証（未知の役割は implementer に寄せる）は
  照合相手の KB が空なので働かない——**知識が無い＝語彙も無い**が可視化された。
- 知識ありの走では architect が先に立ち、`design.md` を残してから実装に入っている。
- **QA タスクだけはコードが補完した**。知識ゼロでも検証は消えない（決定論の床）。

### 成果物の質

| | 知識あり | 知識なし |
|---|---|---|
| 実装 | `process_inventory.py`（Python） | `analyze_deadstock.ps1`（PowerShell。選択の根拠なし） |
| 設計書 | `design.md` あり | 無し |
| 報告書 | `商品コード,商品名,在庫数,純売上数,判定理由` の表 | `Item: 消しゴム, Net Sales: 10` の羅列 |
| 答え | **P006 / P007 / P010**（判定理由つき） | 消しゴム・はさみ・ホッチキス・蛍光ペン（返品90個の P003 を含む） |
| 余計な生成物 | 無し | **架空の入力 `sales_data.csv`（`ItemA,100,20` のトイデータ）を勝手に作った** |
| 判定 | ACHIEVED: yes | **契約違反**（`ACHIEVED: The script correctly implements…` と散文を書き、判定語が無い） |

- 架空入力の生成は 006 で観測した「入力を作り直す」病の再来。ただし**保護対象3ファイルは無傷**
  （`protection violations: none`）——保護の意味論（内容不変だけを守り、新規作成は防がない）どおり。
- QA の契約違反は機械読みで `uncertain` に落ち、**escalate に上がった**。床は効いている。

### 結論

**外に出した知識は効いている。** 知識を抜くと、役割分化・言語選択・設計書・報告形式・
入力の扱い・判定の作法がすべて崩れ、正解にも届かず escalate で終わった。
知識ありとなしで結果が変わったことが、分離が成功していることの実証になる
（[[external-failure-needs-control-group-and-repetition]]）。

## この実走で見つかった**自分の劣化**（対処済み）

知識ありの走でも判定書の書式がドリフトしていた——`## ACHIEVED: yes` / `## REASON` ＋本文
という Markdown 形式になり、**L4 に届く REASON が空**になっていた。原因は Phase2 で
`roles/qa.md` から強い書式指定を削り、コード供給の1ブロックに移して**steering が弱まった**こと。
判定自体は通るが、人間に渡る根拠が消える。

対処（d4b1a13）:

- **読み手を頑健に**: `_verdict_field()` が1行形式でも見出しブロックでも REASON/GAP を読む。
  ただし判定語（yes|no|uncertain）の厳格さは維持——対照走のような散文宣言は uncertain のまま。
- **床を足す**: QA タスクの成功条件に契約の3項目を必ず含める（L2 Reflect が欠落を落とせる）。

**交絡の申告**: 対照走の「QA が契約を守れなかった」という結果には、
知識の欠如だけでなくこの steering 弱化も寄与している可能性がある。
対照実験の結論（知識は効いている）は他の5指標で十分支えられているが、
判定作法の項目だけは切り分けができていない。
