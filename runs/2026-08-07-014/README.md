## 新しく見つかった問題 — 先に作った検査器は「中身」を検査できない

`verifier.ps1` は1回で確定したが、**中身がプレースホルダのままだった**:

```powershell
$toolNames  = @("Tool1", "Tool2", "Tool3", "Tool4")
$viewpoints = @("View1", "View2", "View3", "View4", "View5")
```

検査器を書いた時点で報告書はまだ存在しない。実装者は具体名を確かめられず、
**抽象ラベルで検査器を書いた**（`design.md` にこのラベルは無く、検査器タスクが独自に作った）。

そして次のタスクで報告書を書いた実装者は、**その検査器を通すために報告書側をラベルに合わせた**:

```markdown
- **Conclusion**: Continue using **Ollama (Tool1)**.
| Resource usage (View1) | Ollama (Tool1) | llama.cpp (Tool2) | ...
```

検査器は `PASS` を出す。だが**検査しているのはラベルの存在であって、内容ではない**。
013 とは逆向きの失敗である:

| | 013 | 014 |
|---|---|---|
| 何が起きたか | 検査器を成果物に合わせて**書き換えた** | 成果物を検査器に合わせて**歪めた** |
| 検査の独立性 | 失われた（判定の土台が汚染） | 形式上は保たれたが、**測っている対象がずれた** |

**凍結は「検査器が正しい」ことを保証しない。** 先に凍結するほど、検査器は成果物を知らないまま固まる。

## 実質的な検査を担ったのは PdM の受入基準だった

L4 の最終検査は 5件中 2件 NG:

- 「5つの観点（リソース消費量…）の記述があること」→ 期待文字列「リソース消費量」が無い（報告書は英語 `Resource usage`）
- 「各主張に出典 URL が記載されていること」→ **`http` が出力に現れない**

**報告書の URL は1本だけ**だった（013 は5本すべて実在）。成果物の質は明確に落ちている。
そして落ちていることを捕まえたのは、凍結された検査器ではなく**PdM の素朴な受入基準**である。

なお「リソース消費量」の NG は 013 で観測した**マーカーの言語依存**（③）がそのまま再発している。
ロール定義に「文書のマーカーは言語非依存の量で」と書いたが、PdM は今回も日本語マーカーを置いた。

## 回帰確認 — コーディング走行が収束しなくなった（要対処）

`probe_hard deadstock` を同条件で走らせたところ、**15分の上限で打ち切り**（`EXIT=124`）。
013 の同じ確認では **326秒・1周で完遂**していたので、明確な悪化である。

- 成果物自体は**正しかった**（`dead_stock_report.txt` に P007 ホッチキス・P010 蛍光ペン。罠の p008 も回避）
- 止まっていたのは検証側。PjM は VERIFIER FIRST に従って `verify_logic.ps1` を先に作らせ、
  以後 `UNIT CHECK NG` を6回繰り返して収束しなかった

原因は **013 と 014 の変更の組み合わせ**と見られる:

1. **VERIFIER FIRST がコーディング走行でも発火する** — 成果物が `.txt` レポートなので
   「コード以外の成果物」に当たる。013 の回帰確認でも発火していたが、そのときは収束した
2. **検査器が凍結された（014 B）** — 013 では検査器が巻き添え無効化で再生成され、
   食い違いが（悪い形だが）自然に解消していた。その経路が閉じたので、
   **検査器の側が間違っているときに逃げ場が無くなった**

つまり B の修正は「検査器を守る」と同時に「**間違った検査器も守ってしまう**」。
研究走行で見つかった「先に作った検査器は中身を検査できない」と同じ根であり、
症状が**収束不能**という形で出た。

> 013 で「壊れていない・むしろ改善」と報告したが、それは1走の観察だった。
> 014 の変更を加えた状態では成り立たない。

## 結論 — ③（凍結機構）は不要。別のものが要る

合意014 の判断事項「検査器の凍結機構（`tools.protect()` の自動適用）は要るか」への答え:

**要らない。** 検査器の書き換えは 29回 → 1回になり、原因はプロンプト無視ではなく
**コードの依存伝播だった**。B の修正で消えた以上、保護機構は要らない機構である。
013 の時点で 3 を実装していたら、**効かない場所に機構を足していた**ことになる。

代わりに次が要る:

| 優先 | 課題 | 形 |
|---|---|---|
| **最高** | **検査器が間違っているときの逃げ場が無い**（回帰の原因） | 検査器の食い違いを「検査器の欠陥」として**上へ申告できる経路**を作る（PjM が `replan` で検査器タスクごと作り直す、等）。黙って書き換えるのでも、無限に成果物を直すのでもない第三の道 |
| 高 | **検査器が成果物を知らないまま固まる** | 検査器は「仕様の具体語（4ツール名・5観点名・URL の存在）」を検査するよう仕様側から縛る。SPEC の定義語を検査器タスクの criterion に流し込む |
| 高 | **VERIFIER FIRST の発火条件が広すぎる** | `.txt` レポートを作るコーディング課題でも発火している。「検証手段が既製でない」の判定をもっと絞る |
| 高 | **QA の作業場** | `write_scope` に scratch を足す（データで宣言・コードが適用） |
| 中 | **マーカーの言語依存** | `expect` を ASCII に強制する、または成果物の言語を仕様で固定する |
