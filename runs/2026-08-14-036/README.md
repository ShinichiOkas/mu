## 3. 各題材が掘り当てたもの

### maintain — 破壊は起きない。詰まるなら**手数**で詰まる

r1 は実装者が壊れた出力を出した（PjM の言葉: 「ファイルには元の docstring と末尾の 'i' しかない」）。
**PjM はそれを検知して rerun を選び、予算が尽きて escalate した**——黙って完遂と言わなかった。
壊れた成果物は発行されず、**原本は 9,169バイトのまま残った**。床は効いている。

r2 は同じ課題を **91秒で 16/16 完全達成**。同じ条件で 636s→escalate と 91s→完全達成が並ぶ
（**7倍のばらつき**）。035 の教訓（n=1 の観測に原因を帰属させない）がそのまま効く。

### compat — 後方互換は守れた。壊れたのは**自分で作った基準**のほう

両走とも、呼び出し元3本の出力は**1バイトも変わっていない**（元実装と突き合わせて一致）。
署名も維持された。後方互換という制約そのものは守られている。

r1 が escalate した理由が興味深い。mu は自分で「修正前の出力」を golden として保存する
回帰試験を編んだが、**その golden を、既に区切りを入れた実装で作ってしまった**。
以後「既定の出力が golden と違う」と自分を責め続け、予算が尽きた:

> the gold baselines expect thousands separators (e.g., "1,200") whereas the current
> default behavior of `render` (thousands=False) produces them without separators

**基準を後から作ると、汚染された基準を正だと信じる。** 035 で私自身が
「pristine から golden を毎回その場で作る」設計にしたのと同じ問題を、mu は解けなかった。

### repro — **見せていないデータだけが偽・完遂を暴いた**

両走とも、与えたデータでの症状（顧客 7 と 12 の合計が 0）は正しく直った。原因（0埋め id）も
突き止め、`repro.md` に書いた。QA も全項目 PASS を出した。**しかし2走とも壊れている:**

- **r1: 絶対パスを埋め込んだ。**
  ```python
  CUSTOMERS = "S:/tmp/mu-036/repro-r1/customers.csv"
  ```
  そのディレクトリでしか動かないプログラムになった。
- **r2: 列名を `total` → `total_amount` に改名した。** バグ修正の依頼で出力契約を変えた
  （修理は正しく一般化していた——隠しデータでも 21→300・22→125・25→0 と正解）。

**そして計器の設計がここで効いた。** r1 は「元データで再実行しても正しい」を**通してしまった**
——絶対パスのせいで、どこで走らせても元のファイルを読むからである。
**同じデータで再実行する検査は、絶対パスの埋め込みを構造的に検出できない。**
捕まえたのは「見せていないデータ」の1段だけだった。

## 4. 計器の欠陥（自己申告）

`compat` の隠し検査に **私が仕様に書いていない期待**が1件混ざっていた——`min_width=None` を
明示的に渡せること。両走とも既定を `min_width=0` と設計しており、これは私の課題文
（「min_width=N は…」）に反していない。**この1件は mu の失敗ではない。**
よって compat の実力は **12/13 ではなく 12/12 相当**である。

課題文を `render(rows, title, min_width=None, thousands=False)` と署名まで明示する形に直した
（v2）。**r1/r2 は v1 の文面で走ったもの**であり、以後の走と比較するときはここを揃えて読む。
