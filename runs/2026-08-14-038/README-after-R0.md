# mu

> 与えられたゴールに向かって PDCA を回し、人間の逐次介入なしに自立実行する **汎用エージェント**。
> それを **きわめてミニマルな仕組み** で実装する。

*この文書は mu のコンセプトと仕様を言語化したもの。L0〜L5 まで実装・検証済み（現在 v0）。*

## mu は材料である

**mu そのものは完成品のエージェントではなく、材料である。** `mu/*`（L0〜L5）を使って
**各種エージェントを作ること**が目的であり, mu 自身が特定用途のエージェントになることではない。

この位置づけから、2つのことが従う。

- **依存の最小化がかかるのは「コア」だけ。** `mu/l0.py` 〜 `mu/l5.py` の外部依存が最小であればよい。
  **ツールが外部に依存するのは自明**である——ツールは外の世界に触れるための部品であり、
  用途ごとに差し替わる。`tools.py` は mu を使って作った**一例**であって、コアの一部ではない。
- **汎用性は用途を変えて確かめる。** ここまでの実装と検証は、事実上**コーディングエージェント**として
  積み上げてきた（設計書・実装・テスト・QA）。だが mu は汎用エージェントを名乗る以上、
  **コーディング以外のタスクがこなせるか**を確かめる必要がある。web 検索・取得ツール（合意011）は、
  そのために足した——ディープリサーチのようなタスクを走らせて、同じ層構造が通用するかを見る。

## 三原則

- **シンプル** — 分かりやすい
- **ミニマル** — 最小
- **本質的** — 核だけ

「ミニマル」で最小化する対象を、4つ明示する:

1. **機構の薄さ** — 足場を極薄に。知能は LLM に委ねる
2. **概念の少なさ** — 登場する要素・語彙を絞る
3. **依存とコード量** — **コア（`mu/l0`〜`l5`）の**依存は最小（公式 `ollama` クライアントと、その基盤 `httpx` のみ）・短いコード。ツールの外部依存はこの制約の外（上記「mu は材料である」）
4. **状態・記憶の少なさ** — 内部状態を最小に

## 中核となる考え方 — 自律性の層 (Layers of Autonomy)

mu は入れ子のループでできている。層を貫く軸は **自律性**。

- **内側ほど非自律** — ただ機械的に動く
- **外へ行くほど自律的** — 自分で判断する

作り方も同じ向きに進む。**一番内側の非自律な核を固め、自律性を一枚ずつ外へ重ねていく。**
全体を上から設計しない。内側から育てる。

| 層 | 名前 | 自律性 | 何を回すか |
|---|---|:---:|---|
| **L0** | Ollama インタフェース | ゼロ | Ollama Interface Layer. Stabilizes connectivity and model availability. |
| **L1** | ツールコールのループ | 低 | Tool Call Loop. Executes tools selected by the model (Do). |
| **L2** | Reflect ループ（エージェント） | 中 | PDCA / Reflect Loop (Agent). Wraps L1 with Reflect (Check + Act). |
| **L3** | 大域 Plan（オーケストレータ） | 高 | Global Plan / Orchestrator. Combines L2 units to complete complex goals. |
| **L4** | 進行の層（PjM） | より高 | Progress Layer (PjM). Manages process, roles, and task execution. |
| **L5** | 目的の層（PdM） | さらに高 | Purpose Layer (PdM). Translates purpose to specifications. |
| L6〜 | *（これから）* | さらに高 | L5 の判断スロットに立つ層。同じ再帰同一構造。最上位の停止は人間 |

> 「自律性の層」とは別に、層の**外側**に **設定系**（初期化などに使う）がある（後述）。

**構造規約 — 1 層 = 1 ファイル。** `mu/l0.py` ・ `mu/l1.py` ・ `mu/l2.py` … と、層番号がそのままファイル名になる。1 ファイルに収まらなくなったら「層が厚すぎ」のシグナルで、分割より先に責務を見直す。

層の外には2種類のものが置かれる。どちらも「層が薄いままでいる」ために外にある。

- **データ**（`roles/*.md` ・ `skills/*.md`）— 役割定義・skill・プロンプトなど、**用途によって変動する値**。人間が直接編集できる。データを外に出すのは「分割」ではない。ただし出すのは変動する値だけで、システムが稼働するための**普遍の値（契約・床）はコアに残す**。
- **facility**（`mu/role_kb.py` ・ `mu/skill_kb.py` ・ `mu/process.py` ・ `mu/workspace.py`）— 層ではない共通機能。役割定義の読み込みと権限適用、skill の読み込みと装着、プロセス（タスク列）の状態管理と artifact、作業空間（tray）の隔離と発行。**データの"形"だけが契約で、"出所"は差し替え可能**（いまはファイル、将来 DB でも層は無変更）。

## 層と役割 — 全体像

### 層: それぞれが埋めている「落差」

層は機能の分類ではない。**それぞれが1つの落差を埋めるために在る。**

| 層 | 埋める落差（＝存在意義） | 役割（何をするか） | 主な生成物 |
|---|---|---|---|
| **L0** | 実行環境は不安定 ↔ 上位は「呼べば返る」と仮定したい | 接続・モデル可用性を理想化する（リトライ・自動 pull・4型エラー） | 応答 |
| **L1** | モデルは考えるだけ ↔ 仕事は世界に触れないと終わらない | モデルが選んだツールを実行し、結果を戻して再び問う（＝**Do**） | ツール実行の事実（facts） |
| **L2** | 1回行動した ↔ ゴールに達したかは別問題 | Reflect（Check+Act）で合否を判定し、達成まで繰り返す（**PDCA**） | 単位の成果物ファイル |
| **L3** | checkable な単位 ↔ 人が頼むのは複雑なゴール | 大域 Plan で単位に分解し、各単位を L2 に完遂させる | 複数ファイルの成果物 |
| **L4** | 仕様は決まった ↔ **誰がどの順で何を作るかは別問題** | プロセス（役割つきタスク列）を編み、人選し、役割を着せた L3 に1つずつ回して検証を集める | PROCESS.md / 成果物 / verdict.md |
| **L5** | 詳細な仕様 ↔ **人が自然に言えるのは目的だけ** | 目的を検査可能な仕様に翻訳し、L4 を回し、結果を見て仕様を直すか人間に上げるかを決める | SPEC.md |
| L6〜 | *（これから）* | L5 の判断スロットに立つ層 | — |

**再帰同一構造**: どの層も「内側の層を **D（実行）** として使い、その外側に判断を足す」形をしている。だから層は積み増せる。停止と責任の底は常に人間。

### 役割（role）: 誰が何を担うか

役割は**コード構造ではなくタスクの属性**である（役割ごとのクラスは無い）。定義書は `roles/<パッケージ>/*.md` にあり、**人間が直接編集できる**。すべての役割が同じ形で外にあり、コードの中に役割ごとの分岐やプロンプトは無い。

- **位置はコアが知り、中身は定義書が決める。** 「そこに PdM が居る」ことは不変、「どういう PdM か」は用途で変わる。
- **役割集合は開いている（合意024）。** コードが名前で依存するのは4ポジション——pdm・pjm（L4/L5 そのもの）、qa（末尾必須の独立検証）、implementer（未知役割名のフォールバック先）——だけで、それ以外は純粋なデータ。**対応するドメインが増えるごとに役割を足していく**（小説なら編集者・執筆者・挿絵師が登場する）。現行5役割は「成果物＝ファイル・検査＝コマンド」に接地した仕事の**実証済み第1世代**であり、抽象役割へ書き直さない——定義書の文面は一般論ではなく実走の失敗観測から書かれた対策集で、抽象化すると効き目ごと薄まる。新ドメインの役割も同じ道筋（実走の失敗観測）で書く。
- **バインディングは1点（合意025）: 呼び出し側が渡した役割の集合＝人選の範囲そのもの。** 「この範囲で選んでほしい」はロードするセットで表現する——`load_roles("roles/coding", "roles-extra")` のように**セットを合成**でき、同名衝突は両出所を名指しするエラー（静かな上書きはしない）。PjM に見せる人選一覧と CLI が人間に見せる一覧は**同じ関数**（`staffing_lines`。人選できないポジションは載せない）から出る——構成と表示の一致を構造で保証する。4ポジションの定義書不足は `missing_positions` が可視化する（エラーにしない——定義書の無い役割は「知識が無い状態」で正直に動く）。
- **役割は目的別パッケージに束ねる（合意026）。** 1パッケージ＝1ディレクトリ（`roles/coding/`・`roles/research/`…）で、各パッケージは**自己完結**——4ポジション＋ドメイン役割の全部を自分で持つ（重複は許容。ドメイン間の干渉ゼロを優先し、あるドメインの失敗対策が別ドメインの文面を歪めない）。素性は同居する `manifest.json`（name / description / status: **verified**＝実走群で検証済み・**draft**＝調整中・**planned**＝枠だけ）が名乗り、`list_packages` が列挙する。**どのパッケージで動くかは呼び出し側が選ぶ**（環境変数 `MU_ROLES_DIR`。カンマ区切りで合成可）——起動表示に名前と検証状態が出るので, verified 以外で走っていることが人間に見える。現在: coding（verified）・research / rnd / secretary / book（draft——実走ループで役割文を調整済み、昇格は検証の蓄積後）。
- **パッケージ選択は L5 に委ねられる（合意028）。** `MU_ROLES_DIR=auto` で Director がカタログ（`list_packages`。planned は除く）から目的に適合するパッケージを**構造化出力の1判断**で自選する。やり方はカタログ級定義書 `roles/director.md`（どのパッケージにも属さない判断なのでカタログと同じ場所に住む。人選対象外——4ポジション契約は不変）、選択の材料は manifest の description（データ）。床: 適合なしの申告・カタログに無い名前・役割文ゼロの選択は、**黙って別パッケージを当てず escalate**。結果契約の `package` 欄で選択の正しさを機械検査できる。roles 明示（手動）が常に優先。
- 定義書が無ければ、**役割は認識しているが知識が無い状態**で動く（多くの場合そのプロジェクトは失敗する——それが正しい挙動であり、静かに埋めない）。
- 定義書の frontmatter は**権限の宣言**でもあり、適用するのはコード。LLM が出せるのは役割名だけなので、**権限を LLM 側から書き換えられない**。

下表は **coding パッケージ**（実証済み第1世代・verified）。他パッケージのドメイン役割（いずれも目的→工程分解→継ぎ目の設計で導出し、実走の失敗観測で調整）: research は **researcher**（主張ごとの出典・一次ソースの実読）、secretary は **secretary**（依頼把握→照会→調整→実行→報告を一気通貫）、rnd は **scientist / experimenter**（実施者が設計を曲げない継ぎ目。計測の「再現」は記録生データとの一致＋結論の再現）、book は **writer / editor**（editor は指摘のみ・本文を書き直せない権限。改稿は同一原稿の連続的修正）。

| role | 居場所 | 意味（職掌） | 見るもの | 生むもの | 権限 |
|---|---|---|---|---|---|
| **pdm** | **L5** そのもの | 目的 → 仕様。**まず充足可能性を申告**し、満たせない目的の仕様は作らない | 目的の原文＋**入力の実物** | `SPEC.md`（操作的定義・受入基準・仕様） | — |
| **pjm** | **L4** そのもの | どう進めるか。プロセスを編み、**人選**し、失敗を受けて**部分再実行**を判断する | SPEC＋役割 KB＋モデルプール | `PROCESS.md`（体制表） | — |
| **architect** | プロセス内のタスク | 構造・品質特性・**設計規則**を定める | SPEC | `design.md` | 制限なし |
| **implementer** | プロセス内のタスク | 実装・テスト・品質ゲートの実行 | SPEC・design.md | 成果物 | 制限なし |
| **qa** | プロセス内のタスク | 独立検証。**仕様への忠実さと目的の達成は別物**として検査する | SPEC・成果物の実物・**目的の原文** | `verdict.md` | 自分の判定書のみ書ける（`edit_file` は持たない） |

**人間はモデルプールの外**にいる。PjM が管理する人員ではなく、`escalate` で判断を依頼する相手——再帰の底である。

### skill（技能）: やり方を独立の単位に分離する

役割定義書は性質の違う2つを混ぜて運んでいた——**ポジションの不変**（職掌・継ぎ目・権限）と、**やり方の対策文**（入力ファイルは読み取り専用／検査器を自分の成果物に合わせない）。後者はドメインを跨いで効くので、パッケージが増えるほど手動コピーが膨らむ（029 起草時の実測: `implementer.md` は5パッケージでバイト同一だった）。後者を独立の単位に分離したものが **skill**（`skills/*.md`）である（合意029）。

**skill は層ではない。** 層は「1つの落差を埋め、内側を D として使い、その外側に判断を足す」ものだが, skill が足すのは判断ではなく**知識**である。だから居場所は role と同じ——層の外のデータ＋ facility（`mu/skill_kb.py`）で、装着点は L4 がタスクの system を組む1行（と、ポジション向けの生命線）。

| | role | skill |
|---|---|---|
| 何 | ポジション（誰が） | やり方（どう） |
| 濃度 | 1 task = **ちょうど1** | 1 task = **0..N** |
| 権限 | **持つ**（tools / write_scope、コードが適用） | **絶対に持たない** |
| コードの知識 | 4ポジションは名前で知る（契約） | 名前を1つも知らない（純データ） |
| 宛先 | PjM の人選が決める | **skill の側が名乗る**（`applies_to`） |

- **宛先は skill が名乗る（一方向）。** 役割定義書は skill を知らない。`roles/<pkg>/*.md` はリポジトリの共有資産で個々のプロジェクトが書き換える対象ではなく、かつパッケージが自動選択される（合意028）以上、プロジェクト作者は実行時の役割名を確定できない——確実に名指しできるのは**名前が動かない4ポジション**だけである。`applies_to: all`（省略も同義）で全役割に効く。ドメイン役割名も書けるが、当たらなければ**エラーにせず可視化**する（起動表示で名指し）。
- **skill は権限を持たない（絶対ルール）。** `tools:` / `write_scope:` が書いてあればコードが**名指しでエラーにして落とす**（静かに無視すると、書いた人には効いているように見える）。「LLM が出せるのは役割名だけなので権限を LLM 側から書き換えられない」（合意007 B1）の床は, skill を導入しても不変。
- **`maturity: confirmed` だけが装着される。** 育成中（`draft`）の文は走りに載らない。将来「実走の観測から skill を書き足す」経路を足すときは、**系が書けるのは draft まで・確定は人間**（合意026「verified への昇格は師匠の承認事項」と同型の非対称）。未知の frontmatter キーは文字列のまま持ち回るので、素性（出所・根拠の実走）は契約を変えずに後から載せられる。
- **出所は呼び出し側が規定する**（`MU_SKILLS_DIR`。カンマ区切りで合成可）。既定は同梱の `skills/`。プロジェクト固有のやり方を足すときは `MU_SKILLS_DIR=skills,./.mu/skills` のように共有側も明示する（roles と同じ意味論——指定は置換であって追加ではない）。
- 装備の逆引き（宛先 → skill）は起動時に表示され、**PjM に見せる一覧と人間に見せる一覧は同じ関数**から出る（合意025 の型）。装着量（skill 名と総文字数）は合成点でログに出る——小型モデルでは装着量がそのまま劣化要因になるため。

## L0 — Ollama インタフェース層（最下層 / 自律性ゼロ）

**基本 LLM は Ollama。** 責務はただ一つ:

> 上位の層に対して「**常に安定して応答が返る、理想化された LLM**」を見せる。

**含むもの:**

1. **推論の呼び出し** — `/api/generate` ・ `/api/chat`（tool calling 対応）
2. **モデル可用性の保証（理想化）** — 使うモデルが無ければ L0 が黙って `/api/pull` し、上位には常に居るように見せる（存在・能力確認に `/api/tags` ・ `/api/show`）
3. **接続の安定化** — 接続確立・リトライ／バックオフ・タイムアウト・エラー回復

**含まないもの:** 埋め込み（`/api/embed` `/api/embeddings`）／ 監視（`/api/ps` `/api/version`）／ blob（`/api/blobs`）／ OpenAI 互換（`/v1/*`）／ モデル管理系（→ **設定系** へ）

L0 は判断しない。ただ確実に応答を返す。

### エラーの扱い — 接続は理想化する、中身は関知しない

> **L0 は「接続」を理想化する。「中身」は理想化しない。**

- 「応答を**得られたか**」に関わる失敗 → L0 が吸収する（リトライ等）。どうしても無理なら **型付きの基盤エラー** として通知
- 「応答の**中身**」の問題（拒否・JSON崩れ・`tool_calls` 不正・空返答）→ **L0 は関知しない**。そのまま応答として上位へ渡す（判断は L1 以降）

**吸収する失敗（リトライ対象）:** 接続不可 ／ タイムアウト ／ ストリーム途中切断 ／ 一時的サーバエラー(5xx) ／ モデル未取得（→ 自動 `pull` して再試行）／ 資源不足（限定的に）

**上位へ見せるエラーは 4 つの型だけ**（Ollama の生エラーは隠す）:

| 型 | 意味 |
|---|---|
| `Unreachable` | 到達不能（リトライ尽き）。今 LLM が使えない |
| `ModelUnavailable` | モデルを用意できない（`pull` 失敗・存在しない） |
| `ResourceExhausted` | 資源不足（限定リトライ後も回復せず） |
| `BadRequest` | 呼び出し側の不正（リトライしない・即通知） |

これ以外はすべて「成功応答」として返る。

**リトライ**: 指数バックオフ＋ジッタ／試行回数・遅延に上限。生成は副作用が無いので再試行して安全（部分出力は破棄して全体を再試行）。具体の回数・秒は実装フェーズで調整。

## L1 — ツールコールのループ（行動する層）

L0 の一発の `/api/chat` を、行動ループに育てる層。

**ツールは Ollama ではなく mu が定義・実行する。** モデルがやるのは「このツールをこの引数で呼びたい」という意図（`tool_calls`）を構造化して返すことだけ。実行しない。

```
① mu が tools（関数の説明書）を渡して /api/chat
② モデルが tool_calls（呼びたい意図）を返す   ← ここで一旦止まる
③ mu が実際にツールを実行し、結果を role:"tool" で戻す
④ その履歴で再び /api/chat → 足りなければ ② へ、済めば終了
```

ここで mu は初めて外界に働きかける（**Do**）。ただし「ゴールに向かって進んでいるか」の判断（**Check / Act = PDCA**）はまだ持たない。それは外側の **L2**。

---

## L2 — Reflect ループ（PDCA / エージェント）

L1 の上に「与えられたゴールに向かって自立実行する」層を重ねる。PDCA のうち **D は L1**。L2 が足すのは **Reflect（Check ＋ Act）** ただ一つ:

```
loop（呼び出し側が規定する上限まで）:
  D       : L1 を回す（ゴールに向かって行動）
  Reflect : 「ゴールは達成されたか？ 未達なら何が足りないか」を構造化出力で1回問う
  判定    : 合格 → 終了 ／ 未達 → next を投入して継続（＝そこで計画が生まれる）
```

- **再帰同一構造**: この「内側ループ→Reflect→続行/停止」は、L3 が L2 を管理するときも同じ形。再帰の底（最上位の停止）は人間。
- **無状態**: 状態は messages（上位が持つ）。上限（`max_rounds` / `l1_max`）は自層にハードコードせず、呼び出し側が規定する。
- Reflect は L0 の **構造化出力** で合否を確実に取り、判定は **ゴールに明記された制約だけ** を見る。ゆえにゴールは **checkable な成功条件** で与える（曖昧だと収束しない）。

---

## L3 — 大域的 Plan（オーケストレータ / PDCA 完全体）

L2（単一 checkable タスクの完遂）を"単位"として組み合わせ、複雑なゴールを最後まで完遂する層。L2 で暗黙だった **大域的 Plan が明示・必須**になり、PDCA が完全体で現れる:

| | 中身 | 自律/HITL |
|---|---|---|
| **P** | 複雑ゴールを「ファイルを生む checkable な単位」へ分解 | **HITL**（承認スロット） |
| **D** | 各単位を **L2** が完遂 → 成果物ファイル | 自律 |
| **C** | 成果物を確認／L2 の失敗を検知・分析 | 自律 |
| **A** | 再計画（条件/アプローチ/計画の変更） | **HITL**（承認スロット） |

- **ファイル・グラウンディング（L3 の背骨）**: すべての単位は `(task, 出力ファイル, checkable 基準)`。ファイル＋基準が単位を checkable にし（L2 が達成＆検証できる）、ファイルが次の単位への文脈になる（単位間はファイルを介してつながる）。
- **コードの単位**は基準＝テストパス。テストは先行する別単位として作られる → **L3 が TDD をオーケストレーションする**。
- **判断は外へ、実行は内で**: D・C は自律、P・A（判断）は承認スロット `approve` に上がる。承認者は呼び出し側が差し込む（人間＝`l3_chat`／L4 から呼ぶときは自律承認で、判断は L4 側の PjM が持つ）。再帰の底は人間。
- 上限（`max_rounds` / `l2_max` / `l2_l1_max`）は呼び出し側が規定（L2 と同じ思想）。1周＝1単位実行 or 1回の全体判定なので、`max_rounds` は暗黙に「単位数＋再計画＋全体判定」の予算になる（返り値の `rounds` で上限到達を判別できる）。

**北極星到達済み** — 「GUI を持つアプリ（auto-checkable でない受け入れ境界を含む複合タスク）を自走で最後まで完成」を実機で達成（2026-07-19、GUI 付き AI チャットアプリ）。

## L4 — 進行の層（PjM / Manager）

仕様が決まっても「**誰がどの順で何を作るか**」は別問題である。その落差を埋めるのが L4。
SPEC（何を作るか）を受け取り、**役割注釈付きプロセス**を編み、役割を着せた L3 に1タスクずつ完遂させ、
検証を集める。マルチエージェントを新しいフレームワークとして足すのではなく、
**「役割を着せた L3 のループ」**に還元してある——並列化はそのループの最適化にすぎず、
実際にそう実装された（依存グラフの明示化と作業空間の分離＝合意030、スケジューラ＝合意031。下記）。

| | 中身 | 誰が |
|---|---|---|
| **P** | SPEC → プロセス（役割・出力ファイル・成功条件・**人選**を持つタスク列）＝ `PROCESS.md` | PjM（LLM） |
| **D** | 1タスクずつ、**役割定義＋その役割に宛てた skill** を前置し、**役割の権限で絞ったツール**で L3 に完遂させる | 内側の層 |
| **C** | 受入基準の決定論 check ＋ 末尾の QA タスクが書く `verdict.md` の機械読み | コード |
| **A** | **rerun**（部分再実行）/ **replan**（プロセスを組み直す）は自分で回す | PjM（LLM） |

- **自分の職掌で直せないものは上へ返す**。`respec`（仕様が悪い）と `escalate`（人手が要る／予算切れ）は
  この層では処理せず、**outcome として L5 に申告する**——判断は外へ、実行は内で。
- **役割はコード構造ではなくタスクの属性**。`task = {role, task, file, criterion, needs, check?, model?}`
  ——役割ごとのクラスは無い。**入力も出力も宣言される**（合意030。師匠「Input が暗黙というのは
  よろしくない」）: `file` が出力、`needs` が入力（先行タスクの出力＋外部の実在ファイル）。
  needs の意味論は**ゲート**——満たせなければタスクは実行できない（満たせないタスクは
  正直に失敗して PjM の decide に乗る）。言及ベースの依存推定は**計画時 lint** に降格
  （依存グラフの真実の出所は needs の1つ。QA の needs＝全成果物はコードが必ず供給する床）。
- **作業空間の分離（合意030）**: 呼び出し側が `workspace` を渡すと、各タスクは自分の
  **tray**（`<work>/<role>/task-N/`）で走る——needs＋SPEC を**写して**開始（スナップショット）、
  成果物をそこに書き出す。タスク終了時に PjM が結果を確認し、成功すれば次のタスクへ
  成果物を供給（写し）する。この分離により、L3 が「どのファイルがあるか」という
  環境依存から解放され、純粋にタスクのみに集中できる。
- **PjM の意思決定**: 各タスクの終了後、`decide` 局面で「成功か、部分再実行（rerun）か、
  計画変更（replan）か、仕様不備（respec）か、人間への救援要請（escalate）か」を判定する。
  この判断は L4 の PjM が担う。

## L5 — 目的の層（PdM / Director）

人間が自然に語る「目的」と、L4 が必要とする「仕様（SPEC）」の落差を埋める層。

**責務は、目的から「検査可能な仕様」を導き出すこと。**

1. **充足可能性の判断**: 目的を受け取り、「現在の能力・制約で達成可能か」をまず判断する。
   不可能な場合は、代替案を提示するか、人間にエスカレートする。
2. **SPEC の策定**: 目的を、L4 がプロセスに変換できるレベルの「操作的定義・受入基準・仕様」に翻訳し、`SPEC.md` を生成する。
3. **L4 の監督**: L4 を回し、結果（outcome）を確認する。
4. **Accept / Respec / Escalate**:
   - **Accept**: 成果物が SPEC を満たし、目的が充足されたと判断すれば完了。
   - **Respec**: 成果物が SPEC は満たしたが、目的への到達が不十分な場合（または仕様自体に欠陥があった場合）、SPEC を修正して L4 を再実行する。
   - **Escalate**: 予算切れや、モデルの能力限界で解決できない問題に直面した場合、人間へ判断を仰ぐ。

L5 は「目的」という最も抽象的な入力と、「完了」という最終的な判定を繋ぐ、
mu の最外殻の自律ループである。

## 設定系 (Facilities)

層の外側にある共通機能。層が「薄い」ままであるために、共通の仕組みとして切り出されている。

- **役割 KB (`mu/role_kb.py`)**: `roles/` ディレクトリから役割定義（`.md`）を読み込み、
  プロンプトへの注入や、`write_scope` などの権限管理を行う。
- **Skill KB (`mu/skill_kb.py`)**: `skills/` ディレクトリから技能定義（`.md`）を読み込み、
  役割に応じた skill を装着する。
- **プロセス管理 (`mu/process.py`)**: `PROCESS.md` の状態管理、タスクの実行順序制御、
  および成果物（artifact）の追跡を行う。
- **ワークスペース (`mu/workspace.py`)**: 各タスクに独立した作業領域（tray）を
  発行し、ファイルの隔離と供給を管理する。
