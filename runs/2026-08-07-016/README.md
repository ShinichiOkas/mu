## 何が効いたか

### 防ぐ層（OS の read-only）

`protect()` が登録時に `os.chmod(S_IREAD)` をかけるようにした。実測（合意016）のとおり、
Python の `open(w)` / `unlink`、PowerShell の `Set-Content` / `Out-File` をすべて拒否する。
015 の破壊経路（実装者が `test_inventory.py` を書いて `python` で実行）はここで止まる。

**合意007 の判断を覆していない。** 007 は「任意のコマンド文字列を解析して塞ぐのは
実行者の正当な能力を削る」としたが、OS 属性なら**解析を通らずに防げる**。
007 の時点で見えていなかった選択肢を足しただけである（師匠「方針転換ではなく二層構造」）。

### 検出層（既存）＋ 周ごとの検査（新規）

意図的な回避（`attrib -R` / `Remove-Item -Force`）は実測で**通る**。だから検出層を残す。
加えて 015 で判明した「**走り切らないと検出報告が出ない**」を直し、
`Manager.run(guard=...)` が**各周の頭で**破れを見て、壊れていれば即 escalate するようにした。
壊れた入力の上での作業はすべて偽の前提に乗る（015 では「Widget B」の報告書ができた）。

### 収束不能まで解消したのは想定外

014 / 015 で 15分打ち切りだった `deadstock` が 1周・473秒で完遂した。
015 の記録では「014 の原因（VERIFIER FIRST）は除去済み、別の理由で止まっている」としていたが、
**その『別の理由』が入力破壊だった**可能性が高い——入力が壊れた後、実装者と QA が
食い違う数字を見て延々と噛み合わなかった、という筋が通る。

ただしこれは1走の観察であり、確率的ブレの可能性を排除できない。

## 残る穴（設計として承知の上）

- `attrib -R` / `Remove-Item -Force` による**意図的な回避は防げない**。検出に委ねる
- **プロセスを強制終了されると `finally` が走らない**ため、読み取り専用が残る。
  次の走行の入力配置が失敗しないよう、`probe_hard` の入力配置側で属性を解いてから書くようにした
