## 3. しかしそれは**偽の no-op** だった

私の監査は同じ状態に対して **嘘1件**（skill の件数と宛先）を検出している。
README は「現在10件——`applies_to: implementer` が9件・`pjm` が1件」と述べているが、
ドリフトで skill は **11件**（`qa` 宛てが1件増えた）になっている。**README は嘘を言ったまま、
mu は「満たされている」と宣言して止まった。**

原因は検査器にある。glm が書いた `verify_readme.py` は **450行**あり、
`file_count_patterns` / `role_count_patterns` で数の主張まで照合する精巧なものだが——

```
$ grep -c "skill" verify_readme.py
0
```

**skill という語が1度も出てこない。** 見ていないものは、当然0件になる。

### さらに深い原因 — 範囲の限定が別の軸に漏れた

責務文の**網羅**の要求は「実装を構成する**ファイル・役割・それらの数**について」と
範囲を限定してある（038 で「停止条件を到達可能にする」ために入れた限定）。
一方、**一致**の要求は「実装と食い違う記述は、1件でも直せ」で**無限定**である。

検査器は前者の列挙に引きずられ、**嘘の検出範囲まで「ファイルと役割」に狭めた**。
skill は .py の実装ファイルでも役割でもないので、検出網から落ちた。

> **範囲を限定する語は、意図した軸（網羅）を超えて、別の軸（一致）にも漏れる。**

これは 034 で挙げた懸念——「no-op は**静かな失敗**を生む」——の実証でもある。
同時に、034 で入れた床（根拠を必ず SPEC.md に残す）が効いた: **偽の停止を後から読めた**。
根拠が無ければ「5秒で正常終了」は成功にしか見えなかった。

## 4. モデル差 — **向きが変わっただけで、正しさは来なかった**

| | gemma4:31b（040） | **glm-5.2（042）** |
|---|---|---|
| 保存の最低値 | **24%**（3,876字に崩壊） | **92%**（一度も崩れない） |
| 字数の系列 | 22,674 → 3,876 → 4,272 → 4,272 | 23,162 → 22,518 → 23,052 → 23,052 |
| `no_action` | 4周とも出ず | **R3 で発火（5秒）** |
| 検査器 | 90行・**過剰報告**（実在ファイルを嘘と誤判定・11件） | 450行・**過少報告**（skill を見ない・0件） |
| ドリフトの修正 | 嘘 1→0（**直した**） | 嘘 1 が最後まで**残存** |
| 1周の所要 | 520〜1345s | 940〜2741s |

> **検査器が過剰なら、壊しながら直す。過少なら、保ちながら見逃す。**
> **モデルを上げると失敗の向きが変わるが、検査器の正しさは与えられない。**

事前に立てた予測の答え合わせ:

| 予測 | 結果 |
|---|---|
| 検査器の定義域の誤りは「消える可能性が高い」 | **外れ**。消えず、**向きが反転**した |
| 自作の数字を疑わないのは「残るかも」 | **当たり**。0/0 を検算せず停止した |
| 機械検査が散文の規範に勝つのは？ | glm では**規範が勝った**（保存 92〜100%）。ただし検査器が 0 を返したので競合が起きていない——未検証 |

## 5. 残っている問い

1. **検査器の正しさを誰が担保するか。** モデル能力では解けないことが実測できた。
   検算を成果物として要求する（内訳の列挙）か、skill で「計器を疑う」規律を渡すか
2. **責務文の限定の漏れ。** 網羅の範囲を限定すると一致の検出まで狭まる。
   両者を別々に書くか、限定を網羅の文だけに閉じる書き方が要る
3. 保存はモデル差で劇的に改善する（24% → 92%）。**作用の側は能力で解ける**
