## 2. 原因 — `needs` の1宣言。**tray に原本が無ければ、書き手は作り直すしかない**

implementer の作業トレイの中身を両走で比べると、違いはこれだけである:

| 走 | implementer の tray | 結果 |
|---|---|---|
| 034 R0 | `README.md (47,715 bytes)` + SPEC.md + sync_plan.md | 93% 残存 |
| **035 R1** | SPEC.md + sync_plan.md（**原本なし**） | 5.5% |
| **035 R2** | SPEC.md + design.md（**原本なし**） | 2.7% |

合意030 の作業空間は「宣言された入力だけを写す」。**保守すべき当の文書が `needs` に
無ければ、トレイには存在しない。** `read_file` はトレイに閉じているので原本を読めず、
実装者にできることは**新規に書くこと**だけになる。034 の非破壊は機構の効果ではなく、
**PjM がその走でたまたま `README.md` を needs に書いた**結果だった（n=1 の偶然）。

`edit_file` の skill（032 E-2）を装備しても同じである——**差分を当てる対象がトレイに無い。**

> **更新の仕事は「入力＝出力」の形をしている。** needs（入力の宣言）と publish（出力）が
> 別の機構である限り、対象を入力として宣言し忘れた瞬間、保守は**再生成に化ける**。
> これは知識の不足ではなく、**1つの判断に全部が乗っている構造**の問題である。

## 3. 二次発見 — needs ゲートの失敗が、**宣言そのものを捨てさせた**

両周とも、最初のプロセスは needs を宣言していた。ただし名前が違った:

```
[!] needs 未充足: analysis.md に l0.py, l1.py, l2.py, l3.py, l4.py, l5.py … が無い
```

実体は `mu/l0.py` である（クローン直下には無い）。**ゲートは正しく落とした。**
しかし PjM の replan は**宣言を直さず、宣言を捨てた**——再計画後のプロセスは needs を
ほとんど持たず、トレイは SPEC.md だけになった。R2 も同型（`design.md` に l0.py〜l5.py が無い → replan）。

**ゲートは「間違った宣言」を弾くが、「宣言しない」は弾かない。** 罰を避ける最も安い道が
「宣言をやめる」になっている。
