### f1×12b — 観測した失敗そのものの再走（B1 の受入本体）

**QA が成果物を書き換えようとして、権限で止まった**:

```
[L4] [!] 権限で拒否: (qa) write_file -> todo_app.py     （2回）
```

006 で観測した「QA が成果物を自分で修正してから合格判定（自己修正→自己承認）」の経路が、
**プロンプトではなく権限で塞がれた**。拒否後、QA は成果物を直さずに検証を続けている
（steering が効いている）。`ツール非配布: (qa) edit_file` も QA タスクごとに記録。

走行そのものは **escalated（正直な未達）**。決定論の check は最終的に通っていた
（`SELFTEST OK 12`）が、QA タスクが完遂せず verdict が無いため受理しない——
「検証できていないものを完遂にしない」床が効いた形。12b は穴探査構成であり、
前回の f1×12b も完遂していないので退行ではない。

### 新しく見つかった穴（B1 起因ではない・要検討）

12b の PjM が **QA タスクを2つ立てた**（`verdict.md` と `verdict_check.md`）。すると:

- 2つ目の QA が `verdict.md`（本命の判定書）に書こうとして権限で拒否され、
  `verdict_check.md` に書いた——権限の意味論としては正しい（自タスクの出力に閉じる）。
- しかし L4 は `_read_verdict` で**最後の QA タスク**の判定書を読む。本命の判定書が
  2枚に割れ、「どちらが判定か」が曖昧になる。
- さらに PjM は `qa @gemma4:18b`（プールに無いモデル）を指名した（コード側のフォールバックで既定へ）。

いずれも 006 で観測した **PjM の staffing の穴**の再発であり、権限機構が生んだ問題ではない。
→ LONGTERM_TODO に登録。
- QA の verdict に「SPEC は PURPOSE の制約を弱めていない」という判定文が実際に現れた
  （jsonparse・deadstock）。C1-(b) の必須検査項目が動いている証拠。
