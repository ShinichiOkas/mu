# 2026-08-06/07 走行記録 — ロール定義だけで「検査器を先に作って凍結」は成立するか

合意013。012 で観測した「検査器が成果物になる」穴を、**構造を変えずロール定義だけで**塞げるかを測る。
機構（`tools.protect()` の自動適用）は意図的に足していない——**プロンプトでどこまで効くか**を先に測り、
効かない部分だけを機構に落とすため。

- 条件は 012 と同一（題材・目的文・モデル `gemma4:31b-cloud` ＋ QA `qwen3.5:9b`・予算）。
  **差分は `roles/*.md` のみ**。検査器は置かず、空のディレクトリから始めた
- 所要 4,950 秒（82分）／ L1 の思考 1,033 回／ ログ 3,637 行

---

## 結果 — 半分効いた。凍結だけがプロンプトでは守れなかった

| # | 指標 | 012（変更前） | 013（ロール定義変更後） |
|---|---|---|---|
| 1 | 検査器タスクが本タスク**より前**に置かれたか | ✗ 後・同一走行内 | **○ 2番目（本タスクは3番目）** |
| 2 | 検査器が**上書きされなかった**か | ✗ 上書き | **✗ 29回 上書き＋派生15ファイル** |
| 3 | マーカーが**実物の出力と一致**したか | ✗ 発明（`ALL_URLS_VALID`） | △ PjM のタスク検査は一致（`PASS`）。**PdM の受入基準は日本語「結論」のまま**（言語非依存の指示は効かず） |
| 4 | 決定論 check が通ったか | ✗ 3件中2件 NG | **○ 最終 4件すべて ok** |
| 5 | QA の権限拒否 | 33 回 | ✗ **32 回**（ほぼ不変） |
| 6 | 成果物の妥当性 | ○ 出典 2/2 実在 | **○ 出典 5/5 実在**・4ツール比較・結論あり |
| — | 最終判定 | 記録漏れ（probe の不具合） | `achieved=False` / `escalated=True`（**QA が判定書を完成できず**） |

### 効いたこと — PjM は VERIFIER FIRST を実行した

PROCESS.md のタスク列:

```
1. [x] architect    → design.md
2. [x] implementer  → verify_report.ps1      ← 検査器。本タスクより前
3. [x] implementer  → comparison_report.md   検査: verify_report.ps1 → 「PASS」
4. [ ] qa           → verdict.md
```

**ロール定義に書いた規範を PjM がそのまま計画に落とした。**「検査器の実装を独立タスクとして
本タスクより前に置き、実装者に振る」も、「本タスクの検査にその検査器を使う」も守られた。
師匠の見立て（構造でなくロール定義で解く）は、**計画の側については当たった**。

### 効かなかったこと — 凍結はプロンプトでは守れない

検査器 `verify_report.ps1` は **29回書き換えられた**。加えて
`verify_report_final.ps1` / `_fixed` / `_v3` / `_utf8` / `_simple` / `_test` / `verify_debug_2〜5.ps1` など
**15個の派生ファイル**が作られた。「既存の検査器を書き換えない」と明記したのに、
**元ファイルを直接書き換え、さらに複製を量産する**という二重の破り方をしている。

注目すべきは PjM 自身は凍結を守っていたことである。rerun の判断は
`invalidate=['comparison_report.md']` **のみ**——検査器を無効化していない。
**計画層は規範を守り、実行層（実装者）が破った。**

### なぜ破れたか — ③の失敗が②を誘発した

因果はこうである:

1. **PdM が受入基準のマーカーに日本語「結論」を使った**（ロール定義に「文書のマーカーは
   言語非依存の量で」と書いたが従わなかった）
2. Windows PowerShell の文字コードで日本語が化けた（ログに `���_` として現れる）
3. **検査が通らない**——成果物は正しいのにマーカーが判定できない
4. 実装者は「検査を通す」ために**検査器を直し続けた**（29回＋派生15個）

つまり **マーカーが言語に依存したせいで検査が信用できなくなり、その結果として
検査器いじりが誘発された**。②と③は独立の問題ではなく、③が②の引き金である。

最終的に報告書が「結論」節を含む形になり検査4件は ok になったが、
**通ったのが「正しくなったから」なのか「検査器を通るように直したから」なのかは、
もはや区別できない**。これが検査器を凍結できないことの本当の損害である。

### 未解決 — QA は今回も完遂できなかった

権限拒否 32回（012 は 33回）。ロール定義に「中間メモを別ファイルに書くな。判定書に直接書け」と
明記したが**ほぼ効果がなかった**。QA は `qa_manual_assessment.ps1` / `SPEC_review_for_qa.ps1` /
`tmp_qa_*.txt` などを作ろうとしては拒否され続け、最後まで `verdict.md` を完成できずに
`escalated=True` で終わった。

**検証役が中間生成物なしに検証できないのは、モデルの怠慢ではなく作業の性質**と見るべきである。
文書の検証は「読む → 書き出す → 突き合わせる」であり、書き出す場所が無ければ成立しない。

### 構造的な発見 — 受入基準（PdM）とタスク検査（PjM）は別チャネル

PdM の criteria は `Test-Path` / `Get-Content` ベースで、**作られた検査器を使っていない**。
使ったのは PjM のタスク検査だけである。当然で、**PdM は PjM より先に動くので、
まだ存在しない検査器を受入基準に書けない**。

結果として「検査器を作る」計画は立つが、**最終的な受入判定（L4 の決定論 check）は
検査器と無関係の素朴なコマンドで行われる**。検査器を作らせる意味が半減している。

---

## 結論 — 機構に落とすべきものが特定できた

| 対象 | 判定 | 次の一手 |
|---|---|---|
| 検査器を先に作る計画 | **ロール定義で足りる** | 変更を維持する |
| 検査器の凍結 | **プロンプトでは守れない**（実証） | **機構**へ: タスクに凍結宣言を持たせ、完了時に `tools.protect()` をコードが適用する |
| マーカーの言語非依存 | **プロンプトでは守れない** | 機構 or 仕様側の強制（`expect` を ASCII に限定する等）。②の引き金なので優先度が高い |
| QA の作業場 | **プロンプトでは解けない**（権限の問題） | **機構**へ: `write_scope` に scratch 領域を足す |
| 検査器と受入基準の接続 | 構造の問題 | PdM が「検査器を作らせ、その出力を expect にする」と書けるようにするか、L4 が検査器タスクの成果を受入基準に昇格させる |

**「確かめずに機構を足すと要らない機構を作る」という懸念は正しかった** — 計画の部分は
ロール定義だけで解け、機構は要らなかった。同時に、**凍結・マーカー・作業場の3点は
プロンプトでは守れないことが実証で確定**した。次はこの3点だけを機構に落とせばよい。
