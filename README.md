# mu

> 与えられたゴールに向かって PDCA を回し、人間の逐次介入なしに自立実行する **汎用エージェント**。
> それを **きわめてミニマルな仕組み** で実装する。

*この文書は mu のコンセプトと仕様を言語化したもの。L0〜L3 まで実装・検証済み（現在 v0）。*

---

## 三原則

- **シンプル** — 分かりやすい
- **ミニマル** — 最小
- **本質的** — 核だけ

「ミニマル」で最小化する対象を、4つ明示する:

1. **機構の薄さ** — 足場を極薄に。知能は LLM に委ねる
2. **概念の少なさ** — 登場する要素・語彙を絞る
3. **依存とコード量** — 依存は最小（公式 `ollama` クライアントと、その基盤 `httpx` のみ）・短いコード
4. **状態・記憶の少なさ** — 内部状態を最小に

---

## 中核となる考え方 — 自律性の層 (Layers of Autonomy)

mu は入れ子のループでできている。層を貫く軸は **自律性**。

- **内側ほど非自律** — ただ機械的に動く
- **外へ行くほど自律的** — 自分で判断する

作り方も同じ向きに進む。**一番内側の非自律な核を固め、自律性を一枚ずつ外へ重ねていく。**
全体を上から設計しない。内側から育てる。

| 層 | 名前 | 自律性 | 何を回すか |
|---|---|:---:|---|
| **L0** | Ollama インタフェース | ゼロ | Ollama を呼び応答を得る。接続とモデル可用性を安定化・理想化する |
| **L1** | ツールコールのループ | 低 | モデルが選んだツールを mu が実行し、結果を戻して再び問う（＝行動する / Do） |
| **L2** | Reflect ループ（エージェント） | 中 | D=L1 を Reflect(Check+Act) で包み、ゴール達成まで回す。**PDCA が明示的に現れる**。再帰同一構造 |
| **L3** | 大域 Plan（オーケストレータ） | 高 | L2 を"単位"として組み合わせ複雑ゴールを完遂。**PDCA が完全体で現れる**。P・A は HITL 承認、D・C は自律 |
| L4〜 | *（これから）* | より高 | L3 の承認スロットに立つ層。同じ再帰同一構造。最上位の停止は人間 |

> 「自律性の層」とは別に、層の**外側**に **設定系**（初期化などに使う）がある（後述）。

**構造規約 — 1 層 = 1 ファイル。** `mu/l0.py` ・ `mu/l1.py` ・ `mu/l2.py` … と、層番号がそのままファイル名になる。1 ファイルに収まらなくなったら「層が厚すぎ」のシグナルで、分割より先に責務を見直す。

---

## L0 — Ollama インタフェース層（最下層 / 自律性ゼロ）

**基本 LLM は Ollama。** 責務はただ一つ:

> 上位の層に対して「**常に安定して応答が返る、理想化された LLM**」を見せる。

**含むもの:**

1. **推論の呼び出し** — `/api/generate` ・ `/api/chat`（tool calling 対応）
2. **モデル可用性の保証（理想化）** — 使うモデルが無ければ L0 が黙って `/api/pull` し、上位には常に居るように見せる（存在・能力確認に `/api/tags` ・ `/api/show`）
3. **接続の安定化** — 接続確立・リトライ／バックオフ・タイムアウト・エラー回復

**含まないもの:** 埋め込み（`/api/embed` `/api/embeddings`）／ 監視（`/api/ps` `/api/version`）／ blob（`/api/blobs`）／ OpenAI 互換（`/v1/*`）／ モデル管理系（→ **設定系** へ）

L0 は判断しない。ただ確実に応答を返す。

### エラーの扱い — 接続は理想化する、中身は関知しない

> **L0 は「接続」を理想化する。「中身」は理想化しない。**

- 「応答を**得られたか**」に関わる失敗 → L0 が吸収する（リトライ等）。どうしても無理なら **型付きの基盤エラー** として通知
- 「応答の**中身**」の問題（拒否・JSON崩れ・`tool_calls` 不正・空返答）→ **L0 は関知しない**。そのまま応答として上位へ渡す（判断は L1 以降）

**吸収する失敗（リトライ対象）:** 接続不可 ／ タイムアウト ／ ストリーム途中切断 ／ 一時的サーバエラー(5xx) ／ モデル未取得（→ 自動 `pull` して再試行）／ 資源不足（限定的に）

**上位へ見せるエラーは 4 つの型だけ**（Ollama の生エラーは隠す）:

| 型 | 意味 |
|---|---|
| `Unreachable` | 到達不能（リトライ尽き）。今 LLM が使えない |
| `ModelUnavailable` | モデルを用意できない（`pull` 失敗・存在しない） |
| `ResourceExhausted` | 資源不足（限定リトライ後も回復せず） |
| `BadRequest` | 呼び出し側の不正（リトライしない・即通知） |

これ以外はすべて「成功応答」として返る。

**リトライ**: 指数バックオフ＋ジッタ／試行回数・遅延に上限。生成は副作用が無いので再試行して安全（部分出力は破棄して全体を再試行）。具体の回数・秒は実装フェーズで調整。

## L1 — ツールコールのループ（行動する層）

L0 の一発の `/api/chat` を、行動ループに育てる層。

**ツールは Ollama ではなく mu が定義・実行する。** モデルがやるのは「このツールをこの引数で呼びたい」という意図（`tool_calls`）を構造化して返すことだけ。実行しない。

```
① mu が tools（関数の説明書）を渡して /api/chat
② モデルが tool_calls（呼びたい意図）を返す   ← ここで一旦止まる
③ mu が実際にツールを実行し、結果を role:"tool" で戻す
④ その履歴で再び /api/chat → 足りなければ ② へ、済めば終了
```

ここで mu は初めて外界に働きかける（**Do**）。ただし「ゴールに向かって進んでいるか」の判断（**Check / Act = PDCA**）はまだ持たない。それは外側の **L2**。

---

## L2 — Reflect ループ（PDCA / エージェント）

L1 の上に「与えられたゴールに向かって自立実行する」層を重ねる。PDCA のうち **D は L1**。L2 が足すのは **Reflect（Check ＋ Act）** ただ一つ:

```
loop（呼び出し側が規定する上限まで）:
  D       : L1 を回す（ゴールに向かって行動）
  Reflect : 「ゴールは達成されたか？ 未達なら何が足りないか」を構造化出力で1回問う
  判定    : 合格 → 終了 ／ 未達 → next を再投入して継続（＝そこで計画が生まれる）
```

- **再帰同一構造**: この「内側ループ→Reflect→続行/停止」は、L3 が L2 を管理するときも同じ形。再帰の底（最上位の停止）は人間。
- **無状態**: 状態は messages（上位が持つ）。上限（`max_rounds` / `l1_max`）は自層にハードコードせず、呼び出し側が規定する。
- Reflect は L0 の **構造化出力** で合否を確実に取り、判定は **ゴールに明記された制約だけ** を見る。ゆえにゴールは **checkable な成功条件** で与える（曖昧だと収束しない）。

---

## L3 — 大域的 Plan（オーケストレータ / PDCA 完全体）

L2（単一 checkable タスクの完遂）を"単位"として組み合わせ、複雑なゴールを最後まで完遂する層。L2 で暗黙だった **大域的 Plan が明示・必須**になり、PDCA が完全体で現れる:

| | 中身 | 自律/HITL |
|---|---|---|
| **P** | 複雑ゴールを「ファイルを生む checkable な単位」へ分解 | **HITL**（承認スロット） |
| **D** | 各単位を **L2** が完遂 → 成果物ファイル | 自律 |
| **C** | 成果物を確認／L2 の失敗を検知・分析 | 自律 |
| **A** | 再計画（条件/アプローチ/計画の変更） | **HITL**（承認スロット） |

- **ファイル・グラウンディング（L3 の背骨）**: すべての単位は `(task, 出力ファイル, checkable 基準)`。ファイル＋基準が単位を checkable にし（L2 が達成＆検証できる）、ファイルが次の単位への文脈になる（単位間はファイルを介してつながる）。
- **コードの単位**は基準＝テストパス。テストは先行する別単位として作られる → **L3 が TDD をオーケストレーションする**。
- **判断は外へ、実行は内で**: D・C は自律、P・A（判断）は承認スロット `approve` に上がる。承認者は呼び出し側が差し込む（今は人間＝`l3_chat`、将来は L4）。再帰の底は人間。
- 上限（`max_rounds` / `l2_max` / `l2_l1_max`）は呼び出し側が規定（L2 と同じ思想）。1周＝1単位実行 or 1回の全体判定なので、`max_rounds` は暗黙に「単位数＋再計画＋全体判定」の予算になる（返り値の `rounds` で上限到達を判別できる）。

**北極星到達済み** — 「GUI を持つアプリ（auto-checkable でない受け入れ境界を含む複合タスク）を自走で最後まで完成」を実機で達成（2026-07-19、GUI 付き AI チャットアプリ）。

---

## 設定系（自律性の層の外 / 初期化用）

mu の中にあるが、**エージェントのループ・自律性の層（L0〜）の外**。実行前の初期化などで使う。

- `/api/create` ・ `/api/copy` ・ `/api/delete` ・ `/api/push`（モデル管理系）

## 触ってみる

各層を直接叩く最小の CLI チャットを、層ごとに `l{N}_chat.py` として用意する。

```
.\.venv\Scripts\python.exe l0_chat.py [model]
```

`l0_chat.py` は L0 だけを使う（既定モデル `gemma3:1b`）。ツールも PDCA も無い「理想化された chat」だけ。会話履歴は CLI 側が保持し、L0 は無状態のまま。L0 の 4 型エラーはそのまま表示される。

```
.\.venv\Scripts\python.exe l1_chat.py [model]
```

`l1_chat.py` は L1（ツールコールのループ）を使う（既定 `qwen3.5:9b`、tool 対応モデルが必要）。検証用ツール `read_file` / `write_file` / `edit_file` / `list_dir` / `execute_command`（PowerShell 実行）を登録済み。起動時に OS・作業ディレクトリ・シェルの環境情報を渡すので、「このフォルダのファイルを見て README を要約して」のような実タスクが回る。ツール実行は `[tool] ...` と表示。

```
.\.venv\Scripts\python.exe l2_chat.py [model]
```

`l2_chat.py` は L2（PDCA / Reflect ループ）を使う（既定 `qwen3.5:9b`）。1行の**ゴール**を入力すると、`D → Reflect → 続行/停止` を各周ごとに表示しながら達成まで回す。参照モデルは **qwen3.5:9b / gemma4:12b**。ゴールは checkable な成功条件で与える（例:「概要を `- ` 箇条書き3項目で abstract.md に」）。

```
.\.venv\Scripts\python.exe l3_chat.py [model]
```

`l3_chat.py` は L3（大域 Plan）を使う（既定 `gemma4:12b`）。複雑ゴール（例:「電卓ロジックを calc.py に実装し、test_calc.py のテストをパスさせる」）を入力すると Plan を提示して承認を求め（`y`=実行 / `d N`=単位 N 削除 / `n`=中断）、各単位を L2 が自走する。各層の動き（Plan・Reflect・思考・ツール実行）はインデント付きで実況される。**成果物は cwd に実ファイルとして生成されるので、使い捨てのディレクトリで実行すること。**

## 決定事項と未決事項

- **決定**: 基本 LLM = Ollama ／ L0 のスコープ（上記）／ **L0 のエラー方針（接続を理想化・4型・リトライ）** ／ L1 = ツールコールのループ ／ **L2 = Reflect ループ（再帰同一構造）** ／ **L3 = 大域 Plan（P・A は HITL 承認スロット、D・C は自律、ファイル・グラウンディング）** ／ 設定系の位置づけ
- **L0 は実装・テスト済み** — `mu/l0.py`（言語 Python／依存 公式 `ollama` クライアント）。接続の理想化に connect タイムアウト・pull リトライを含む
- **L1 は実装・テスト済み** — `mu/l1.py`（無状態 `step()`／`(func, usage_text)` ペア／system注入＋構造化tools／dispatch はシグネチャ束縛＝幻覚 kwarg を落として注記）。検証用ツール `tools.py`（read_file / write_file / edit_file / list_dir / execute_command＝PowerShell）＋環境グラウンディング（呼び出し側が OS/cwd/shell を注入）
- **L2 は実装・検証済み** — `mu/l2.py`（`Agent`, `step`/`run`）。D=L1 を Reflect(C+A) で包む再帰同一構造。実タスク T1〜T4（網羅性・制約＋修正・正確性・実行照合）を**参照モデル qwen3.5:9b / gemma4:12b で検証**
- **L3 は実装・検証済み** — `mu/l3.py`（`Orchestrator`）。Plan／失敗分析／再計画／全体判定の生命線プロンプトを実タスクで調整。**北極星「GUI を持つアプリの自走完遂」到達**（2026-07-19）。既定モデルは gemma4:12b（qwen3.5:9b は参照として残し、構造限界とモデル限界を切り分ける）
- テスト全体 **73 green**（ユニット＋実接続 live）
- **未決**: L4（L3 の承認スロットに立つ外層）／ HITL 承認の粒度 ／ 収束しない場合の運用 — 内側から順に、対話で決める

*Ollama API の全エンドポイント一覧は公式 docs（docs.ollama.com/api）参照。上記は mu が扱う範囲のみ。*
