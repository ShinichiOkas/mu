# mu

> 与えられたゴールに向かって PDCA を回し、人間の逐次介入なしに自立実行する **汎用エージェント**。
> それを **きわめてミニマルな仕組み** で実装する。

*この文書は mu のコンセプトと仕様を言語化し、対話で洗練していくためのもの。実装はこの後。現在 v0（たたき台）。*

---

## 三原則

- **シンプル** — 分かりやすい
- **ミニマル** — 最小
- **本質的** — 核だけ

「ミニマル」で最小化する対象を、4つ明示する:

1. **機構の薄さ** — 足場を極薄に。知能は LLM に委ねる
2. **概念の少なさ** — 登場する要素・語彙を絞る
3. **依存とコード量** — 外部依存ゼロ・短いコード
4. **状態・記憶の少なさ** — 内部状態を最小に

---

## 中核となる考え方 — 自律性の層 (Layers of Autonomy)

mu は入れ子のループでできている。層を貫く軸は **自律性**。

- **内側ほど非自律** — ただ機械的に動く
- **外へ行くほど自律的** — 自分で判断する

作り方も同じ向きに進む。**一番内側の非自律な核を固め、自律性を一枚ずつ外へ重ねていく。**
全体を上から設計しない。内側から育てる。

| 層 | 名前 | 自律性 | 何を回すか |
|---|---|:---:|---|
| **L0** | Ollama インタフェース | ゼロ | Ollama を呼び応答を得る。接続とモデル可用性を安定化・理想化する |
| **L1** | ツールコールのループ | 低 | モデルが選んだツールを mu が実行し、結果を戻して再び問う（＝行動する / Do） |
| L2〜 | *（これから）* | → | 内側が固まり次第、外へ向かって順次定義する |
| *（外側のどこか）* | エージェント | 高 | 与えられたゴール + PDCA を回して自立実行。**PDCA はこの層で明示的に現れる** |

> 「自律性の層」とは別に、層の**外側**に **設定系**（初期化などに使う）がある（後述）。

**構造規約 — 1 層 = 1 ファイル。** `mu/l0.py` ・ `mu/l1.py` ・ `mu/l2.py` … と、層番号がそのままファイル名になる。1 ファイルに収まらなくなったら「層が厚すぎ」のシグナルで、分割より先に責務を見直す。

---

## L0 — Ollama インタフェース層（最下層 / 自律性ゼロ）

**基本 LLM は Ollama。** 責務はただ一つ:

> 上位の層に対して「**常に安定して応答が返る、理想化された LLM**」を見せる。

**含むもの:**

1. **推論の呼び出し** — `/api/generate` ・ `/api/chat`（tool calling 対応）
2. **モデル可用性の保証（理想化）** — 使うモデルが無ければ L0 が黙って `/api/pull` し、上位には常に居るように見せる（存在・能力確認に `/api/tags` ・ `/api/show`）
3. **接続の安定化** — 接続確立・リトライ／バックオフ・タイムアウト・エラー回復

**含まないもの:** 埋め込み（`/api/embed` `/api/embeddings`）／ 監視（`/api/ps` `/api/version`）／ blob（`/api/blobs`）／ OpenAI 互換（`/v1/*`）／ モデル管理系（→ **設定系** へ）

L0 は判断しない。ただ確実に応答を返す。

### エラーの扱い — 接続は理想化する、中身は関知しない

> **L0 は「接続」を理想化する。「中身」は理想化しない。**

- 「応答を**得られたか**」に関わる失敗 → L0 が吸収する（リトライ等）。どうしても無理なら **型付きの基盤エラー** として通知
- 「応答の**中身**」の問題（拒否・JSON崩れ・`tool_calls` 不正・空返答）→ **L0 は関知しない**。そのまま応答として上位へ渡す（判断は L1 以降）

**吸収する失敗（リトライ対象）:** 接続不可 ／ タイムアウト ／ ストリーム途中切断 ／ 一時的サーバエラー(5xx) ／ モデル未取得（→ 自動 `pull` して再試行）／ 資源不足（限定的に）

**上位へ見せるエラーは 4 つの型だけ**（Ollama の生エラーは隠す）:

| 型 | 意味 |
|---|---|
| `Unreachable` | 到達不能（リトライ尽き）。今 LLM が使えない |
| `ModelUnavailable` | モデルを用意できない（`pull` 失敗・存在しない） |
| `ResourceExhausted` | 資源不足（限定リトライ後も回復せず） |
| `BadRequest` | 呼び出し側の不正（リトライしない・即通知） |

これ以外はすべて「成功応答」として返る。

**リトライ**: 指数バックオフ＋ジッタ／試行回数・遅延に上限。生成は副作用が無いので再試行して安全（部分出力は破棄して全体を再試行）。具体の回数・秒は実装フェーズで調整。

## L1 — ツールコールのループ（行動する層）

L0 の一発の `/api/chat` を、行動ループに育てる層。

**ツールは Ollama ではなく mu が定義・実行する。** モデルがやるのは「このツールをこの引数で呼びたい」という意図（`tool_calls`）を構造化して返すことだけ。実行しない。

```
① mu が tools（関数の説明書）を渡して /api/chat
② モデルが tool_calls（呼びたい意図）を返す   ← ここで一旦止まる
③ mu が実際にツールを実行し、結果を role:"tool" で戻す
④ その履歴で再び /api/chat → 足りなければ ② へ、済めば終了
```

ここで mu は初めて外界に働きかける（**Do**）。ただし「ゴールに向かって進んでいるか」の判断（**Check / Act = PDCA**）はまだ持たない。それは更に外側の層。

---

## 設定系（自律性の層の外 / 初期化用）

mu の中にあるが、**エージェントのループ・自律性の層（L0〜）の外**。実行前の初期化などで使う。

- `/api/create` ・ `/api/copy` ・ `/api/delete` ・ `/api/push`（モデル管理系）

---

## 触ってみる

各層を直接叩く最小の CLI チャットを、層ごとに `l{N}_chat.py` として用意する。

```
.\.venv\Scripts\python.exe l0_chat.py [model]
```

`l0_chat.py` は L0 だけを使う（既定モデル `gemma3:1b`）。ツールも PDCA も無い「理想化された chat」だけ。会話履歴は CLI 側が保持し、L0 は無状態のまま。L0 の 4 型エラーはそのまま表示される。
