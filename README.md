# mu

> 与えられたゴールに向かって PDCA を回し、人間の逐次介入なしに自立実行する **汎用エージェント**。
> それを **きわめてミニマルな仕組み** で実装する。

*この文書は mu のコンセプトと仕様を言語化したもの。L0〜L5 まで実装・検証済み（現在 v0）。*

---

## 三原則

- **シンプル** — 分かりやすい
- **ミニマル** — 最小
- **本質的** — 核だけ

「ミニマル」で最小化する対象を、4つ明示する:

1. **機構の薄さ** — 足場を極薄に。知能は LLM に委ねる
2. **概念の少なさ** — 登場する要素・語彙を絞る
3. **依存とコード量** — 依存は最小（公式 `ollama` クライアントと、その基盤 `httpx` のみ）・短いコード
4. **状態・記憶の少なさ** — 内部状態を最小に

---

## 中核となる考え方 — 自律性の層 (Layers of Autonomy)

mu は入れ子のループでできている。層を貫く軸は **自律性**。

- **内側ほど非自律** — ただ機械的に動く
- **外へ行くほど自律的** — 自分で判断する

作り方も同じ向きに進む。**一番内側の非自律な核を固め、自律性を一枚ずつ外へ重ねていく。**
全体を上から設計しない。内側から育てる。

| 層 | 名前 | 自律性 | 何を回すか |
|---|---|:---:|---|
| **L0** | Ollama インタフェース | ゼロ | Ollama を呼び応答を得る。接続とモデル可用性を安定化・理想化する |
| **L1** | ツールコールのループ | 低 | モデルが選んだツールを mu が実行し、結果を戻して再び問う（＝行動する / Do） |
| **L2** | Reflect ループ（エージェント） | 中 | D=L1 を Reflect(Check+Act) で包み、ゴール達成まで回す。**PDCA が明示的に現れる**。再帰同一構造 |
| **L3** | 大域 Plan（オーケストレータ） | 高 | L2 を"単位"として組み合わせ複雑ゴールを完遂。**PDCA が完全体で現れる**。P・A は HITL 承認、D・C は自律 |
| **L4** | 進行の層（PjM） | より高 | SPEC を受け取り**役割注釈付きプロセス**を編み、L3 に1タスクずつ着せて回す。QA は独立タスク。rerun/replan は自分で、respec/escalate は上へ返す |
| **L5** | 目的の層（PdM） | さらに高 | **目的**を受け取り、充足可能性を判断して仕様を定め、L4 を回し、結果を見て accept / respec / escalate を決める |
| L6〜 | *（これから）* | さらに高 | L5 の判断スロットに立つ層。同じ再帰同一構造。最上位の停止は人間 |

> 「自律性の層」とは別に、層の**外側**に **設定系**（初期化などに使う）がある（後述）。

**構造規約 — 1 層 = 1 ファイル。** `mu/l0.py` ・ `mu/l1.py` ・ `mu/l2.py` … と、層番号がそのままファイル名になる。1 ファイルに収まらなくなったら「層が厚すぎ」のシグナルで、分割より先に責務を見直す。

層の外には2種類のものが置かれる。どちらも「層が薄いままでいる」ために外にある。

- **データ**（`roles/*.md`）— 役割定義・プロンプトなど、**用途によって変動する値**。人間が直接編集できる。データを外に出すのは「分割」ではない。ただし出すのは変動する値だけで、システムが稼働するための**普遍の値（契約・床）はコアに残す**。
- **facility**（`mu/role_kb.py` ・ `mu/process.py` ・ `tools.py`）— 層ではない共通機能。役割定義の読み込みと権限適用、プロセス（タスク列）の状態管理と artifact、検証用ツール群。**データの"形"だけが契約で、"出所"は差し替え可能**（いまはファイル、将来 DB でも層は無変更）。

## 層と役割 — 全体像

### 層: それぞれが埋めている「落差」

層は機能の分類ではない。**それぞれが1つの落差を埋めるために在る。**

| 層 | 埋める落差（＝存在意義） | 役割（何をするか） | 主な生成物 |
|---|---|---|---|
| **L0** | 実行環境は不安定 ↔ 上位は「呼べば返る」と仮定したい | 接続・モデル可用性を理想化する（リトライ・自動 pull・4型エラー） | 応答 |
| **L1** | モデルは考えるだけ ↔ 仕事は世界に触れないと終わらない | モデルが選んだツールを実行し、結果を戻して再び問う（＝**Do**） | ツール実行の事実（facts） |
| **L2** | 1回行動した ↔ ゴールに達したかは別問題 | Reflect（Check+Act）で合否を判定し、達成まで繰り返す（**PDCA**） | 単位の成果物ファイル |
| **L3** | checkable な単位 ↔ 人が頼むのは複雑なゴール | 大域 Plan で単位に分解し、各単位を L2 に完遂させる | 複数ファイルの成果物 |
| **L4** | 仕様は決まった ↔ **誰がどの順で何を作るかは別問題** | プロセス（役割つきタスク列）を編み、人選し、役割を着せた L3 に1つずつ回して検証を集める | PROCESS.md / 成果物 / verdict.md |
| **L5** | 詳細な仕様 ↔ **人が自然に言えるのは目的だけ** | 目的を検査可能な仕様に翻訳し、L4 を回し、結果を見て仕様を直すか人間に上げるかを決める | SPEC.md |
| L6〜 | *（これから）* | L5 の判断スロットに立つ層 | — |

**再帰同一構造**: どの層も「内側の層を **D（実行）** として使い、その外側に判断を足す」形をしている。だから層は積み増せる。停止と責任の底は常に人間。

### 役割（role）: 誰が何を担うか

役割は**コード構造ではなくタスクの属性**である（役割ごとのクラスは無い）。定義書は `roles/*.md` にあり、**人間が直接編集できる**。5役割すべてが同じ形で外にあり、コードの中に役割ごとの分岐やプロンプトは無い。

- **位置はコアが知り、中身は定義書が決める。** 「そこに PdM が居る」ことは不変、「どういう PdM か」は用途で変わる。
- 定義書が無ければ、**役割は認識しているが知識が無い状態**で動く（多くの場合そのプロジェクトは失敗する——それが正しい挙動であり、静かに埋めない）。
- 定義書の frontmatter は**権限の宣言**でもあり、適用するのはコード。LLM が出せるのは役割名だけなので、**権限を LLM 側から書き換えられない**。

| role | 居場所 | 意味（職掌） | 見るもの | 生むもの | 権限 |
|---|---|---|---|---|---|
| **pdm** | **L5** そのもの | 目的 → 仕様。**まず充足可能性を申告**し、満たせない目的の仕様は作らない | 目的の原文＋**入力の実物** | `SPEC.md`（操作的定義・受入基準・仕様） | — |
| **pjm** | **L4** そのもの | どう進めるか。プロセスを編み、**人選**し、失敗を受けて**部分再実行**を判断する | SPEC＋役割 KB＋モデルプール | `PROCESS.md`（体制表） | — |
| **architect** | プロセス内のタスク | 構造・品質特性・**設計規則**を定める | SPEC | `design.md` | 制限なし |
| **implementer** | プロセス内のタスク | 実装・テスト・品質ゲートの実行 | SPEC・design.md | 成果物 | 制限なし |
| **qa** | プロセス内のタスク | 独立検証。**仕様への忠実さと目的の達成は別物**として検査する | SPEC・成果物の実物・**目的の原文** | `verdict.md` | 自分の判定書のみ書ける（`edit_file` は持たない） |

**人間はモデルプールの外**にいる。PjM が管理する人員ではなく、`escalate` で判断を依頼する相手——再帰の底である。

## L0 — Ollama インタフェース層（最下層 / 自律性ゼロ）

**基本 LLM は Ollama。** 責務はただ一つ:

> 上位の層に対して「**常に安定して応答が返る、理想化された LLM**」を見せる。

**含むもの:**

1. **推論の呼び出し** — `/api/generate` ・ `/api/chat`（tool calling 対応）
2. **モデル可用性の保証（理想化）** — 使うモデルが無ければ L0 が黙って `/api/pull` し、上位には常に居るように見せる（存在・能力確認に `/api/tags` ・ `/api/show`）
3. **接続の安定化** — 接続確立・リトライ／バックオフ・タイムアウト・エラー回復

**含まないもの:** 埋め込み（`/api/embed` `/api/embeddings`）／ 監視（`/api/ps` `/api/version`）／ blob（`/api/blobs`）／ OpenAI 互換（`/v1/*`）／ モデル管理系（→ **設定系** へ）

L0 は判断しない。ただ確実に応答を返す。

### エラーの扱い — 接続は理想化する、中身は関知しない

> **L0 は「接続」を理想化する。「中身」は理想化しない。**

- 「応答を**得られたか**」に関わる失敗 → L0 が吸収する（リトライ等）。どうしても無理なら **型付きの基盤エラー** として通知
- 「応答の**中身**」の問題（拒否・JSON崩れ・`tool_calls` 不正・空返答）→ **L0 は関知しない**。そのまま応答として上位へ渡す（判断は L1 以降）

**吸収する失敗（リトライ対象）:** 接続不可 ／ タイムアウト ／ ストリーム途中切断 ／ 一時的サーバエラー(5xx) ／ モデル未取得（→ 自動 `pull` して再試行）／ 資源不足（限定的に）

**上位へ見せるエラーは 4 つの型だけ**（Ollama の生エラーは隠す）:

| 型 | 意味 |
|---|---|
| `Unreachable` | 到達不能（リトライ尽き）。今 LLM が使えない |
| `ModelUnavailable` | モデルを用意できない（`pull` 失敗・存在しない） |
| `ResourceExhausted` | 資源不足（限定リトライ後も回復せず） |
| `BadRequest` | 呼び出し側の不正（リトライしない・即通知） |

これ以外はすべて「成功応答」として返る。

**リトライ**: 指数バックオフ＋ジッタ／試行回数・遅延に上限。生成は副作用が無いので再試行して安全（部分出力は破棄して全体を再試行）。具体の回数・秒は実装フェーズで調整。

## L1 — ツールコールのループ（行動する層）

L0 の一発の `/api/chat` を、行動ループに育てる層。

**ツールは Ollama ではなく mu が定義・実行する。** モデルがやるのは「このツールをこの引数で呼びたい」という意図（`tool_calls`）を構造化して返すことだけ。実行しない。

```
① mu が tools（関数の説明書）を渡して /api/chat
② モデルが tool_calls（呼びたい意図）を返す   ← ここで一旦止まる
③ mu が実際にツールを実行し、結果を role:"tool" で戻す
④ その履歴で再び /api/chat → 足りなければ ② へ、済めば終了
```

ここで mu は初めて外界に働きかける（**Do**）。ただし「ゴールに向かって進んでいるか」の判断（**Check / Act = PDCA**）はまだ持たない。それは外側の **L2**。

---

## L2 — Reflect ループ（PDCA / エージェント）

L1 の上に「与えられたゴールに向かって自立実行する」層を重ねる。PDCA のうち **D は L1**。L2 が足すのは **Reflect（Check ＋ Act）** ただ一つ:

```
loop（呼び出し側が規定する上限まで）:
  D       : L1 を回す（ゴールに向かって行動）
  Reflect : 「ゴールは達成されたか？ 未達なら何が足りないか」を構造化出力で1回問う
  判定    : 合格 → 終了 ／ 未達 → next を再投入して継続（＝そこで計画が生まれる）
```

- **再帰同一構造**: この「内側ループ→Reflect→続行/停止」は、L3 が L2 を管理するときも同じ形。再帰の底（最上位の停止）は人間。
- **無状態**: 状態は messages（上位が持つ）。上限（`max_rounds` / `l1_max`）は自層にハードコードせず、呼び出し側が規定する。
- Reflect は L0 の **構造化出力** で合否を確実に取り、判定は **ゴールに明記された制約だけ** を見る。ゆえにゴールは **checkable な成功条件** で与える（曖昧だと収束しない）。

---

## L3 — 大域的 Plan（オーケストレータ / PDCA 完全体）

L2（単一 checkable タスクの完遂）を"単位"として組み合わせ、複雑なゴールを最後まで完遂する層。L2 で暗黙だった **大域的 Plan が明示・必須**になり、PDCA が完全体で現れる:

| | 中身 | 自律/HITL |
|---|---|---|
| **P** | 複雑ゴールを「ファイルを生む checkable な単位」へ分解 | **HITL**（承認スロット） |
| **D** | 各単位を **L2** が完遂 → 成果物ファイル | 自律 |
| **C** | 成果物を確認／L2 の失敗を検知・分析 | 自律 |
| **A** | 再計画（条件/アプローチ/計画の変更） | **HITL**（承認スロット） |

- **ファイル・グラウンディング（L3 の背骨）**: すべての単位は `(task, 出力ファイル, checkable 基準)`。ファイル＋基準が単位を checkable にし（L2 が達成＆検証できる）、ファイルが次の単位への文脈になる（単位間はファイルを介してつながる）。
- **コードの単位**は基準＝テストパス。テストは先行する別単位として作られる → **L3 が TDD をオーケストレーションする**。
- **判断は外へ、実行は内で**: D・C は自律、P・A（判断）は承認スロット `approve` に上がる。承認者は呼び出し側が差し込む（人間＝`l3_chat`／L4 から呼ぶときは自律承認で、判断は L4 側の PjM が持つ）。再帰の底は人間。
- 上限（`max_rounds` / `l2_max` / `l2_l1_max`）は呼び出し側が規定（L2 と同じ思想）。1周＝1単位実行 or 1回の全体判定なので、`max_rounds` は暗黙に「単位数＋再計画＋全体判定」の予算になる（返り値の `rounds` で上限到達を判別できる）。

**北極星到達済み** — 「GUI を持つアプリ（auto-checkable でない受け入れ境界を含む複合タスク）を自走で最後まで完成」を実機で達成（2026-07-19、GUI 付き AI チャットアプリ）。

## L4 — 進行の層（PjM / Manager）

仕様が決まっても「**誰がどの順で何を作るか**」は別問題である。その落差を埋めるのが L4。
SPEC（何を作るか）を受け取り、**役割注釈付きプロセス**を編み、役割を着せた L3 に1タスクずつ完遂させ、
検証を集める。マルチエージェントを新しいフレームワークとして足すのではなく、
**「役割を着せた L3 の逐次ループ」**に還元してある（並列化は後から足せる最適化にすぎない）。

| | 中身 | 誰が |
|---|---|---|
| **P** | SPEC → プロセス（役割・出力ファイル・成功条件・**人選**を持つタスク列）＝ `PROCESS.md` | PjM（LLM） |
| **D** | 1タスクずつ、役割定義を前置し**役割の権限で絞ったツール**で L3 に完遂させる | 内側の層 |
| **C** | 受入基準の決定論 check ＋ 末尾の QA タスクが書く `verdict.md` の機械読み | コード |
| **A** | **rerun**（部分再実行）/ **replan**（プロセスを組み直す）は自分で回す | PjM（LLM） |

- **自分の職掌で直せないものは上へ返す**。`respec`（仕様が悪い）と `escalate`（人手が要る／予算切れ）は
  この層では処理せず、**outcome として L5 に申告する**——判断は外へ、実行は内で。
- **役割はコード構造ではなくタスクの属性**。増えたのは `task = {role, task, file, criterion, check?, model?}` の
  2属性だけで、役割ごとのクラスは無い。
- **決定論の床**: プロセス末尾に QA タスクが無ければコードが足す ／ 判定書の契約はコードが供給する ／
  無効化はファイル依存で伝播し **QA は必ず再実行** ／ 受入基準の check は verdict と独立に走る ／
  役割の権限はコードが適用する（**QA は自分の判定書しか書けない**）／ 壊れた判断は安全側へ落ちる。
- プロセス（タスク列）の状態管理と判定書の入出力は facility [`mu/process.py`](mu/process.py) にある。
  依存グラフは**並列可能性を判定するグラフと同一物**であり、並列実行を入れるときに触るのもそこ。

---

## L5 — 目的の層（PdM / Director）

L4 に渡せるのは「仕様」だが、**人間が自然に言えるのは目的**である（「この売上表から不採算商品を特定してくれ」）。
*なぜ作るか* と *何を作るか* の落差を埋めるのが L5。

| | 中身 | 誰が |
|---|---|---|
| **P** | 目的 → **充足可能性の判断** → 操作的定義＋受入基準＋仕様 ＝ `SPEC.md` | PdM（LLM） |
| **D** | SPEC を L4 に渡し、プロセスを編ませて完遂させる | 内側の層 |
| **C** | L4 が返す `verdict`（QA の判定）と `checks`（決定論の受入検査）を読む | コード |
| **A** | accept ／ respec（仕様を直して再実行）／ escalate（人間へ） | レビュー担当 |

- **充足不能なら仕様を作らない**。制約が同時に満たせない目的（「完全に除去せよ、ただし1文字も変えるな」）は、
  退化解を独断で採らずに人間へ上げる。申告は `SPEC.md` にも残る——コードの分岐なので握り潰せない。
- **定義は入力の実物に接地する**。仕様を作る前に、作業ディレクトリの実在ファイル（一覧＋先頭）を
  コードが読んで PdM に前置する（形式を発明させない）。
- **人間はモデルプールの外**にいる。PjM が管理する人員ではなく、`escalate` で依頼する相手（再帰の底）。
- **無状態**。上限（予算の封筒）・レビュー担当・役割 KB・モデルプールは呼び出し側が規定する。
  **予算は各層が自分で持つ**——L5 は respec サイクル、L4 は PjM サイクル。
- **入力保護**は `tools.protect()`（呼び出し側が宣言）。守るのは列挙したファイルの**内容不変だけ**で、
  ディレクトリ不変ではない。塞げない破れ（シェルリダイレクト等）は `protection_violations()` で**検出できる**。

**検証済み** — 難課題6件（曖昧語の操作的定義・禁止制約・矛盾した目的・依存連鎖・テスト変更禁止の契約・
性能要件）で実走し、**偽・完遂ゼロ**。充足不能の目的は仕様を作らずに人間へ上がる（3/3）。
役割定義を空にした対照走では成果が崩れ、**外に出した知識が効いていること**も実証済み。→ [runs/](runs/)

---

## 設定系（自律性の層の外 / 初期化用）

mu の中にあるが、**エージェントのループ・自律性の層（L0〜）の外**。実行前の初期化などで使う。

- `/api/create` ・ `/api/copy` ・ `/api/delete` ・ `/api/push`（モデル管理系）

## 触ってみる

各層を直接叩く最小の CLI チャットを、層ごとに `l{N}_chat.py` として用意する。

```
.\.venv\Scripts\python.exe l0_chat.py [model]
```

`l0_chat.py` は L0 だけを使う（既定モデル `gemma3:1b`）。ツールも PDCA も無い「理想化された chat」だけ。会話履歴は CLI 側が保持し、L0 は無状態のまま。L0 の 4 型エラーはそのまま表示される。

```
.\.venv\Scripts\python.exe l1_chat.py [model]
```

`l1_chat.py` は L1（ツールコールのループ）を使う（既定 `qwen3.5:9b`、tool 対応モデルが必要）。検証用ツール `read_file` / `write_file` / `edit_file` / `list_dir` / `execute_command`（PowerShell 実行）を登録済み。起動時に OS・作業ディレクトリ・シェルの環境情報を渡すので、「このフォルダのファイルを見て README を要約して」のような実タスクが回る。ツール実行は `[tool] ...` と表示。

```
.\.venv\Scripts\python.exe l2_chat.py [model]
```

`l2_chat.py` は L2（PDCA / Reflect ループ）を使う（既定 `qwen3.5:9b`）。1行の**ゴール**を入力すると、`D → Reflect → 続行/停止` を各周ごとに表示しながら達成まで回す。参照モデルは **qwen3.5:9b / gemma4:12b**。ゴールは checkable な成功条件で与える（例:「概要を `- ` 箇条書き3項目で abstract.md に」）。

```
.\.venv\Scripts\python.exe l3_chat.py [model]
```

`l3_chat.py` は L3（大域 Plan）を使う（既定 `gemma4:12b`）。複雑ゴール（例:「電卓ロジックを calc.py に実装し、test_calc.py のテストをパスさせる」）を入力すると Plan を提示して承認を求め（`y`=実行 / `d N`=単位 N 削除 / `n`=中断）、各単位を L2 が自走する。各層の動き（Plan・Reflect・思考・ツール実行）はインデント付きで実況される。**成果物は cwd に実ファイルとして生成されるので、使い捨てのディレクトリで実行すること。**

```
.\.venv\Scripts\python.exe l4_chat.py <spec.json|spec.md> [model] [追加モデル...]
```

`l4_chat.py` は L4（進行の層）だけを使う。**仕様を直接渡す**と、PjM がプロセスを編み、役割を着せた L3 が1タスクずつ完遂し、決定論 check と QA の verdict が集まる。返る `outcome`（`done` / `respec` / `escalate`）がこの層の申告——「自分の職掌で直せるか否か」が観測できる。

```
.\.venv\Scripts\python.exe l5_chat.py [model] [追加モデル...]
```

`l5_chat.py` は L5（目的の層）を使う（既定 `gemma4:12b`、開発回転は `gemma4:31b-cloud` を推奨）。**目的**を1行入力すると、SPEC.md（仕様）→ PROCESS.md（体制表）→ 各タスクの実行 → verdict.md（QA 判定）が順に生成され、全層の動きが実況される。追加モデルは PjM の人選プール（例: QA を別ファミリーに出す `qwen3.5:9b`）。最終判定では `y`=受理 / `f XXX`=フィードバックで仕様を改訂して再実行 / `n`=未達のまま終了。**同じく使い捨てのディレクトリで実行すること。**

## 決定事項と未決事項

- **決定**: 基本 LLM = Ollama ／ L0 のスコープ（上記）／ **L0 のエラー方針（接続を理想化・4型・リトライ）** ／ L1 = ツールコールのループ ／ **L2 = Reflect ループ（再帰同一構造）** ／ **L3 = 大域 Plan（P・A は HITL 承認スロット、D・C は自律、ファイル・グラウンディング）** ／ **L4 = 進行の層（PjM。プロセスと人選、rerun/replan は自分で・respec/escalate は上へ）** ／ **L5 = 目的の層（PdM。目的→仕様、充足可能性の判断、accept/respec/escalate）** ／ 設定系の位置づけ
- **L0 は実装・テスト済み** — `mu/l0.py`（言語 Python／依存 公式 `ollama` クライアント）。接続の理想化に connect タイムアウト・pull リトライを含む
- **L1 は実装・テスト済み** — `mu/l1.py`（無状態 `step()`／`(func, usage_text)` ペア／system注入＋構造化tools／dispatch はシグネチャ束縛＝幻覚 kwarg を落として注記）。検証用ツール `tools.py`（read_file / write_file / edit_file / list_dir / execute_command＝PowerShell）＋環境グラウンディング（呼び出し側が OS/cwd/shell を注入）
- **L2 は実装・検証済み** — `mu/l2.py`（`Agent`, `step`/`run`）。D=L1 を Reflect(C+A) で包む再帰同一構造。実タスク T1〜T4（網羅性・制約＋修正・正確性・実行照合）を**参照モデル qwen3.5:9b / gemma4:12b で検証**
- **L3 は実装・検証済み** — `mu/l3.py`（`Orchestrator`）。Plan／失敗分析／再計画／全体判定の生命線プロンプトを実タスクで調整。**北極星「GUI を持つアプリの自走完遂」到達**（2026-07-19）。既定モデルは gemma4:12b（qwen3.5:9b は参照として残し、構造限界とモデル限界を切り分ける）
- **L4 / L5 は実装・検証済み** — `mu/l4.py`（`Manager`＝進行の層）・`mu/l5.py`（`Director`＝目的の層）＋ `roles/`（役割定義書＝ナレッジベース兼権限宣言）＋ facility（`role_kb.py` / `process.py`）。充足可能性の申告・入力の実物への接地・役割注釈付きプロセス・部分再実行・独立 QA・役割別ツール権限。難課題6件で実走し**偽・完遂ゼロ**
- テスト全体 **166 green**（ユニット＋実接続 live）
- **未決**: **並列実行**（無効でない独立タスクの同時実行。依存グラフは `mu/process.py` に敷設済み）／ L6（L5 の判断スロットに立つ外層）／ 収束しない場合の運用 — 内側から順に、対話で決める
