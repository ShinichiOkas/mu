## 新しく出た病理と対処

### 1. 部分可視が API の発明を招く（schedule 偽・不合格）

実体は完璧（唯一の正解枠を予約）・QA yes なのに、機械検査が落ちて escalate。
PdM が**見えていない usage の続きを推測**して存在しないサブコマンド `list` を発明
（**3走連続で再現**——安定した病理）。さらに自作モックが未知コマンドに
ヘルプ＋exit 0 で応じ、壊れた検査を静かに成功扱いにしていた（計測器自身が
[[denial-must-carry-the-norm]] 違反）。

対処は抜粋算術と同じ二段構え＋α:
- 規範「**実際に見た呼び出し形だけを使う**」（pdm.md）
- **自己記述の全文接地**（`_input_grounding` が .py の docstring / .ps1 のコメント塊を
  丸ごと見せる——発明の必要そのものを消す）
- 「検査コマンド自体の故障は respec」（pjm.md。PjM が原因を言語化しながら rerun を
  選び続けた対処）＋ `escalation_reason` の結果契約追加

**3条件比較で因果を分離**: v1（旧規範・静かなモック）偽・不合格 → v2（旧規範・大声モック）
発明は継続 → v3（新規範＋全文接地）**発明消滅・achieved**。
規範だけでなく接地が効いたことが対照つきで言える。

### 2. 偽・不合格という失敗クラスの初観測

偽・達成（危険側）はゼロのまま、偽・不合格（安全側・高価）が初めて出た。
安全側に倒れる設計は正しく働いたが、正しい成果物が2周ぶん疑われ続けた。
検証系の誤りは両方向とも修理対象——ただし優先度は非対称のまま（危険側＞安全側）。

## 学び（Skill 候補）

- 道具の使い方は全文見せる——**部分可視は発明を招く**（LLM は見えない部分を
  「無い」でなく「こうだろう」で埋める。データの抜粋算術と道具の API 発明は同根）
- **協調的締切は、全てのブロッキング呼び出しが有限であって初めて機能する**
  （1つの無限 I/O が watchdog 全体を無効化する）
- 修理の検証に**対照条件**を使う（v2 = 計測器修理のみ、で規範の効果を分離）——
