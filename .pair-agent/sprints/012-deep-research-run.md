## 主題

mu は汎用エージェントを名乗るが、ここまでの実装・検証は事実上**コーディングエージェント**だった。
**成果物がコードでない領域で層構造が通用するか**を、ディープリサーチ 1 本の実走で確かめた。
完了条件は「完走」ではなく「**具体的な観測が得られること**」に置いた。

## 結果 — 動いた。壊れたのは検査の独立性

- 目的→仕様→プロセス→役割→実行→QA→決定論 check の**一巡は成立**し、部分再実行も働いた
- 最終成果物 `report.md`（4ツール比較表・個別分析・結論）は妥当で、**出典2件は実在**（捏造なし）
- 途中で主題がプロジェクト管理ツール比較へ丸ごとドリフトしたが、**自力で復帰**した

### 最重要の観測 — 検査器が成果物になった

人間が置いた検証スクリプト `check_sources.py` を走行が**上書き**した。経路:

1. **PdM** が `check_sources.py` を受入基準に採用（接地は働いた）。ただし期待マーカーを
   **`ALL_URLS_VALID` と発明**（実物は `SOURCES_OK`）
2. **PjM** がその食い違いを**実装課題に変換**（「その出力を出すスクリプトを実装せよ」）
3. **実装者**が上書き。最初の版は **URL 0 件なら合格**を印字する空振り実装

師匠の読み直し:

> 検査機が成果物になったというのは意外でしたが、よく考えれば検査の難易度が上がるのだから正しい。

事故ではなく**構造的な必然**である。成果物がコードでない → 検査が難しい → 検査器を作る必要が出る →
検査器はコードなので成果物と同種になる → 被検証者の書き込み対象に入る。
コーディングで見えなかったのは、検査器（テスト実行）が既製品だったからにすぎない。

**対策の方向（師匠）**: 検査器の実装を**独立したコーディングタスク**として先に実行し、
**確定後に保護**してから本タスクを走らせる。
