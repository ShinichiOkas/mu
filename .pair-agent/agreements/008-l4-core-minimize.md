## 診断 — 何がコアを膨らませているか

`mu/l4.py` は **827行**。うち**プロンプト定数とスキーマで約250行**を占め、層の骨格
（決定論のループと分岐）がデータに埋もれている。

外出しの基準は [[externalize-only-what-varies-by-use]]（師匠の宣言・confirmed）:
**用途によって変動する値は外へ、システムが稼働するための普遍の値はコアに残す。**

| 中身 | 用途で変動するか | 判定（案） |
|---|---|---|
| `_SPECIFY_SYSTEM` / `_RESPECIFY_SYSTEM`（PdM のプロンプト） | する | **外** |
| `_PROCESS_SYSTEM` / `_DECIDE_SYSTEM`（PjM のプロンプト） | する | **外** |
| `_SPECIFY_SCHEMA` / `_PROCESS_SCHEMA` / `_DECIDE_SCHEMA` | しない（**コードの分岐が依存**: `feasible=false`→escalate、`action` の enum、task の必須キー） | **中** |
| `_DEFAULT_QA_TASK` | 構造は普遍（検証を飛ばさせない床）／文面は変動 | 未決2 |
| `_write_spec` / `_write_process`（artifact の書式） | 人間向け表示は変動しうる／file grounding の背骨でもある | 未決2 |
| 実行ループ・部分再実行・権限適用・verdict の機械読み | しない | **中** |

### 非対称の発見

**PdM と PjM も役割なのに `roles/` に居ない。** アーキテクト・実装者・QA だけが定義書を持ち、
PdM/PjM はコード内定数として特別扱いされている。006 で「role 定義は PjM に渡すナレッジベース」と
決めたのに、PjM 自身の定義だけが外に出ていない。ここを揃えると、L4 のコードは
**「役割定義を読んで着せ、決定論の床を回すだけ」**（＝師匠のイメージ）になる。

## 決めたこと（暫定）

1. **データを外に出すのは構造の分割ではない**（[[one-file-per-layer]] と衝突しない）。
   ただし外に出すのは**用途で変動する値だけ**。
2. スコープは L4 のミニマイズに絞る。**並列実行・リスク領域・証拠デッドロックは本スプリント外**。
3. 挙動は変えない。**外出しの前後で受入（007 の実走セット）が同じ結果を出すこと**を条件にする。

## 未決の解消（2026-08-04 師匠の判断）

1. **PdM / PjM も `roles/` に出す。切り分けは「位置は不変・中身は変動」。** 師匠:

   > その場所にいるのがPdM、PjMであることは間違いないでしょう。そこは不変ですが、どのような
   > PjM/PdMであるかは変動要素だと考えていますが何かおかしいですか？コアとしてはPdMであることは
   > 認識しているがやり方の指示もスキルもない状態ということになるかと思います。

   - **コアが持つのは「そこに PdM/PjM が居る」という配置・順序と、そのポジションの契約
     （＝スキーマ）と、決定論の床**。やり方・知識・規範は外。
   - これは architect / implementer / QA で既に成立している形であり、**PdM/PjM だけが例外だった**。
   - **帰結（重要）**: 「やり方の指示もスキルもない状態」を**本物の状態として許す**必要がある。
     定義書が無いときに既定プロンプトへフォールバックしてはならない——変動する値がコアに戻るため。
     AI が当初挙げた選択肢 (c)「フォールバックをコードに残す」は**この基準では不可**であり撤回する。
   - 採る形: **既定パス `roles/` から読む。無ければ「指示なしの役割」として動き、その事実をログに出す**
     （スキーマは残るので出力の形は保たれ、質だけが落ちる。静かに劣化させない ←
     [[silent-degradation-must-be-logged]]）。
   - **空の役割は失敗してよい**（2026-08-04 師匠）:

     > 役割定義所〔書〕が無い状態の空のPjM,PdMやアーキテクトなどは多くの場合プロジェクトに
     > 失敗する結果になるはずですが、それで正常だという考え方です。

     → [[empty-knowledge-failure-is-correct]]（confirmed）。この状態を安全網で埋めない。
     さらに**知識を抜いた走は対照実験として使える**——外に出した知識が効いていることの実証になる
     （受入への反映は未決5）。

2. **ミニマム定義はコードに残し、定義書で拡張または上書き可能にする**（師匠）。
   `_DEFAULT_QA_TASK` も artifact の書式も、**床が成立するための最小形**をコードが持ち、
   外の定義書がそれを拡張・上書きできる。①との関係: ①は**やり方（知識）**の話でフォールバック禁止、
   ②は**床そのものの最小形**の話であり、最小形は不変だから中に残る。
   - *解釈は師匠が承認（2026-08-04）*:「役割を認識しているが知識が無い状態がミニマム」。
     上書きできるのは文面・criterion・check・人選まで。
     **「プロセス末尾に QA タスクが存在すること」自体は上書き不可**とする（決定論の床。
     定義書から検証を消せると、偽・完遂の経路がデータ側から再び開く）。
3. **プロンプト（外）とスキーマ（中）の整合 = (a)+(b)**（師匠）。役割定義書に JSON の形を
   書かせず**スキーマを唯一の出所**とし、コードが「返すべき形」の1行を生成してプロンプトへ足す。
   整合はテストで固定する。①の切り分けと整合（契約はポジション側＝コアの持ち物）。
4. **達成の判定に行数目標を置かない**（師匠）。「**コアに残ったものがすべて『不変』と
   説明できること**」を条件とし、仕分けの一覧を記録に残す。
5. **比較実走は中間案**（師匠）: H3×1（feasible 分岐）＋正常系2件（通常経路）＋
   **`roles/` を空にした対照走1本**。f1×12b（3.5時間）は省略——権限機構は 007 で実走確認済みで、
   今回見るのは「移動が壊していないか」だから。

## 先に規定した失敗点（既知リスク）

- **コアの空洞化**: 出しすぎると「どこで何が決まるか」が読めなくなる。特にプロンプトは
  層の意味論そのものを含むため、外に出した瞬間に層の docstring が嘘になりやすい
  （[[mechanism-change-updates-layer-docs]] を完了条件に入れる）。
- **役割定義書の肥大**: PdM/PjM のプロンプトは長い。`roles/*.md` が「ナレッジベース＋権限宣言＋
  生命線プロンプト」の3役を負う形になり、ファイルの責務が曖昧になる恐れ。
- **リグレッションの見えにくさ**: プロンプトを移すだけでも改行や順序が変われば挙動が変わる
  （LLM は入力の些細な差に反応する）。ユニットテストは通っても実走が劣化しうる。
- **007 で入れたばかりの機構を触る**: `feasible` の分岐・権限適用・入力接地はまだ実走の実績が
  1セットしかない。移動の巻き添えで壊すと発見が遅れる。
