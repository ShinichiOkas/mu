created: 2026-08-12

## 背景

mu には role の概念はあるが skill の概念が無い。師匠の問い（2026-08-12）:
「role は skill の上位概念とも捉えられる。導入するならどのレイヤーで、role との関係をどうするか」。

**痛みは既に実在する。** `roles/` を全ハッシュした実測（20ファイル / 1390行）:

| 定義書 | 実態 |
|---|---|
| `implementer.md` | **5パッケージ全部バイト同一**（27行 × 5） |
| `qa.md` | coding / book / secretary が同一。research・rnd が各1ブロック追加 |
| `pdm.md` | coding / book が同一。research / rnd / secretary が各差分 |
| `pjm.md` | 5つとも別。ただし diff は8割方が同一文面（人選指示の段落だけが違う） |

つまり現状の `roles/` は「**共通の対策集＋ドメイン差分**」の手動コピーである。
役割定義書がいま性質の違う2つを混ぜて運んでいることが原因:

- **ポジションの不変**（職掌・継ぎ目・権限・人選指示）— パッケージごとに少数
- **やり方の対策文**（入力ファイルは読み取り専用／検査器を自分の成果物に合わせない／
  文書成果物は judge で自己検査）— 仕事ごとに多数、ドメインを跨いで効く

後者が増えるほどパッケージの複製が膨らむ。これが埋めるべき落差。

**目的は3つ、うち今回は①②**（師匠 2026-08-12）:

1. 重複の解消（いまの痛み）
2. **ユーザー側のやり方・個々のプロジェクト方針の記述**——師匠「重要な要素」
3. 自己成長の器（pair-agent と同型。mu の目標が自律型エージェントである以上、
   自己成長の仕組みは必要）——**今回は作らない。塞がないだけ**

## 設計（師匠承認 2026-08-12）

### 1. skill は層ではない

層は「1つの落差を埋め、内側を D として使い judgment を足す」もの。skill が足すのは
判断ではなく**知識**であり、知識の居場所は既にある（README「データは層の外、facility が供給」）。
よって追加は **データ `skills/*.md` ＋ facility `mu/skill_kb.py`** の2つだけ。
装着点は既存の1行——[`mu/l4.py`](../../mu/l4.py) の `task_system` 合成。

知識の注入経路は既に2本ある（`system`＝呼び出し側 / `role_prompt`＝ポジション）。
skill の導入とは新経路を掘ることではなく、**この2経路に名前で参照できる単位を与える**こと。

### 2. 宛先は skill の側が名乗る（`applies_to`）— 一方向に一本化

②のために role 側宣言（`skills:` を役割定義書に書く）は**成立しない**:

- `roles/<pkg>/*.md` はリポジトリの共有資産であり、個々のプロジェクトが書き換える対象ではない
- 028 で L5 がパッケージを自選する以上、プロジェクト作者は role 名を確定できない

よって skill が「誰のためのスキルか」を明示する（師匠の理解を採用）。副産物として:

- ①も同じ機構で解ける（機構は1つ）
- **役割定義書への追記がゼロ。移行は削除だけ**——実走で調整された文面を触らずに済む
- 逆引き（この役割は何を装備しているか）は `staffing_lines` と同型の表示関数で構造的に保証する

`applies_to` に書けるのは**ポジション名**が基本。パッケージが自動選択されても名前が動かないのは
4ポジション（pdm / pjm / qa / implementer）契約だけだからである。ドメイン役割名も書けるが、
当たらなければ**ログに出して落とす**（エラーにしない——「知識が無い状態で動く」が正常）。

- `applies_to: all` を**明示形として用意**する（師匠指定）。**省略も同義**（既定＝全タスク）
- ただし**表示とログは常に `all` に正規化**して出す——省略で書かれたものが人間から
  見えなくなるのを防ぐ（025「構成と表示の一致を構造で保証する」の型）

### 3. skill は権限を持たない（絶対ルール・師匠確定）

宣言だけでは規範文の域で確率的にしか効かない。**コードで担保する**:

- frontmatter はホワイトリスト（`description` / `applies_to` / `maturity` ＋自由キー）
- `tools:` / `write_scope:` が書かれていたら**名指しでエラーにして落とす**
  （静かに無視しない——書いた人には効いているように見えてしまう）

これで「LLM が出せるのは役割名だけ → 権限を LLM 側から書き換えられない」（合意007 B1）の床が、
skill 導入後も破れない。権限を宣言できるのは role だけ。

### 4. `maturity: confirmed` だけが装着される

`draft` は載らない。育成中の文を誤って走りに載せない門であり、③が来たときの接続点でもある。
**系が提案できるのは draft まで、confirmed への昇格は人間**——026「verified への昇格は
師匠の承認事項」と同型の非対称を最初から入れる。

### 5. ③を塞がない方法＝欄を契約にしない

`parse_role_doc` は既に「未知のキーは文字列のまま持ち回る」設計（[`mu/role_kb.py`](../../mu/role_kb.py)）。
skill パーサも同じにする。すると `origin:` `evidence:` `proposed_by:` を**後から契約変更なしに**
足せる。③のために今やることは maturity の門1つだけで、欄の作り込みはしない。

### 6. 出所は呼び出し側が規定（`MU_SKILLS_DIR`）

`roles_paths()` の隣に `skills_paths()`。既定は同梱の `skills/`、カンマ区切りで合成可
（プロジェクト方針を足すときは `MU_SKILLS_DIR=skills,./.mu/skills`）。roles と同一の意味論に揃える
——特別扱いを作らない。同名衝突は両出所を名指しするエラー（025 と同型）。

## スコープ（フェーズ＝コミット単位）

1. **A — 機構（TDD）**: `mu/skill_kb.py`（`load_skills` / `parse_skill_doc` / `applies_to` 解決 /

2. **B — ①の移行＋表面**: `roles/*/implementer.md` の本文を `skills/` へ分解（**削るだけ**。

   起動表示・README 明文化。
3. **C — ②の実例＋検証・クローズ**: プロジェクト側 skill を1本置いて e2e で効くことを確認・

## 実行中に採る判断（AI の判断。事後確認対象）

- **分解の粒度**: `implementer.md` の本文は箇条書き6項目。意味の切れ目＝箇条書き単位で
  5〜6本の skill に割る（近接する検査器2項目は統合の可能性あり）。**文言は変えない**。
- **合成順序**: `role_prompt → skills → task_contract → system`。契約と環境は後ろに残す
  （契約は L3 の再計画で薄まらない経路として 019 で確立済み。順序を動かさない）。
- **本文に frontmatter を含めない**（role と同じ。`parse_role_doc` と同型）。
- 装着ログのイベント: `("skills", role, [names], 総文字数)`——小型モデルでは装着量が
  そのまま劣化要因なので、合成点で観測に出す（`observability-at-composition-seams`）。
- `MU_SKILLS_DIR` 未指定でも既定 `skills/` をロードする。移行後は implementer の知識が
  そこにあるため、ロードしなければ知識が消える（既定の変更ではなく移行の必然）。

*[フェーズ A 実行時に追加。事後確認対象]*

- **装着点は `task_system` だけでなく `lifeline_system` にも置いた**（＝`mu/l5.py` にも触れた）。
  設計上 `applies_to` の宛先は「名前が動かない4ポジション」であり、そこに pdm / pjm が
  含まれる以上、生命線側に着せなければ `applies_to: pdm`（目的②の代表例——この案件の
  仕様はこう書く）が空手形になる。起草時の「装着点は1行」より touch surface が広い。
- **maturity の門は opt-out**（省略＝`confirmed`＝装着される）。②のプロジェクト方針を
  書く人に maturity の作法を強いないため。育成中のものは書き手が `draft` と明示する。
  ③を作るときは「系が書き戻す skill は必ず `draft` を明示する」が書き手側の契約になる。
- `skills` 引数はすべて省略可（既定 `{}`）。装備ゼロなら合成結果は 029 以前と1文字も
  変わらない（テストで固定）——既存の測定基準を動かさないため。

## AIの懸念

> [2026-08-12] severity: medium
> **026「パッケージ自己完結・ドメイン間の干渉ゼロ」を部分的に巻き戻す。**
> 和解条件を床として置く: **skill に上げてよいのは、複数ドメインで同一文面のまま
> 使われていることが実測で確認できた文だけ。ドメイン差分がある文は role 定義書に残す。**
> ただし今回対象の `implementer.md` の同一性は**コピー由来であって中立性の実証ではない**
> （secretary の pjm.md は implementer を検査ツール作成に限定しており、起動機会が少ない）。
> 「5パッケージで調整の必要が観測されなかった」という弱い証拠に留まることを記録しておく。

> [2026-08-12] severity: low
> **完全な no-op は保証できない。** 役割定義書の途中にあった文が合成後は後ろのブロックへ
> 移るため、文言が同一でも順序が変わる。「無変更のはず」ではなく**再測定**として扱う
> （順序変化のみを diff で確認 → coding スモーク）。

> [2026-08-12] severity: low
> **`applies_to` 省略＝全体が増えると全タスクの context を食う。** 小型モデル
> （gemma4:12b / qwen3.5:9b）では劣化要因になる。上限は設けない（合意010 の思想）が、
> 装着量は必ず観測に出す。
