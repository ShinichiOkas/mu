## なぜこれが要るか — 最後の1箇所だけ原則が破られている

合意007 で「**判断は structured output で申告させ、分岐はコードに置く**」を確立し、
それが偽・完遂を潰す決め手になった。ところが**完遂判定だけは LLM の総合判断**
（`ACHIEVED: yes|no|uncertain`）に委ねたままである。総合判断はスカラー的で、
まさに LLM が苦手な形——実走でそこが壊れている:

- **012**: 決定論 check が 3件中2件 NG なのに、QA は `ACHIEVED: yes` と書いた
- **015**: judge の FAIL を受けて `no` になったが、それは QA の裁量次第だった（`yes` とも書けた）

「全体としてどうか」を聞かれると LLM は寛容側に倒れる（部分的な達成を加点する）。
項目ごとに「**この項目の証拠は成果物の中にあるか**」に還元すれば、
judge の設計（逐語引用を要求・既定は fail）と噛み合う。

### 現状にある部品と、足りないもの

| 要素 | 現状 |
|---|---|
| 完成を複数項目で定義 | **ある**（PdM の `criteria`）。ただし論理的な粒度はまちまち |
| 項目ごとの二値判定 | **judge は既に3値**（pass/fail/uncertain）。だが QA が総合値に潰している |
| 全項目 PASS で完成 | **無い**。集約が QA の主観的総合判断 |
| 集約をコードで | **無い**。`verdict["achieved"] == "yes"` を読むだけ |

足りないのは「**項目ごとの判定を集めて、集約はコードがやる**」の一点。

## 師匠の決定（2026-08-07 協議）

| 論点 | 決定 |
|---|---|
| ① 判定の集め方 | **QA が項目表を書き、コードが集約する**。QA が各項目を（必要なら judge を使って）判定し、判定書に PASS/FAIL の表を書く。**総合判断は QA から取り上げる** |
| ② `uncertain` の扱い | **PASS でなければ未達**。「10個なら10個 PASS」の論理に忠実。ただし理由表示では「判定不能」と「FAIL」を区別する |
| ③ 集約規則 | **全項目 PASS のみ完成**。部分達成を完成と呼ばない |

## 設計

### A. 判定書の契約を「項目表」に変える

現行（`process._VERDICT_CONTRACT`）:

```
ACHIEVED: yes|no|uncertain
REASON: ...
GAP: ...
```

新（**項目ごとに1行**。行の形は機械が読む）:

```
ITEM: <受入基準のテキスト> | PASS|FAIL|UNCERTAIN | <根拠。成果物からの引用か、実行した検査>
...（受入基準の数だけ）
GAP: <PASS でない項目について、何が欠けているか>
```

- **`ACHIEVED` 行は書かせない**。総合判断は LLM の仕事ではなくなる
- 項目は**受入基準（SPEC の criteria）と1対1**にする。新しい概念を増やさない
- 根拠を必須にする（judge と同じ思想——**証拠が無いことを合格にしない**）

### B. 集約はコードが行う（`read_verdict` の書き換え）

- 判定書から項目行を読み、**受入基準の全項目が PASS のときだけ達成**とする
- 項目が欠けている（判定書に現れない受入基準がある）場合は**その項目を UNCERTAIN 扱い**にする——
  黙って落とさない
- 返り値に**項目別の内訳**を含める（実況と結果に出す）。どの項目で落ちたかが人間に見える
- 既存の `achieved` キーは互換のため残す（コードが集約した結果を入れる）

### C. 決定論 check との関係

**床は床のまま。** `_run_criteria_checks`（機械検査）は今までどおり独立に走り、
`failed_checks` があれば未達。今回変えるのは**QA 側の判定の集め方**だけである。

同じ受入基準が「機械検査でも見られ、QA でも見られる」状態になるが、それは重複ではなく
**二重化**である（合意016 の二層構造と同じ考え方）。

### D. PdM への影響

「完成を論理的に定義する」は PdM の仕事である。`roles/pdm.md` に足す:

- 各受入基準は**独立に真偽が判定できる命題**にする。複数の条件を1項目に束ねない
  （「4ツールを比較し、出典を付け、結論を書くこと」は**3項目**に割る）
- 項目数を절約しない。10 個必要なら 10 個書く

## やらないこと

- 決定論 check の変更（床は動かさない）
- judge の変更（既に二値＋不明で、この設計に合っている）
- 必須項目／任意項目の区別 — ③の決定（全項目必須）。甲乙をつけさせると判断が LLM に戻る

## 進め方（TDD）

| Phase | 内容 | 完了条件 |
|---|---|---|
| 1 | `read_verdict` の項目表読み取り＋集約のテストを先に書く | 新テストが失敗する（既存 230 green） |
| 2 | 契約（`_VERDICT_CONTRACT`）と `read_verdict` の実装 | 全項目 PASS でのみ達成・欠けた項目は UNCERTAIN 扱い |
| 3 | 実況と結果に項目別の内訳を出す／`roles/pdm.md`・`qa.md` の更新 | どの項目で落ちたかが見える |
| 4 | 実走（リサーチ＋コーディング回帰） | 判定が項目単位で出ること・偽の達成が減るか観測 |

## 完了条件

- 完遂判定が**コードによる全項目 PASS の集約**になっている（LLM の総合判断を経由しない）
- どの項目で落ちたかが実況・結果・判定書のすべてで見える
- 既存 230 テスト＋新テストが green
- 実走で、判定が項目単位で出ることを確認している
