## 背景

並列化の協議（2026-08-12）から。師匠の方針:

> 並列化の目的は速度です。待たずにできることはやっておくというスタンス。
> 今はローカルだがローカルで運用し続けることは前提じゃない。
> needsを足すのはいずれにせよ必要では？Inputが暗黙というのはよろしくないだろう。

現状、task が宣言するのは出力（`file`）だけで、入力は暗黙——**PjM の並び順**と
**言及ベースの推定**（`invalidate` の文字列一致）に寄りかかっている。推定は「依存が有る」しか
言えず「依存が無い」の保証が出ないため、そのまま並列判定に使うと推定の漏れがレース
（再現しない壊れ方）になり、**壊れた判断が安全側に落ちない**。013 の依存逆流（検査器の
巻き込み再生成）もこの暗黙さが根。

並列実行そのものは次スプリントに分け、本スプリントは**依存グラフの明示化と作業空間の分離を
逐次のまま入れて、グラフが正しいことを実走で実証する**。逆順（並列を先に入れてグラフを直し
ながら走る）はグラフの誤りとレースが混ざって切り分けられない。

## 設計（師匠確定 2026-08-12）

### 1. needs — 入力の宣言（複数・外部ファイルも含む）

    task = {role, task, file, criterion, needs?, check?, model?}   ← 006 の型: スキーマ拡張だけ

- needs には**そのタスクが読むファイルを全部**書く: 先行タスクの出力＋外部入力（実在ファイル）。
  SPEC は全タスク共通なのでコードが常に供給する（宣言不要）。
- 改稿チェーン（027「同一原稿の連続的修正」）では自分の出力ファイル自身も needs に入る
  （前版を読むため）。先行の産出タスクが居れば正当。

### 2. needs の意味論はゲート（師匠の定式化）

「needs が正」という優先順位ではなく、**「needs が満たせなければタスクは実行できない」**という
実行条件。ゲートは存在で判定する（Make と同じ）: 需要ファイルが共有空間に実在するか。
満たせなければタスクは正直に失敗し、PjM の decide（rerun / replan）に乗る。
実行順序は引き続き PjM の並び（本スプリントでは並べ替えない。並べ替えは次スプリントの
スケジューラの仕事で、同じゲート述語を dispatch 条件として使う）。

### 3. 読み取りゲート（(ii)）— 作業空間の分離で構造的に閉じる

師匠の宣言:

> ロールごとにディレクトリを分ける方向が筋だろう。入出力ファイルは共有空間に置く、
> 作業ファイルは個別ディレクトリに置く。入力ファイルは複数ロールで共有してもよいが、
> 出力ファイルは複数ロールで共有してはいけない。つまり書き込みができるロールは1に固定。

機構は **copy-in / publish-out**:

- タスク開始時、コードが needs＋SPEC をそのタスクの**作業区画（tray）へ写す**（スナップショット）
- タスクのツールは tray に閉じる（read/write/list/exec の相対パスは tray 起点。tray 外への
  パスはコードが拒否——`_own_file_only` と同じ包みの型）
- 完了時、コードが `file` を共有空間へ**発行**する。失敗したタスクは発行しない
  （半端な成果物が共有空間に出ない）

未宣言の依存は「静かなレース」ではなく**そのタスクの可視な失敗**（tray に無いから読めない）に
変わる——**依存グラフが構成的に真**になる。これが並列安全の根拠。
`execute_command` の絶対パス逃げは塞げない破れとして残る（入力保護と同じ扱い: 防止ではなく
検出——protect/guard は原本＝共有空間側を見張っており、tray 写しへの変更は原本に届かない。
副産物として入力保護が構造で強くなる）。

### 4. 言及ベースの推定は lint に降格（③の結論）

グラフの真実の出所は needs の1つ。無効化伝播（`invalidate`）は**宣言された needs 辺だけ**を
走る（tray のもとでは未宣言の入力は読めないので、needs に無い依存は構造的に存在できない）。
言及推定は**計画時 lint**として残す:「タスク3は design.md に言及しているが needs に無い——
実行時に読めない」を実行前に可視化する（エラーにしない。起動表示・ログで名指し）。
013 型の「出所が2つで食い違う」は構造から消える。

### 5. single-writer はコードが適用する

出力ファイルの書き手は1ロールに固定（師匠宣言）。所有権は宣言から決定論で導出する
（file → その file を出力する最初のタスクの role）。**発行ゲートで適用**: 別ロールのタスクが
同じファイルを発行しようとしたらコードが拒否し、タスクは可視に失敗して PjM に乗る。
計画時 lint でも名指しする。同ロール内の改稿チェーン（複数タスクが同じファイルを列挙順に
書く）は正当。QA の write_scope=own はこの一般形の先行特例だった、という位置づけになる。

### 6. 決定論の床（この層に足すもの）

- QA タスクの needs はコードが必ず供給する（全非 QA タスクの出力。検証者が実物を見られない
  プロセスを作れない）
- needs の意味論（書かなければ見えない）は skill（`applies_to: pjm`）で PjM に装備する
  ——5パッケージの pjm.md への手動コピーはしない（029 の機構をそのまま使う）

## 実行中に採る判断（AI の判断。事後確認対象）

- **tray は role 配下にタスク単位で切る**（`<work>/<role>/task-N/`）。role 単位の共有 scratch は
  タスク間の隠れ結合（宣言外の依存）を許してしまい、せっかく閉じたグラフが scratch 経由で
  破れる。同 role の fan-out（幅）も B スプリントでそのまま並列にできる。役割ごとの机の中に
  タスクごとのトレー、という形。
- tray の実装は per-task のツール包み（closure）で行い、プロセス cwd は動かさない
  （`os.chdir` の大域状態を避ける。並列化がそのまま載る形）。
- needs 向け PjM skill は `maturity: confirmed` で置く（装備されないと機構が空手形になる）。

*[フェーズ B/C 実行時に追加。事後確認対象]*

- **`read_file` はシステム一時ディレクトリ「直下」だけ tray の外でも読める。**
  `execute_command` の長い出力は temp 直下に全文保存され read_file で辿る契約（合意010
  「見えない部分を残さない」）であり、完全に閉じると観測が死ぬ。直下限定なのは、
  temp 配下の他の作業領域（pytest の tmp 等）まで開けないため。書き込みは tray のみ。
- **single-writer の強制は発行ゲート、計画時は lint。** 所有者＝そのファイルを最初に産出する
  タスクのロール（宣言からの決定論・状態なし）。計画時に落とさないのは「壊れた判断は
  安全側へ落ちる」の型——エラーで走を殺すより、実行時の正直な失敗として PjM の decide に
  乗せる方が回復経路がある。
- **`workspace` は L4 の注入引数（guard / deadline / protected と同じ型）、CLI の既定は ON**
  （`MU_WORKSPACE` 無指定＝cwd の `.mu-work/`。`off` で従来どおり）。隔離の床は走らせた人が
  何もしなくても立ち、無効化したことは起動表示に出る。
- 前回試行の残骸対策: tray はタスク再実行で再利用するが、**宣言された出力だけは実行前に消す**
  （残骸の発行を防ぐ。scratch は観測のために残す）。
- 実行ゲートの内部依存は「産出タスクの done」で判定し、外部ファイルだけ実在で判定する
  （Make の target / source と同じ区別。鮮度の判断は PjM=invalidate の領分のまま）。
