## ゴール

**L3 = 複数タスクからなる複雑なタスクを最後まで完遂する仕組み。** L2 に渡せる"単位の仕事"を組み合わせて全体目標を達成する。L2 で暗黙だった **大域的 Plan が必須**になる。

- **L2 まで**（確認済み・祖語なし）= **単一の checkable なゴール**を Do＋Reflect で達成まで回す。大域計画は持たない。
- **L3** = その L2 を"単位"として組み合わせ、複雑ゴールを完遂する。

## 構造 — PDCA が完全体で現れる層

| | 中身 | 自律/HITL | 生命線プロンプト |
|---|---|---|---|
| **P** | 複雑ゴールを「ファイルを生む checkable な単位」へ分解 | **HITL**（人間 or L4 が承認） | **Plan プロンプト** |
| **D** | 各単位を **L2** が完遂 → 成果物ファイル | 自律 | （L2 に委譲） |
| **C** | 成果物ファイルを確認／L2 の失敗を検知 | 自律 | （ファイル確認＋L2結果） |
| **A** | **再計画**（条件/アプローチ/計画の変更） | **HITL**（人間 or L4 が承認） | **失敗分析プロンプト** |

- **L3 の D は L2**（再帰同一構造）。自律性が外へ一枚上がり、**P が明示・必須**に。
- **判断は外へ、実行は内で**: D・C は自律、P・A（判断）は上位に上げる半自律層。

## ファイル・グラウンディング（L3 の背骨）

**すべての単位は"成果物ファイル"を生む。** これが2つを同時に解く:
- ファイル＋基準が **単位を checkable にする**（L2 が達成＆検証できる）
- ファイルが **次の単位への文脈**になる（単位間はファイルを介してつながる）

→ 「成果物をファイルに入れて確認する」ループが L3 の背骨。

## 単位の形

`(task, 出力ファイル, checkable基準)`。
- **コードの単位**: 基準＝**テストをパス**。テストコード自体が**別の L2 単位**として先に作られる → **L3 が TDD をオーケストレーションする**（confirmed skill `process-tdd` が L3 の構造に現れる）。L2 のテスト実行は既存 `execute_command` で足りる。複雑さは"Plan の依存関係"に集約。
- **最終成果物は複数 OK**（L2 に十分な知性がある）。

## HITL 承認スロット

- 最初の Plan と、再計画の Act は **上位（人間 or L4）に承認を仰ぐ**。
- **承認者は呼び出し側が差し込むスロット**（L2 の「上限は呼び出し側が規定」と同じ思想）。今は人間（`l3_chat`）、将来は L4。再帰の底（人間）が「plan の承認者」として具体化しただけ。

## 最小の L3 の形（たたき台）

```
L3.run(複雑ゴール, tools, approve, 上限):     # approve = 承認スロット（人間/L4）
  plan = Plan(複雑ゴール)                      # P: 分解案（各単位=task/出力ファイル/基準）
  approve(plan)  ← HITL
  loop（上限まで）:
    次の未完単位 → L2 で完遂（→ 成果物ファイル）  # D（コードなら基準=テストパス）
    成功→完了 / 失敗→失敗分析                    # C
    Reflect(全体): 複雑ゴール達成？
       達成 → 終了
       未達 → replan案 → approve(replan) ← HITL  # A（条件/アプローチ/計画の変更）
```

## 到達目標（北極星）

**「GUI を持つ関数電卓アプリ」を自走で最後まで完成できること。**

- 選定理由: 1つのアプリの中に L3 の**スイートスポットと限界**を同時に含む。
  - **電卓ロジック**（四則・関数・優先順位）= ◎ 完全にテスト可能 → 自律で回る（TDD の理想形）
  - **GUI**（ボタン・表示・イベント）= ✕ 自動検証が困難 → **L3 の構造的な崖**。しかもここが **HITL 境界**（GUI 受け入れは人間/L4 に上げる）
- **切り分け**: 限界が「①L3 構造の限界」か「②モデル能力の限界」かを混同しない。**2モデル**（qwen3.5:9b / gemma4:12b）で切り分ける（[[multi-model-reference-avoid-overfit]]）。

## 進め方（内側から、の流儀）

1. まず **GUI 無しの複合タスク**（例: 電卓ロジックを `calc.py` に実装＋`test_calc.py` でテストパス = 2〜3単位）で **L3 の機構を検証**。
2. 次に **GUI を足して** auto/HITL 境界を実地観測。

## 先に規定した失敗点

- **GUI は auto-checkable でない** → HITL 受け入れ（設計と整合）。
- **HITL の粒度** — 再計画のたび毎回承認は煩い。初期 Plan＋"重要な"再計画だけ上げる線引きが要りそう。
- **Plan プロンプト / 失敗分析プロンプト** が L3 の2大生命線（実タスクで詰める）。
- **依存関係を持つ Plan の表現**（テスト単位→実装単位 の順序・参照）。
- **再計画の暴走** → 各層ハード上限（呼び出し側規定）＋人間。

## 進め方（確定ルール準拠）

- 1層=1ファイル `mu/l3.py` ／ `l3_chat.py` を用意 ／ 内側から一層ずつ完成 ／ TDD・実タスクで生命線プロンプトを詰める。
