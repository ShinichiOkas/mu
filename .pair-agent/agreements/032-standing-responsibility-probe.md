北極星の再設定の協議（2026-08-13）で4候補を提示し、師匠は **候補C（継続する責務）** を選択:

**候補C は新しい北極星として据える**（前の北極星「GUI を持つアプリの自走完遂」は
2026-07-19 到達済み）。本スプリントはその**最初の観測**であり、到達を目指す走ではない。

候補C の構造の主張:

> 一回の目的ではなく「**この状態を保て**」という立ち続ける責任を渡され、mu が自分で
> 「いま何をすべきか」を目的として生成し、**複数の走を跨いで**責任を果たす。
> 埋める落差は「**目的は都度来る ↔ 人が本当に渡したいのは任せた範囲そのもの**」。

## このスプリントで**やらないこと**を先に書く

**L6 を実装しない。** 機構を足す前に既存構造の役割かを問う（confirmed スキル
[[ask-existing-structure-before-adding-mechanism]]）。継続責務を現行の L0〜L5 に渡して
**どこまで行けて何が足りないか**を実物で見るまで、L6 の落差は言語化できない。
029 で確立した型（構成は設計から／規範文は失敗から）とも整合する——L6 の**構成**を
設計するには、まず落差の実物が要る。

このスプリントの成果物は**動く L6 ではなく、L6 の落差の言語化と実走の証跡**である。

## 設計

### 1. L6 の代役はスクリプト（＝いま人間が立っている位置）

各ラウンドで**同じ継続責務の原文**を purpose として L5 に渡すだけ。「いま何をすべきか」の
判断は mu に委ねる——そこが観測点。スクリプトがやるのは (a) 状態の注入 (b) 呼び出し
(c) 事実の記録だけで、判断は一切持たない。

### 2. 題材は **mu 自身の使い捨てクローン**（師匠の判断 2026-08-13）

継続責務は「**この作業ディレクトリの README.md を実装と一致させ続けよ**」。
対象は mu の実物——ミニチュアではなく、33KB の README と 3,500 行の実装が相手になる。

**使い捨てクローン**を作業ディレクトリにする（リポジトリ本体には触れさせない）:

- 複製するのは `mu/` `roles/` `skills/` `tests/` `docs/` ＋ ルートの `*.py` `*.md` `*.toml`（約2MB）
- **除外**: `runs/`（23MB）・`.venv/`・`.git/`・`__pycache__`。runs/ を外す理由は容量だけでなく、
  **実リポジトリの絶対パスを含む唯一の追跡ファイル群**だから——確認済み（`git grep` で
  runs/ 以外のヒットゼロ）。絶対パスでの作業ディレクトリ外書き込みの実例が既にある
  （LONGTERM_TODO のセーフティ検討項目）ので、手掛かりごと落とす
- クローンはリポジトリの外（セッションの一時領域）に置く。走行ログと成果物だけを
  `runs/2026-08-13-032/` に回収する

### 3. ラウンド構成（4周）

| 周 | 注入するドリフト | 期待する挙動 | 観測したいこと |
|---|---|---|---|
| R0 | なし（一致している） | **何もしない** | 「やることが無い」を申告できるか。過剰行動しないか |
| R1 | **追加**方向（README の主張が過小になる） | 検知して追記 | 差分を特定できるか |
| R2 | **削除**方向（README が実在しないものを語る） | 検知して削除 | 消す方向も見るか（足す方向より難しい） |
| R3 | なし（R2 の修正後） | **何もしない** | 直した後に止まれるか |

**R0 と R3 の「何もしない」が主デリバラブル。** 継続責務の難しさは
「**動くべきときだけ動く**」ことであり、過剰行動しない証明が要る。

ドリフトの実体はフェーズ A で確定する。条件は2つ——**README が実際に主張していること**を
嘘にすること、そして**テスト群を壊さない**こと（壊すと mu がテストを直しにいき、
継続責務の観測が濁る）。候補は README の機械検査できる主張（skill 件数と宛先・
パッケージ数と status・ツール一覧・環境変数・テスト数・probe の構成）。

### 4. 評価（実体に接地する）

- **一致**: README の機械検査できる主張と実装を突き合わせる**監査スクリプト**（観測者の持ち物。
  029/README 更新時に実際に使ったものを流用）。**mu には渡さない**——渡せば「何を検査すべきか」
  という最も難しい部分を肩代わりしてしまい、仮説2の検証にならない
- **検知**: R1 / R2 で正しい差分を指摘したか（SPEC.md・成果物・判定書を人間が読む）
- **無行動**: R0 / R3 で README のハッシュが不変か（機械検査）
- **走を跨ぐ状態**: 各周が前周を知らないことで何が起きるか（観測のみ）

### 5. 条件

- モデル: **`gemma4:31b-cloud` のみ**（QA も。追試2 で直列区間の揺れが1桁縮むことを実測済み）
- 役割パッケージ: `MU_ROLES_DIR=auto`（Director に選ばせる——「文書を実装に合わせる」が
  どのドメインと判定されるか自体が観測対象）
- 並列: 既定 1（このスプリントの観測対象ではない）
- 保護: 実装ファイルは `protect()` で内容不変を宣言（**直すべきは README の側**という
  非対称を床で立てる。実装を書き換えて「一致」させる退化解を潰す）

## 事前の仮説（観測で検証する。当たっても外れても記録する）

1. **L5 には「やることが無い」の語彙が無い**。判断は accept / respec / escalate の3つで、
   「責務は満たされているので何もしない」はどれでもない。R0 で何が起きるか
2. **「一致させ続けよ」は checkable でない**。PdM が操作的定義（公開関数の集合の一致）まで
   降ろせるか。降ろせなければ L6 以前に L5 の限界
3. **走を跨ぐ状態が無い**ので毎周ゼロから読み直す。責務の記憶が無いことの実害が出るか

これらが**そのまま L6 の落差の候補**になる。

## AIの懸念

> [2026-08-13] severity: medium

> 誤診になる——**現行の層に無いものを求めている**だけであり、それこそが L6 の落差の実体。
> 観測の書き方に注意する（[[failure-needs-analysis-not-blind-retry]]）。

> [2026-08-13] severity: medium

> 実装 3,500 行）。時間切れや「一部しか見ていない README 更新」が出たとき、それが
> 継続責務の落差なのか規模の問題なのかを、記録の側で切り分けて書く必要がある。
> 各周に時間予算を置き、時間切れは**部分結果つきの正常な申告**として扱う（合意018 ⑥）。
