# 合意 034 — no-op を L5 の第一級の結果にする

status: executing（2026-08-13 師匠承認。振り返りは 033 と合同で行う——師匠の選択(b)）
created: 2026-08-13

## 背景

032 の実測: 継続責務（「README を実装と一致させ続けよ」）を一致した状態で渡した4走とも、
mu は**必ず何かを作った**。skill に「差分がゼロなら成果は変更なし」と明記しても効かない。
理由は構造にある——**L5 の結果契約に「やる必要がない」という終端が無い**。
[[contracts-not-knowledge-define-outcome-kinds]]（契約に無い結果の種類は知識では作れない）。

師匠の整理（2026-08-13）で、これが **L6（学習）とも ループエンジニアリング（トリガーの機械）
とも別問題**であることが確定した:

> no-op の追加はループとは別問題じゃない？ …no-op 対応はすぐに入れて問題ないと思う。
> L6 の話ではないので。

## 何を作るか

L5 に**4つ目の終端**を足す。これは新機構ではなく、**既にある兄弟の対称形**である:

| 既存（合意007 C1-(d)） | 本スプリント |
|---|---|
| PdM が「**充足不能**」と申告 → 仕様を作らず人間へ | PdM が「**充足済み**」と申告 → 仕様を作らず正常終了 |
| `feasible: False` → `_stop_infeasible` | `satisfied: True` → `_stop_satisfied` |
| 結果: escalate（人間の判断が要る） | 結果: **`no_action`（正常。何もしないことが正解）** |

## 設計

### 1. 判断は**独立した1問**にする（bundle しない）

`_SPECIFY_SCHEMA` に `satisfied` 欄を足す形は採らない。033 B3 の実測がその理由:

| 形式 | 結果 |
|---|---|
| 生成タスクに yes/no を同梱（1判断で選ぶ） | 8/16・否定形の申告 0/32 |
| **独立した二値判定に分解** | **7/9**・否定形はコードが導出 |

**生成を求められた判断は生成に引かれる。** 「仕様を作れ」の中で「作らなくてよい」は選ばれない
——032 で実測済み。よって `specify` の**前に**、`{satisfied, evidence}` だけを返す
**独立した判断**を置く。

```
目的＋入力の実物（接地） → assess（satisfied?）
   satisfied=true  → SPEC を作らず no_action で返す（L4 を回さない）
   それ以外        → 従来どおり specify → L4 …
```

### 2. 決定論の床

- **証拠を要求する**: `satisfied=true` は**接地された入力からの引用**を伴わなければ無効
  （コードが空証拠を False に落とす）。QA の verdict と同じ思想——判定は実体に接地する
- **安全側は「進める」**: 欄の欠落・壊れた応答・空証拠はすべて `satisfied=False` に落ちる
  （`feasible` の「欠落・True はどちらも進める」と同型。**サボる側に倒れない**）
- **「何もしなかった」の根拠を必ず残す**: `SPEC.md` に「充足済みと判断した。根拠: …」を書く
  ——032 の協議で私が挙げた懸念（no-op は**静かな失敗**を生む）への床。
  握り潰せない分岐＋残る証跡にする（合意007 決定4 と同じ型）
- **結果契約で区別できる**: `no_action` は `done`（作って達成）とも `escalate` とも別の値。
  機械で判別できる＝計測にも使える

### 3. やり方は定義書（`roles/*/pdm.md` の `## assess` 節）

コードが供給するのは**位置と契約と床**だけ。「何をもって充足済みとするか」は定義書に書く
——節が無ければ知識ゼロで判断し、`role_doc_missing` で可視化される（既存の哲学のまま）。
初版は職掌レベル＋032/033 で実測済みの規律のみ:

- 目的が**状態への約束**（〜を保て・一致させ続けよ）でないなら、充足済みはまず有り得ない
  （作る仕事は作らないと終わらない）
- 充足済みと言うには、**目的が要求する状態を実際に観測した証拠**が要る。
  「たぶん大丈夫」「入力が見当たらない」は充足の証拠ではない
- 迷ったら `satisfied=false`。**間違って作るコストより、間違って何もしないコストが高い**
  （何もしない失敗は静かで、次の走まで気づかれない）

## スコープ（フェーズ＝コミット単位）

1. **A — 機構（TDD）**: `_ASSESS_SCHEMA`・`Director._assess`・`_stop_satisfied`・
   結果契約に `no_action`・床（空証拠→False／欠落→False／SPEC.md への根拠記録）。
   ユニットは FakeL0 で全経路（充足済み／証拠なし→進む／欠落→進む／通常経路は無変更）
2. **B — 表面と定義書**: 5パッケージの `pdm.md` に `## assess` 初版・CLI/probe の結果表示・
   README 明文化
3. **C — 実証**: (1) 032 の継続責務 R0（一致した状態）を再走し **no_action で止まるか**
   ——**これが主デリバラブル**（0/4 だったものが初めて成立するか）
   (2) coding スモーク1本（プロンプトを触るので confirmed スキル準拠）
   (3) 通常の目的で誤って no_action にならないことの確認

## 完了条件

- 一致した状態の継続責務で **`no_action` が出る**（出なければ**その事実**が成果——
  次の落差の在処が1つ絞れる）
- 通常の目的（空の作業ディレクトリ・作る仕事）では従来どおり動く（回帰）
- 空証拠・欠落・壊れた応答がすべて「進める」に落ちることがテストで固定されている
- 「何もしなかった」根拠が SPEC.md に残る
- coding スモーク合格・テスト全 green

## やらないこと（スコープ外）

- **責務の座**（責務＋観測 → 差分判定 → 目的生成）——別スプリント。本件は
  「**L5 が no_action を返せるようにする**」だけで、**誰が責務を持つか**には触れない
- **トリガー / ループエンジニアリング**——別スプリント
- L6（学習）——033 の設計どおり別軸
- 差分の自動測定（何をもって一致とするかの機械化）——判断は PdM に委ねる

## AIの懸念

> [2026-08-13] severity: medium
> **no-op は新しい失敗モードを作る——「気づかなかった」。** いまの mu の失敗はうるさい
> （壊す・escalate する）が、no_action は何も出力しない失敗になりうる。床として
> 「根拠を必ず残す」を入れたが、**根拠がもっともらしい嘘であるケース**は防げない。
> 033 の台帳に監視対象として登録し、実走で観測する（そのための台帳である）。
