## ゴール

**mu** ＝ 与えられたゴールに向かって PDCA を回し、人間の逐次介入なしに自立実行する **汎用エージェント**。それを **きわめてミニマルな仕組み**（シンプル・ミニマル・本質的）で実装する。

まずコンセプトと仕様を README に言語化し、対話で洗練する。

## 進め方（確定ルール）

- **レイヤを一つずつ完成させる。** 複数の層を同時に半端に作らない。内側の層を完成させてから次の層へ。
- 作る向きは **内側 → 外側**。一番内側の非自律な核を固め、自律性を一枚ずつ外へ重ねる。
- **1 層 = 1 ファイル**（`mu/l0.py`, `mu/l1.py`, …）。層番号がファイル名。1 ファイルに収まらなくなったら層が厚すぎのシグナル。（2026-07-02 確定）
- → プロジェクトSkill: `.pair-agent/skills/layer-by-layer-completion.md` ／ `.pair-agent/skills/one-file-per-layer.md`

## 決定事項

1. **基本 LLM = Ollama**
2. **中核モデル = 自律性の層**: 内側ほど非自律、外へ行くほど自律的。作り方も内側から。
3. **ミニマルの4軸**（すべて最小化）: 機構の薄さ／概念の少なさ／依存とコード量／状態・記憶の少なさ
4. **L0 = Ollama インタフェース層（自律性ゼロ）** — 上位に「常に安定して応答が返る、理想化された LLM」を見せる:
   - 推論: `/api/generate`・`/api/chat`（tool calling 対応）
   - モデル可用性の理想化: 無ければ黙って `/api/pull`（存在・能力確認に `/api/tags`・`/api/show`）
   - 接続の安定化: 接続確立・リトライ／バックオフ・タイムアウト・エラー回復
   - **含まない**: 埋め込み(B) ／ 監視(D `ps`/`version`) ／ blob(E) ／ OpenAI互換(F `/v1`)
5. **L1 = ツールコールのループ**（行動する層 / Do）: ツールは Ollama ではなく **mu が定義・実行**。モデルは `tool_calls`（意図）を返すだけ。`chat → tool_calls → mu実行 → role:"tool"で戻す → chat …` の反復。PDCA(Check/Act)はまだ持たない。
6. **設定系** = mu の中だが自律性の層・エージェントのループの外。初期化処理などで使う。モデル管理系（`/api/create`・`/api/copy`・`/api/delete`・`/api/push`）。
7. **L0 のエラー方針** — 背骨: **「接続を理想化・中身は関知しない」**。
   - 「応答を得られたか」= L0 の領分（吸収／リトライ、無理なら型付き通知）。「応答の中身」（拒否・崩れ・空・`tool_calls`不正）= 関知せずそのまま上位へ。
   - 吸収対象（リトライ）: 接続不可・タイムアウト・ストリーム切断・一時5xx・モデル未取得(→自動 `pull`)・資源不足(限定リトライ→駄目なら通知)。
   - 上位へ見せる型は **4つだけ**: `Unreachable`／`ModelUnavailable`／`ResourceExhausted`／`BadRequest`。それ以外は成功応答。
   - リトライ = 指数バックオフ＋ジッタ＋回数・遅延の上限。生成は副作用なしで再試行安全（部分出力は破棄）。**具体値は実装フェーズ**。

> **L0 完成**（概念仕様＋実装＋テスト, 2026-07-02）。次の層は L1。

## 実装メモ（L0 / 2026-07-02）

- 言語 **Python** ／ 依存 **公式 `ollama` クライアント**（`ollama>=0.6`、実測 0.6.2）。
- コード: `mu/l0.py`（`OllamaInterface` ＋ 4 型エラー）。テスト: `tests/test_l0.py`（フェイク差し替え 14 件）＋ `tests/test_l0_live.py`（実 Ollama スモーク 2 件）。**16 green**。
- 例外マッピング（実物で裏取り）: 接続断 → 組み込み `ConnectionError` ／ タイムアウト・ストリーム切断 → `httpx.TransportError` ／ HTTPエラー → `ollama.ResponseError(.status_code)` ／ 構築不正 → `ollama.RequestError`。
- **ラティファイ結果（2026-07-03）**:
  1. **自動 pull は反応的**（chat → 404 → pull → 再試行）→ **採用**（師匠: Good）。`show`/`list` は上位向けに公開のみ。
  2. **ストリーミングは v1 未対応** → **確定**。実装は先送り、ただし**拡張点を下記に確定**。
  3. **OOM 判定はヒューリスティック**（5xx の文言に memory 等）→ **採用**（師匠: OK）。

### ストリーミング拡張点（場所だけ確定・実装は先送り）

現状 `chat`/`generate` → `_idealize(model, call)`（`call` を1回呼び値を返す・例外を4型分類）。`stream=True` では `client.chat` が**イテレータ**を返し、通信エラーは**反復中**＝今の `try/except` の外で起きるため素通りする。後付けは**内部3点のみ・公開API不変**（L1 に影響なし）:

- **A. 例外分類器の抽出**: `_idealize` 内の except ラダー（接続 / `httpx.TransportError` / `ollama.ResponseError` / `ollama.RequestError` → リトライ｜pull｜4型）を共通分類器へ切り出し、ストリーム／非ストリームで共有。
- **B. `_idealize_stream` 追加**: イテレータを包むジェネレータ。**最初のチャンク前**の失敗（接続・404）は A で完全吸収（未 yield なので安全に再開）。**チャンク開始後**の切断は逐次表示の意味論と衝突 → v1方針では `Unreachable` で上位へ（部分破棄）。
- **C. 分岐**: `chat`/`generate` で `kwargs.get("stream")` が真なら B、偽なら現状 A 経路。

- **付随（解決 2026-07-03）**: `stream=True` は `_reject_streaming` で `NotImplementedError`（ネットワークに触れる前に fail-fast）。4型契約は汚さない（機能未実装は別カテゴリ）。テスト2件追加。
