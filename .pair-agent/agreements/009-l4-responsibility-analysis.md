### 見立て — **2層分の仕事が1ファイルに同居している**

群を「誰の仕事か」で分けると、きれいに2つに割れる。

| | 目的の層（PdM の仕事） | 進行の層（PjM の仕事） |
|---|---|---|
| 入力 | 人間の**目的** | **SPEC**（仕様・受入基準） |
| 判断 | 充足可能か／仕様は何か／verdict と check を見て accept・respec・escalate | プロセスをどう編むか・誰に振るか・どこを再実行するか |
| 生成物 | `SPEC.md` | `PROCESS.md` ・ 成果物 ・ `verdict.md` |
| 該当する群 | B・F・K・I ＋ SPEC artifact ＋ 制御の一部 | C・D・E・H ＋ PROCESS artifact ＋ 制御の一部 |
| 概算 | **約185行** | **約320行** |

この2つは **mu の層の定義（内側を D として使い、外側が判断を足す）にそのまま乗る**——
目的の層は進行の層を D として使い、返ってきた verdict と check を見て「仕様を直すか・人間に上げるか」を
判断する。これは L2→L3 の関係と同型であり、分ければ両者とも既存の層と同じ規模（180〜320行）に収まる。

つまり**責務過剰の正体は「太った層」ではなく「2層が1ファイルに同居している」こと**である可能性が高い。

## 未決の解消（2026-08-05 師匠の判断）

1. **(1) 層として分ける**。PdM を L5 に分割する。
2. **`L4 = 進行の層（PjM）` / `L5 = 目的の層（PdM）`**。既存の「L4＝目的の層」記述はすべて改訂する。
3. **予算の封筒は各層が自分で持つ**（L2/L3 と同じ思想）。L4 は PjM 判断サイクル（rerun/replan）、
   L5 は respec サイクルの上限を持つ。
4. **受入は「挙動不変＋比較実走（H3×1・正常系2件）」**。

## 構造（確定）

    L5 Director（PdM）: 目的 → 充足可能性の申告 → 仕様（SPEC.md）→ L4 を D として使う
                        → 返ってきた verdict/checks を見て accept / respec / escalate
    L4 Manager  （PjM）: SPEC → プロセス（PROCESS.md）→ 役割を着せた L3 を1タスクずつ
                        → 決定論 check と verdict を集め → rerun/replan は自分で処理し、
                          **respec / escalate は上へ返す**（自分の職掌で直せないという申告）

- **`decide` の語彙は変えない**（PjM の判断は rerun / replan / respec / escalate のまま）。
  変わるのは**処理の場所**——rerun・replan は L4 の中で回し、respec・escalate は L4 の run を終えて
  L5 へ返す。「判断は外へ、実行は内で」の再帰がそのまま1段増える形。
- **受入基準の check（決定論）は L4 が走らせる**（PjM が rerun を判断するのに必要なため）。
  結果は L5 にも返り、accept 判定に使われる。
- クラス名: L4 = `Manager`（PjM）／ L5 = `Director`（PdM。既存名を上へ移す）。
- CLI: 目的を入力する `l5_chat.py`（現 `l4_chat.py` を改名）。`l4_chat.py` は
  **SPEC を入力して進行の層だけを叩く最小 CLI**として置き直す（層ごとに CLI という規約）。

## 先に規定した失敗点（既知リスク）

- **層の再定義は文書の広範囲に波及する**（README・全 docstring・合意005〜008 の記述）。
  008 で「機構を変えたら層の定義文書も直す」を Skill 化した直後であり、ここは徹底する。
- **rounds の分配を誤ると挙動が変わる**。現在は1つの予算で PjM 判断と respec を賄っており、
  分けると「どちらが先に尽きるか」が変わりうる（実走で比較する）。
- **概念が増える**。「層は積むもの」という mu の思想には合うが、L5 を作ると
  「その外に何が来るか」の問いが自動的に発生する（人間が底、は変わらない）。
