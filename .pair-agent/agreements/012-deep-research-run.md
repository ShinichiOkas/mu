## 目的 — 「良い報告書」ではなく「層構造が通用するか」

**成果物の出来は主目的ではない。** 見たいのは、コーディング用に育てた層構造
（L5 目的→仕様 / L4 プロセス・人選 / 役割 / 独立 QA / 決定論 check）が、
**成果物がコードでない領域でそのまま働くか、どこで噛み合わないか**である。

したがって**完走しなくても失敗ではない**。噛み合わなかった箇所が具体的に見えたら、そのスプリントは成功。
（[[sprint-acceptance-is-the-observed-failure]]）

## 事前に確認した機構の実態

- **決定論 check はコーディング固有ではない** — 実体は `{run: コマンド, expect: 期待文字列}` を
  実行して照合するだけ（`mu/l3.py: run_check`）。リサーチにも置ける
- **ただし役割名は機構が期待している** — `mu/process.py` は `qa` タスクが無ければ自動補完し、
  未知の役割は `implementer` にフォールバックする。roles を差し替えても**名前は自由でない**
- 実行環境: Ollama に 22 モデル（`gemma4:12b` / `gemma4:31b-cloud` / `qwen3.5:9b` ほか）

## 師匠の決定（2026-08-05 協議）

| 論点 | 決定 |
|---|---|
| ① 題材 | **ローカル LLM 実行基盤の比較**（Ollama / llama.cpp / vLLM / LM Studio）→ mu の基盤としての妥当性。師匠が内容を判定でき、実利があり、複数ソースが要る |
| ② 役割定義 | **まず既存の `roles/` のまま当てて壊れ方を見る**。推測で作ったリサーチ役割より、観測してから直す方が確実 |
| ③ 決定論 check | **出典 URL の実在確認**。報告書中の URL を実際に叩き、到達件数を照合する（リサーチにおける偽・完遂＝**出典の捏造**を機械的に検出する） |
| ④ 走行範囲 | **まず小さく L2 → 通ったら L5**。011 の未検証点（モデルが `web_search` → `fetch_url` を繋げるか）を先に潰し、失敗時の切り分けを可能にする |
| ⑤ モデル | **本体 `gemma4:31b-cloud` ／ QA `qwen3.5:9b`**（README の開発回転構成。QA は別ファミリーで非相関） |

## 設計

### Phase 1 — L2 で web ツール連携の最小確認

モデルが `web_search` → `fetch_url` → `write_file` を**繋げられるか**だけを見る小さな走行。
ここが通らなければ L5 実走は意味を持たない（層の検証にならない）。

### Phase 2 — 走行の器を用意する

- 作業ディレクトリ `runs/2026-08-05-012/research/`（使い捨て・file grounding）
- **`check_sources.py`** を作業ディレクトリに置く — 報告書中の URL を全部叩き、
  全部到達すれば `SOURCES_OK n/n`、1つでも死んでいれば `SOURCES_NG` を印字する。
  これを**環境の実物として置いておく**だけにして、
  **PdM が受入基準の `run` に採用するかどうかは観測対象にする**（仕様を人間が書かない）
- `probe_research.py`（`probe_hard.py` と同じ形の自動走行 probe）

### Phase 3 — L5 実走（目的だけ渡す）

目的文（案。PdM に仕様化の余地を残す「なぜ」の形にする）:

> ローカルで LLM を動かす実行基盤について、Ollama / llama.cpp / vLLM / LM Studio を比較し、
> mu（きわめてミニマルな汎用エージェント）の基盤として Ollama を使い続けるべきかを
> 判断できる材料を報告書にまとめてほしい。判断に効く観点で比べ、
> 主張には必ず出典 URL を添えること。

### Phase 4 — 観測を記録に落とす

`runs/2026-08-05-012/README.md` に、**噛み合わなかった点**を具体で残す。想定される観測点:

- 役割定義（実装・QA 前提の `roles/*.md`）がリサーチでどう働くか／空回りするか
- PdM が受入基準に何を置くか（`check_sources.py` を拾うか、コード用の検査を書こうとするか）
- QA が「事実の検証」をできるか（コードの検証しか知らない定義書で）
- 出典の捏造（偽・完遂のリサーチ版）が起きるか、起きたら check が捕まえるか

## やらないこと

- 役割定義の新規作成（②の決定。壊れ方を見てから）
- `mu/*`（コア）の変更 — 摩擦が見つかっても、この走行では直さず**記録する**
- 報告書の内容の作り込み・人手での補正 — 検証にならない
