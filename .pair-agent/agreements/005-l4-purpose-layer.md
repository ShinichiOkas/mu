## ゴール

**L4 = 抽象的なお題と抽象的なゴールを、詳細な仕様と詳細なゴールに変換する層。**
そして L4 の停止条件は **目的（なぜ作るか）レベル**にある。

- **L3 まで**（既存）= 詳細な仕様とゴールを与えられ、それを達成するプランを作って L2 に実行させる。
- **L4** = その「詳細な仕様とゴール」を、人間から与えられた**目的**から作る。成果が目的を達成したかで判定する。

## 診断 — なぜ偽・完遂が起きたのか

### 現象の統一（実験記録より）

4件の偽陽性は、いずれも **判定が「実体」でなく「表象」に対して行われている**という単一構造だった。

| 機序 | 判定者 | 見ていた表象 | 見ていなかった実体 |
|---|---|---|---|
| ① `_carry_done` の穴（修正済） | L3 の pending 判定 | `done` フラグ | 単位が実際に完遂したか |
| ② 未書き込み pass | L2 Reflect | transcript 上の提案コード | ディスク上のファイル |
| ③ criterion の要件漏れ | L2 Reflect | criterion のテキスト | ゴールの要求 |
| ④ overall の幻覚 | L3 overall | plan summary のテキスト | 成果物の中身 |

### V字モデルで見ると、欠落が名指しできる

V字の肝は「各段階の検証は、**同じ段階の仕様**に対して行う」こと。mu は右側（検証）は揃っているが、
**左側の最上位＝要求定義に当たるものが存在しない**。人間の1行の願いがそのまま Plan（基本設計）に流れ込む。

結果、受入判定に相当する overall が対応する要求仕様を持たず、**一段下の Plan テキストに対して判定する**しかない。
V字の右腕が、対応相手を失って一段下にぶら下がっている状態だった。

> **表象に対して判定すること自体は誤りではない**（単体テストは詳細設計という表象に対して行う）。
> 誤りは、**最上位の表象が存在しないこと**にある。

### TDD で見ると、非対称が露骨になる

合意004 は「テストコード自体が別の L2 単位として先に作られる → L3 が TDD をオーケストレーションする」と宣言している。
**単位レベルでは TDD をやっているのに、全体ゴールに対しては先に書くテストが無い。**

さらに F1 の題材は「todo_app.py 以外のファイルを作らないこと」と制約したため、
**L3 自身の TDD 規則（テストは先行する別単位）が成立不能**になっていた。因果はこう繋がる:

```
実行可能な受入条件が作れない
  → criterion が散文になる
    → L2 が机上のコードを見て pass する（機序②）
      → overall が Plan テキストを読んで幻覚する（機序④）
        → 偽・完遂
```

**mu における「checkable」は事実上「実行できるテストがある」を意味しており、それが無いときの防御が無い。**
しかも致命的なのは、**mu 自身が checkability を失ったことに気づかない**点。黙って主観で判定し成功を報告する。
これは北極星で既知だった「GUI は auto-checkable でない」の一般形であり、GUI ですらない F1 が同じ崖から落ちた。

### 落差の正体

**人間が自然に言えるのは目的である。詳細な仕様は言えない。**
「タスク管理を楽にしたい」は一言で出るが、「9機能それぞれに検査があり `--selftest` が12件以上を実行して exit 0」は出てこない。

ところが mu は L3 の入り口で後者を要求していた。README が L2 について
「ゴールは checkable な成功条件で与える」と書いた前提を、L3 でも黙って引き継いだためである。
**人間が自然に供給できるものと、mu が要求していたものの間に落差があり、それを埋める層が無かった。**

## L4 の構造

### 各層は同じ形をしている（再帰同一構造の完成形）

| 層 | goal（判定の相手） | P（一段具体にして下へ渡すもの） | D（内側） | Reflect |
|---|---|---|---|---|
| L2 | 単位ゴール | — | L1 の行動 | ゴールを達成したか |
| L3 | 仕様 | 単位（file + criterion） | L2 | 仕様を満たしたか |
| **L4** | **目的（なぜ）** | **定義 + 完了条件 + 仕様（何を）** | **L3** | **目的を達成したか** |

**「何を作るか」は L4 の Plan であって goal ではない。goal は「なぜ作るか」。**
L3 が仕様を単位に割るのと同じ動作で、L4 は目的を仕様に割る。

### L4 の仕事の正体は「操作的定義」

例（師匠の題材）: 「この売上表から不採算商品を特定してくれ」

1. **不採算とは何かを定める** — 「粗利率 X% 未満」等、測定手続きに落とす（＝操作的定義）
2. **特定できたとはどういう状態かを定める** — これが**受入テスト**。V字の左上と右上がここで揃う
3. **スクリプトの仕様とゴールを L3 に渡す**

L3 は意味を扱わない。「不採算」という概念は L4 で計算に還元され、L3 が受け取るのは手続きだけになる。

### 層の梯子

| 層 | 扱うもの |
|---|---|
| L4 | **意味**（不採算とは何か） |
| L3 | **手続き**（どう分解し、どう作るか） |
| L2 | **遂行**（この単位は達成されたか） |
| L1 | **行動**（ツールを実行する） |
| L0 | **呼び出し** |

自律性の軸で「意味を定めること」が最も自律的なのは自然である。曖昧さが宿るのは意味の層であり、
それを解消するのが最も高い判断だから。

### なぜ L4 が必要か — 手続きの成功と目的の達成は別の事実

スクリプトが正常終了して「不採算商品: 該当なし」と出力したとする。
L3 の目から見れば完璧（仕様どおり動き、テストが通り、exit 0）。
**しかし本当に該当が無いのか、結合キーを間違えて全行が落ちたのか、L3 には区別がつかない。**
L3 が持っているのは手続きの仕様だけだから。区別できるのは目的を持つ層だけである。

F1 で `--selftest` が exit 0 で通ったのに期限・優先度が無かったのは、まったく同じ穴だった。

## 推測の扱い — 幻覚をなくすのではなく、外に出す

L4 が「不採算＝粗利率5%未満」と定めるのは推測である。業種によって基準は違うので L4 に知りようがない。
**しかし推測を避けることはできない。避けるべきは、推測を暗黙のまま結論に混ぜることである。**

- overall が幻覚したのは、判定基準が**暗黙で不可視**だったから。外から見えず、直しようもなかった。
- L4 が「不採算を粗利率5%未満と定義しました」と**明示して**進めば、同じ推測が**検証可能な仮定**になる。

→ **定義は artifact（ファイル）であるべき。** L3 も L2 も参照でき、人間も直接直せる。
**ファイル・グラウンディングが、意味の層まで届く。**

## 抽象度の再帰 — 層の数は構造では決まらない

### L5 は L4 と同型

- **L5**: 抽象（P/L改善）→ 定量目標（5%）＋ 手段（販売停止）→ L4 へ依頼 → 成果を目標に照らす
- **L4**: 抽象（不採算商品の特定）→ 定義（粗利率5%未満）＋ 完了条件 → L3 へ仕様 → 成果を目的に照らす

どちらも「受け取った抽象を一段具体にして下へ渡し、返ってきた成果を自分の抽象に照らして判定する」。
**中身が違うだけで形は同じ。**

### 層のインタフェースは「ドキュメント → ドキュメント」＋適切性判定（師匠 2026-07-30）

pi 比較調査のレビューで師匠が同型性の中身を一段精密にした（原文は「師匠の言葉」参照）:

- 各層の **IN はドキュメント**（一段抽象の要求）、**OUT もドキュメント**（一段具体の仕様・成果）。
- 各層の Reflect の正体は「**IN の要求に対して OUT が適切か？**」であり、この問いが抽象度を
  上げながら何階層も続く。
- 「定義は artifact（ファイル）にする」決定と合わせると、**層の境界はすべてファイルになる**。
  ファイル・グラウンディング（L3 の背骨）が全層のインタフェース原理へ一般化される。
- そして**入出力がドキュメントに揃った時点で、層ごとに別コードを書く必要が消える** —
  同一コードに一段抽象な IN を与えて**再入**する再帰構造が自然になる（未決2 の方向）。

傍証: pi も再帰を「層を積む」のではなく**同じプログラムの再入**で実現している
（subagent 拡張は別プロセスの pi を起動、orchestrator は CLI の上から pi プロセス群を監督。
[docs/compare-pi-2026-07-30.md](../../docs/compare-pi-2026-07-30.md) 学びB-2周辺）。

### 帰結: 層の数を決めるのは人間の入力の抽象度

| 人間の入力 | 必要な最上層 |
|---|---|
| 「粗利率5%未満の商品を抽出する script.py を書け」 | L3（もう仕様） |
| 「この売上表から不採算商品を特定してくれ」 | L4 |
| 「P/L を改善してくれ」 | L5 |
| さらに抽象的なお題 | さらに上 |

同じ mu が、入力の高さに応じて必要な段だけ使う。
**「再帰の底は人間」は、人間が最下段にいるという意味ではなく、
人間がどの段からでも入れて、その上はすべて人間、という意味になる。**
天井は構造の側には無い。

### 上に行くほど Reflect が閉じにくくなる

| 層 | 判定に何が要るか |
|---|---|
| L2 | ファイルを読めば分かる |
| L3 | テストを走らせれば分かる |
| L4 | 出力を見て定義が妥当だったか判断する（人間の知識が要る） |
| L5 | P/L が5%改善したか（**数ヶ月待たないと分からない**。因果も不確か） |

**上に行くほど、判定に必要な情報が mu の外にあり、時間がかかり、因果が曖昧になる。**

→ **mu が層を持てるのは Reflect のループを閉じられる範囲まで。閉じられなくなったところが人間の場所。**
これは恣意的な線引きではなく mu 自身の構造から出てくる線であり、
「Reflect は判定するためというより、人間に上げる境界を作るためにある」という理解と噛み合う。
上に行くほど、Reflect の重心は「判定する」から「上げる」へ移る。

## 既存層への影響

### 1. L3 の overall は L4 の仕事の前借りだった

現在の `_OVERALL_SYSTEM` は、抽象的な1行ゴールとファイル名＋散文 criterion のリストだけを与えられて
「この成果物一覧はこの願いを網羅しているか」と問われている。**この問いには事実として答えようがない。**
推測するしかなく、推測は幻覚と区別がつかない。**幻覚はモデルの弱さというより構造上の無理だった。**

L4 が仕様を持てば、判定は二層に分かれる:

- **L3 の判定** = 仕様を満たしたか。仕様が checkable なら**照合**でできる（機械的に縮む）
- **L4 の判定** = 目的を達成したか。本質的に人間的で、再帰の底に届く

**L4 を足すと L3 は薄くなる。** 概念は1つ増えるが、L3 の中の無理な責務が1つ消える。

### 2. 承認の位置が一段低すぎた

現在の `l3_chat` を見直すと、責務が逆転している。

- **人間**が承認しているのは Plan と再計画 ＝ **技術的分解の妥当性**（人間には判断しにくい）
- **LLM** が判定しているのは overall ＝ **ゴールを達成したか**（人間が最も強い）

合意004 の「判断は外へ」という原則は正しかったが、**外に出した判断の種類が外側の判断力に合っていなかった**。
これは 合意004 が先に懸念した「HITL の粒度 — 再計画のたび毎回承認は煩い」の答えでもある。
**煩いのは回数のせいではなく、聞くべきでないことを聞いているから。**
L4 が仕様を持てば計画の承認は L4 が自律的にでき、人間は目的の達成だけを見る。

### 3. 機序②（未書き込み pass）は L4 だけでは塞がらない — コード側の証拠を併設する（2026-07-30 採用）

診断の因果連鎖では「実行可能な受入条件が作れない → criterion が散文 → L2 が机上のコードで
pass（機序②）」であり、L4 が criterion を実行可能に寄せれば②の引き金は消える。しかし
**実行可能な受入条件がそもそも作れない題材**（F1 の「ファイル1つ縛り」、GUI）では②の穴が残る。

防御は L4（プロンプト・構造）でなく**コード側**に置く: ツール結果に機械可読な事実
（成功/失敗フラグ、書き込んだパスとバイト数 等）を持たせ、Reflect には散文の transcript より
それを優先して見せる（[docs/compare-pi-2026-07-30.md](../../docs/compare-pi-2026-07-30.md) 学びA-3。
pi は `isError` と型付き `details` を content と別チャネルで持つ）。
これは既知リスク「決定的に守りたい不変条件はコード側に置く必要がある」の具体例そのもの。
L4 と独立に効くため、L4 スプリント内で併設するか先行させるかは実装協議で決める。

### 4. 判断の重さが層で変わる

L5 が決める「不採算商品の販売停止」は実世界に帰結を持つ経営判断であり、
L3 の「ファイルをどう分割するか」とは重さが違う。
三層非対称（説明責任は師匠に一極化）は保ちつつ、**mu が自律的に決めてよい範囲は層ごとに違う**はずである。
下は自律、上は承認、という非対称は自然に見える。

## 決めたこと

- **L4 = 目的（なぜ作るか）を人間から受け取り、定義・完了条件・仕様を定めて L3 に渡す層。**
- **L4 の停止条件は目的レベル**（L3 の成果で目的が達成できたか）。仕様の checkability は
  停止条件ではなく **Plan に課す品質規則**（L3 の「各単位は file を生み checkable」と同じ位置）。
- **L5 以降は L4 と同型**。層の数は構造でなく人間の入力の抽象度で決まる。
- **定義は artifact（ファイル）にする。** 推測をなくすのではなく、明示して検証可能な仮定に変える。
- **mu が層を持てるのは Reflect のループを閉じられる範囲まで。**

## 決定済み（旧・未決。2026-07-30 師匠の判断）

1. **着手順・実装の形**（旧未決1+2、統合）— **まず `mu/l4.py` として具体化し、動いてから再入形へ畳む。**
   方向としての「再入」（入出力がドキュメントに揃った時点で同一コードへの再入で再帰する）は維持するが、
   再帰の正しい抽象は具体を1つ見てからの方が確か。F1 の教訓「実機ログこそが接地」と
   [[one-file-per-layer]] に沿う。L5 を置く段になったら l4.py を再入形へ畳む。
2. **定義の確認タイミング** — **決めて明示し、動かして見せてから直す。**
   L4 は操作的定義を artifact として明示して進み、成果と一緒に提示する。
   「5%で計算したらこの12商品が出ました」の形が人間には直しやすい。[[per-layer-chat-cli]] と一致。
3. **L3 の overall** — **L4 導入と同時に機械的照合へ縮める。**
   L4 が仕様を持つ以上、L3 の判定は「仕様を満たしたか」の照合で足りる。
   幻覚の温床（機序④）を本スプリント内で塞ぐ。L3 改修が本スプリントの範囲に入る。
   ※機序④は本スプリントの発端そのものなので「既存課題を巻き込まない」には抵触しない。
4. **機序②へのコード側防御と検証のフック化** — **構造化 tool 結果を L4 着手前に先行実装。**
   tool 結果に機械可読な事実（成功/失敗フラグ、書き込んだパスとバイト数 等）を持たせ、
   Reflect には散文 transcript より優先して見せる。
   **verify スロット化（コード検証器の差し込み口）は保留** — L4 実走で機序②の再現具合を

## 先に規定した失敗点（既知リスク）

- **L4 の Reflect も曖昧になりうる** — 目的レベルの判定は仕様適合より曖昧で、また推測になり幻覚する恐れ。
  ただしこれは欠陥ではなく**正しい設計**と解釈している。曖昧だからこそ人間に上げる。
  mu の役割は「判定して報告する」ことではなく「**自分では判定できないと分かって人間に上げる**」ことになる。
  F1 が黙って `完遂 ✓` と言ったのは、判定できないことを判定できると思っていたから。
- **プロンプトのガードは確率的にしか効かない** — F1-g2 で `_PLAN_SYSTEM` のガードは無視され
  `_REPLAN_SYSTEM` のガードは効いた。**決定的に守りたい不変条件はコード側に置く必要がある**という実証がある。
  L4 でも同じ問題が出る前提で設計する。
- **ミニマル原則との緊張** — 概念が1つ増える（三原則の「概念の少なさ」）。
  ただし L3 が薄くなる分で相殺される可能性があり、また偽・完遂を防げないならエージェントとして成立しないため、
  「本質的＝核だけ」の側に入る候補と見ている。最終判断は師匠。
- **層が増えるほど1タスクの実行時間が伸びる** — 既に F1 は1走10分超。L4 を足すとさらに伸びる。
- **未着手の既存課題を巻き込まない** — `_ANALYZE_SYSTEM` の詰め、証拠デッドロック、
  `write_file` の path 欠け steering は [LONGTERM_TODO.md](../../LONGTERM_TODO.md) に残っている。
  本スプリントで一緒に潰そうとしない（クールダウンの趣旨）。
