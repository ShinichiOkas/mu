## これは方針転換ではない — 二層構造である

合意007 B2 は「塞ぐには任意のコマンド文字列の解析が要り、実行者の正当な能力を削る」として
**意図的に塞がなかった**。016 はそれを否定しない。**その上に「防ぐ層」を足す**。

人間社会と同じ構造である——**原本は金庫に入れる（防ぐ）。それでも監査はする（検出）。**
どちらか一方ではない。

**OS レベルの読み取り専用属性なら、合意007 が避けた道（コマンド文字列の解析）を通らずに防げる。**
これが 007 の時点で見えていなかった選択肢である。

## 実測（提示前の裏取り）

| 経路 | read-only 属性で防げるか |
|---|---|
| Python `open(w)` | **拒否**（PermissionError） |
| Python `unlink` | **拒否**（PermissionError） |
| PowerShell `Set-Content` | **拒否**（exit 1） |
| PowerShell `Out-File`（リダイレクト） | **拒否**（exit 1） |
| `attrib -R` してから書く | 通る（**回避できる**） |
| `Remove-Item -Force` | 通る（**削除できる**） |

**防ぐ層は偶発的・無自覚な改変を確実に止めるが、意図的な回避は止められない。**
015 の破壊（テスト用サンプルの生成）は前者なので、これで止まる。後者のために検出層が要る——
実測が二層構造の必要性をそのまま裏付けている。

## 師匠の決定（2026-08-07 協議）

| 論点 | 決定 |

## 設計

### 三つの機構、二つの層

| 層 | 機構 | 役割 |
|---|---|---|
| **防ぐ（内側）** | `tools` 層の拒否（既存） | **理由を言葉で返せる**のはこの層だけ。steering になる |
| **防ぐ（外側）** | **OS の read-only 属性**（新規） | `execute_command` 経由でも効く。理由は伝わらないが確実 |
| **検出** | `protection_violations()`（既存）＋**周ごとの検査**（新規） | 意図的な回避が起きたら見え、その場で止まる |

### A. `protect()` が OS レベルの保護をかける

- 登録時に**保護前の属性を控え**、`os.chmod(path, S_IREAD)` をかける
- `clear_protection()` が**控えた属性へ復元**する（元々 read-only だったならそのまま）
- 存在しないパスは登録だけして保護をかけない（検出層が「missing」で拾う）

### B. 破れを周ごとに検査して止める（②）

015 で判明した穴: `protection_violations()` は**走行の最後にしか呼ばれない**ため、
timeout 打ち切りだと**検出報告そのものが出ない**。「破れは検出できる」設計が走り切らないと働かない。

- `Manager.run(..., guard=None)` を足す。`guard` は「破れのリスト」を返す呼び出し可能。
  **各周の頭で呼び、非空なら即 escalate**する
- 注入するのは呼び出し側（`guard=tools.protection_violations`）。
  **層は保護機構を持たない**——環境への接地は caller の責務、という既存の設計に従う
  （`run_check` が実行器を tools から受け取るのと同型）
- L5 は `guard` を L4 へ素通しする

### C. 走行の器が `finally` で解除する（①）

`probe_hard.py` / `probe_research.py` / `l5_chat.py` を `try/finally` で囲み、
**異常終了・timeout 打ち切りでも `clear_protection()` が走る**ようにする。

## やらないこと

- `attrib -R` / `Remove-Item -Force` の封鎖 — 任意コマンドの解析が要る（合意007 の判断のまま）。
  だから検出層を残す
- ACL（`icacls`）による強制 — 実測で解除も同じ権限でできたため、read-only 属性より強くない
- 入力を作業ディレクトリ外に置いてコピーを渡す案 — 「入力の実物への接地」の意味が薄れる
