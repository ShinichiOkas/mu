## 経緯の中間形と、その棄却 — 二軸モデル

中間形（二軸モデル）は「個人軸 × 組織軸が対称に進化する」とし、組織軸に独自の順序原理
「調整失敗のクラス（逐次 → 並列=競合 → 階層=委譲の情報損失）」を与え、
`roles/ : 個人 :: workflows/ : 組織` という知識の対称も立てた。

これを棄却した理由（棄却の記録は再発防止のため残す）:

1. **分類器として壊れる**（師匠の指摘）— TODO/WBS はどちらの軸にも属さない。
   「すべての知識はどちらかの軸に属する」という暗黙の仮定が誤り。対称に**見えるように**
   作った表であり、綺麗さが嘘をついていた。
2. **型が還元を示していた** — L4 task は L3 unit ＋ 割り付け列2本（下記診断）。
   組織側に「新しい能力」は実装上ひとつも存在しなかった。
3. **順序原理も還元される** — 「逐次→並列→階層」は失敗クラスの階段ではなく
   **スケジューリング方針の列挙**にすぎない。これにより、二軸モデルが改訂対象とした
   合意006 の「並列は後から足せる最適化にすぎない」は**概ね正しかった**と再確認された
   （条件は変わらず: 依存が散文の部分一致でなく `deps` として実在すること。
   現状のままの並列化は危険）。

## 診断 — 還元を支える証拠（すべてリポジトリ内で検証済み）

### 1. 型が既に語っている

```
L3 unit : {task, file, criterion, check?} + done
L4 task : {task, file, criterion, check?} + done + role + model
```

L4 が足した列は **role（誰が）と model（どのリソースで）の2本だけ**。どちらも割り付け列で、
どちらも optional（role 不明→implementer、model 未指定→プール先頭）。すなわち:

> **L3 は「割り付けが自明（全部自分）」という退化ケースの L4。**
> 組織は新しい能力ではなく、同じ仕事オブジェクトの上に割り付けの自由度が生まれた状態。

### 2. 同じオブジェクトを認識しなかった代償が既に出ている

| L3 | L4 | 中身 |
|---|---|---|
| `_PLAN_SCHEMA` | `_PROCESS_SCHEMA` | ほぼ同一 |
| `_unit_goal` | `_task_goal` | ほぼ同一 |
| `_carry_done` | `_carry_done_tasks` | **偽・完遂を防ぐ同じ防御を二度実装** |
| `_plan_summary` | `_process_summary` | ほぼ同一 |

加えて `mu/l4.py` は l3 の私的名（`_parse_json` / `_with_env`）を import しており、
共有物が層に押し込まれている症状が出ている。

### 3. 共通ルールを知識ファイルに複製する drift は実験済み（結果も出ている）

「入力ファイルは読み取り専用」の出現箇所: `roles/architect.md`（散文）／`roles/implementer.md`
（散文・重複）／`tools.py` の `protect()`（機構・後付け）。
**散文2箇所は H4 で破られ、効いたのは機構だけだった。** ここから機械的テストが引ける:

> 全ての `roles/*.md` に同じ行が現れたら、それは配置ミス。機構か基底文書へ移す。

### 4. H セットの難所の座標はすべて能力側

難所は H3（目的→仕様の独断）・H4（実装者のスコープ規律・check 文字列の脆さ）・
check の空振り（レビュー B章）— **全部が個人の能力と装備の問題**。
割り付け側の事故は deadstock の design.md 再生成（承認済み 2970 bytes が 2626 bytes に
書き直された）1件のみで、原因は依存を散文の部分一致で推定していた**字句バグ**。
つまり割り付け側は普通の工学（決定論的に直せる・テストが書ける）に落ち、
LLM の不確実性が本質的に残るのは能力側だけ、という配分が実走からも読める。

### 5. プロセスの分散は実測ゼロに近い

H セット6走のプロセス形状: **5走が architect > implementer > qa の完全同型**
（残る perf は implementer が2つ）。課題の性質は6走とも異なるのに、である。
PjM のプロセス設計は毎回 LLM 呼び出しで**同じ一つの定石を再発明し、文言ノイズを混ぜている**
（そのノイズが上記 design.md 再生成の引き金だった）。ワークフロー（定石）化は美学ではなく、
同じ出力をノイズ抜きで得るための置換である。

## 構造 — 合意する概念構成

### 能力（個人）— 二つの成長モード

| モード | 中身 | 性質 |
|---|---|---|
| **深さ** | L0..L3 のループ構造 | 入れ子。自律性で全順序。**ほぼ完成** |
| **装備** | 道具・知識・規律の**差分** | 入れ子にならない。同じループが「何に触れられるか・何を知っているか」が変わる |

- 基底道具（read/write/edit/list/execute）は装備ではなく**深さ（L1 の構成要素）**。
  専門化は常に基底に対する差分。
- 差分は3種で性質が違う: **制限**（引き算。QA は verdict.md にしか書けない —
  コードで決定論的に強制できる唯一の種類）／**追加**（足し算。専門道具）／
  **既定**（癖。散文でしか書けない・確率的）。混ぜない。
- **検証は本来この軸の装備**である。自分の主張を自分で反証する能力（check の反証テスト等）は
  チーム以前に一人が持つべきもの。QA は**二重化**であって代替ではない
  （現状は代替になっているため、QA が甘い日に床が消える — レビュー B-3）。

### 割り付け（組織）— 軸ではなくビュー

- 組織側とは、能力を持つ個体群に対する**仕事・リソース・文脈・決定権の割り付けの管理**。
  **組織は能力を増やさない。割り付けの自由度を増やすだけ。**
- 逐次／並列／階層は capability の階段ではなく**スケジューリング方針**。
- 組織的に見えるものの還元先: QA の独立性 = anti-affinity 制約つき割り付け／
  「誰が何を見られるか」（prior_files）= 文脈の割り付け／escalate = 決定権の割り付け。
  現在の mu の射程で残余は見つかっていない。
- 割り付けは**既知の工学**（探索・制約充足・スケジューリング）であり、決定論的に書けてテストできる。
  ただし「簡単」ではない — 難しさの**種類**が違うだけ（部分再実行の最小集合はほぼ最小被覆問題）。
- 「マルチエージェントの組織構造を工夫すれば賢くなる」という期待は、この還元により**否定**される。
  研究資源は能力側（とくに装備）に集中する。

### 三分法 — 共通要素の置き場（師匠の警告への答え)

| カテゴリ | 何か | どこに置くか | 個人/組織で分かれるか |
|---|---|---|---|
| **機構** | 不変条件・ループ構造・スケジューラ | コード | 分かれない（共通） |
| **媒体** | 仕事・成果を表現する器（WBS 項目、ファイル、TODO） | 型として**1つ** | 分かれない（共通） |
| **知識** | 差分のみ（役割の装備、定石） | ファイル（roles/ 等） | ここで初めて分かれる |

- 共通要素が現れたら、それは知識ではなく機構か媒体。**共通要素を知識ファイルに置いた瞬間が設計ミス**
  （診断3で実証済み）。
- WBS 項目（unit/task）は媒体。ファイル・グラウンディングの「ファイル」と同格で、だから両方に共通する。

### 役割の対称化と、決定論の床の不可侵

- 現在、5役割のうち architect/implementer/qa は `roles/`（データ）、PdM/PjM は
  `mu/l4.py` 内のプロンプト直書き（コード）。この非対称は実装順序の名残であり、設計根拠はない。
  **PdM・PjM も `roles/` の役割として対称化する。**
- PdM（目的→仕様）は割り付けを一切含まない**純粋な個人の能力**であり、組織側の住人ではない。
  系全体で最も高度な能力がここにあり、H3 で落ちたのもここ。能力と割り付けが `Director` に
  融合していることが l4.py 589行（L0+L1+L2 の合計 573行超）の主因。
- 対称化後の `Director`（旧 L4）に残るのは**機構だけ**: スケジューラ（逐次実行ループ）、
  決定論の床（QA 自動付加・verdict 機械読み・criteria check・依存伝播）。
- **歯止め（不可侵）: 役割は提案する、不変条件はコードが強制する。**
  現在コードが握っている保証を役割プロンプトの散文に溶かさない。
  PjM 役割化で最も壊しやすい場所として先に釘を刺しておく。

### ワークフロー — WBS テンプレート（媒体側の知識）

- ワークフローは新しい層ではなく、**組織の持ち物でもない**。手順の型は割り付けの**前**に決まる
  **WBS テンプレート**であり、一人でも使える（判定テスト:「一人でも使えるか？」）。
- 効用は「実行時にモデルが発明しなければならない自由度を計画から削る」こと。
  `_bind_to_signature` → overall 機械照合 → check 埋め込み、と続いてきた本プロジェクトの
  同じ一手の、計画への適用。流行（ループエンジニアリング）との一致は結果であって動機ではない。
- 副次効果: 定石があると PjM の仕事が「発明」から「**選択と逸脱の判断**」に変わり、
  テンプレートとの diff という ground truth が生まれる。PjM の出力が初めて反証可能になる。

## 合意事項（案 — 師匠の agreed で確定）

1. **還元の採用**: 進化の軸は**能力（深さ × 装備）ただ一つ**。組織側は割り付けビュー
   （リソースアロケーションの管理）であり、能力の軸ではない。二軸モデルは棄却（経緯は本文書に保存）。
2. **三分法の採用**: 機構（コード）／媒体（共通の型）／知識（差分のみ）。
   配置テスト2つ — 「全 roles/*.md に同じ行 = 配置ミス」「一人でも使える = 組織の持ち物ではない」。
3. **媒体の統合**: L3 unit と L4 task を1つの WBS 項目型に統合する
   （`role`/`model` は optional な割り付け列）。置き場所は層でないファイル（例: `mu/work.py`）。
   構造規約に「**媒体は層ではない**（層は1ファイル、ただし全ファイルが層ではない）」を追記する。
4. **役割の対称化**: PdM・PjM を `roles/` へ。`Director` には機構（スケジューラ＋決定論の床）だけを残す。
   不変条件を役割散文に移さない（不可侵）。
5. **専門化の配線**: 役割（装備）を L3 単体に渡せるようにする（`l3_chat --role qa` が動くこと）。
   専門能力の検証を組織機構抜きの単体実験にする。
6. **装備は diff として持つ**: 役割ファイルに道具の全集合を書かない。制限/追加/既定を区別して書く。
7. **ワークフローの規律（作るのはまだ）**: `workflows/` は現時点で切らない。
   定石の新設は「**実走で2回以上、同じ形状が独立に観測されたときだけ**」（発明しない・観測を昇格する）。
   現データでは定石は1つ（architect > implementer > qa）しか存在しない。
8. **probe の対照群**: ワークフロー導入後も「定石なし」の対照走を probe セットに恒久的に残す。
   定石ありの数字を能力の証拠として報告しない（測定の汚染防止）。
9. **並列の位置づけの確認**: 合意006「並列は最適化」を維持。ただし前提条件として
   依存の明示（`deps` 列。散文部分一致の廃止）を課す。
10. **記録の改訂**: [docs/review-2026-08-02.md](../../docs/review-2026-08-02.md) A章に
    本合意への追記注釈を入れる（書き換えではなく追記 — 記録の作法に従う）。

### 実装順序 — 能力側の床が先、媒体統合が次（師匠賛成 2026-08-02）

二正面の回避（失敗点5）に従い、スプリントは片側ずつ:

1. **次スプリント（能力側の床）**: check の同語反復ゲート＋反証テスト（レビュー B-2①②）、
   `_SPECIFY_SCHEMA` の unsatisfiable / blocking_questions チャネル（同 C-3）、
   `roles/qa.md` に「SPEC が目的の制約を弱めていないか（原文照合)」の検査項目1行。
2. **その次（媒体統合）**: unit/task の単一 WBS 項目型への統合（合意3。還元の反証テストを兼ねる）、

   rerun で invalidate 空のとき QA だけ空振りするバグの修正。

## 先に規定した失敗点（既知リスク）

1. **「〜でしかない」の誤読** — 割り付け＝簡単、ではない。難しさの種類が「確率を実走で追う」から
   「既知の工学」に変わっただけ。スケジューリングを舐めた実装は逐次でも壊れる（design.md 再生成が前例）。
2. **測定の汚染** — 定石は能力の穴を隠す。対照群（合意8）を落とした時点で、実験記録の信頼が崩れる。
3. **定石の増殖** — 規律（合意7）を破って「あったら便利」で定石を発明し始めたら、
   選択問題（どの定石か＝新しい LLM 判断＝新しい失敗点）と陳腐化が来る。
4. **不変条件の散文化** — PjM 役割化の際、コード側の床（QA 自動付加等）を役割プロンプトへ
   移してしまう。テストで担保する: 床の各項目に対応するユニットテストが消えていないこと。
5. **二正面** — 能力側（check 反証テスト等）と割り付け側（媒体統合）を同時に走らせて両方半端になる。
   スプリントは片側ずつ。
6. **将来の残余** — 交渉・規範形成のような「真に組織的な現象」が将来観測されたら、
   還元の射程を超えた証拠として本合意を再協議する（現時点で観測なし）。

## AIの懸念

- **私は本協議で一度間違えた**（二軸モデルを対称に見えるよう構成し、師匠の指摘2回で棄却に至った）。
  綺麗な構造化への傾きは AI 側のバイアスとして実証済みであり、**本合意の三分法・還元にも同じ傾きが
  混入している可能性がある**。だからこそ合意の確定を概念の美しさでなく反証テスト（媒体統合の実施）に
  委ねる構成にした。統合が軋んだら、その記録を消さないこと。
- 還元の検証範囲は**現在の mu の射程**（逐次・5役割・ファイルグラウンディング）に限る。
  並列・階層で新しい失敗クラスが観測された場合、「スケジューリング方針にすぎない」という位置づけは
  データで再審査されるべき。
- 合意10（レビュー A章への追記）を忘れると、将来の読者が二軸モデルを現行の結論と誤読する。
  記録が資産であるこのプロジェクトでは、古い結論の放置は他プロジェクトより高くつく。
