## 現状の制限（実測）

| 箇所 | 制限 | 起きること |
|---|---|---|
| `read_file` | 先頭 `_MAX_OUTPUT`=4000 文字で切り詰め。**続きを読む手段がない** | 4000 文字を超えるファイルは後半が永久に見えない |
| `read_file` | `Path.read_text()` で**全文をメモリに載せる** | 巨大ファイルで無駄（原理的な上限） |
| `write_file` | 上書き／新規のみ | 大きな成果物を**分割して書けない**。1回の生成長がそのまま上限になる |
| `edit_file` | 全文一致置換のみ | 末尾追加ができない（`old` に末尾の一部を書く迂回が要る） |
| `execute_command` | 4000 文字で切り詰め。**続きがない** | 長いテスト出力・ログの後半が見えない |
| `list_dir` | 上限なし（全件） | 逆に巨大ディレクトリで文脈が爆発する |

**本質は「窓が固定で、動かせないこと」**。窓を小さく保つこと自体は LLM 文脈の防衛として正しいので、
撤廃ではなく **窓を動かせるようにする** のが本スプリントの方針。

## 師匠の決定（2026-08-05 協議）

| 論点 | 決定 |
|---|---|
| ① `read_file` の刻み単位 | **行単位**（`offset` / `limit` 行） |
| ② 既定の出力上限 4000 文字 | **既定窓として残し、切り詰め時に「続きの offset」を案内する** |
| ③ 末尾追加の形 | **`write_file` に `mode` 引数**（ツールは増やさない＝責務最小化） |
| ④ `execute_command` の出力 | **スコープに含める**（出力全般を無制限化） |

## 設計

### A. `read_file(path, offset=0, limit=None)`

- `offset` = **先頭から読み飛ばす行数（0 が先頭）**。`limit` = 返す最大行数。
- 文字上限（`_MAX_OUTPUT`）は**常に効く**（②の決定）。`limit` 指定でも上限に達したらそこで打ち切る。
- **切り詰め時は必ず「続きの呼び出し方」を content と facts の両方に出す**。
  モデルには散文で、検証者には `next_offset` で。
- 実装は**行のストリーム読み**にする（`read_text()` をやめる）。返す窓の外はメモリに載せない。
  総行数だけは走査して数える（安い・位置感覚に要る）。

```
read_file("mu/l4.py", offset=200, limit=100)
→ content: <200行目以降の100行>
          ...(lines 200-299 of 4821 shown. 続き: read_file(path, offset=300))
   facts: {action:"read", path, offset:200, lines:100, total_lines:4821,
           chars:3120, truncated:true, next_offset:300}
```

- 末尾まで読み切ったら `truncated=false` / `next_offset=None`（「もう続きはない」が機械可読で分かる）。
- `offset` が総行数を超えたら空 content ＋ `total_lines` を案内（エラーにしない）。

### B. `write_file(path, content, mode="overwrite")`

- `mode="append"` で末尾追加。ファイルが無ければ新規作成（親ディレクトリも作る）。
- **facts の後方互換**: `bytes` は従来どおり**書いた後のディスク実体**（`stat().st_size`）。
  追記分は `appended` として別キーで足す（既存の契約・テストを壊さない）。
- 保護ファイル（`protect()`）は `mode` に関わらず拒否する。**追記も内容改変である**。
- 弱いモデル対策として `mode` の表記ゆれ（`a` / `add` / `w` / `write`）を吸収する。
  未知の値はエラーで返し、正しい値を案内する（黙って上書きに倒さない＝破壊は起こさない）。

### C. `edit_file(path, old, new)` — 変更なし＋案内だけ足す

末尾追加は B に寄せたので、`edit_file` に追加モードは持たせない（置換と追加が1関数に同居すると
意味論が濁る）。ただし **`old` が見つからないときのエラー文に「末尾に足したいなら
`write_file(path, content, mode="append")`」を案内**する。実際に起きる誤用への steering。

### D. `execute_command(command)` — 出力全文をファイルに落として辿れるようにする

出力はディスクに残らないので、**切り詰めたときだけ全文を一時ファイルに保存し、そのパスを案内**する。
続きは既存の `read_file(path, offset=...)` で辿れる（新しい機構を足さない＝責務最小化）。

```
exit=0
<先頭4000文字>
...(truncated, 152300 chars total. 全文: read_file("<tmp>/mu-exec-xxxx.txt", offset=N))
facts: {action:"exec", exit:0, chars:152300, truncated:true, output_path:"..."}
```

保存先は OS の一時ディレクトリ（`tempfile`）。切り詰めなかった走行ではファイルを作らない。

### E. `list_dir(path, offset=0, limit=None)` — 同じ窓を入れる

④「出力全般を無制限化」の対として、**入り口の防衛**も同じ形にする。巨大ディレクトリで
全件返すと文脈が壊れるため、既定窓＋続きの案内を `read_file` と**同じ語彙**で持たせる。

## AI の判断（要・事後確認）— 窓より長い1行をどうするか

行単位の窓では、**1行が既定窓（4000 文字）より長い**場合に「行を割るか / 丸ごと返すか」が決まらない。
**行を割らず丸ごと返す**方針を採る。

- 割ると `offset`（行番号）ではその行の続きを指せず、**辿る手段が消える**——今回の目的
  （制限を無くす）に正面から反する。
- したがって窓は「**上限に達するまで行を足す。足した結果超えるのは許す**」という単純な規則にする。
  返る量は最大 `_MAX_OUTPUT ＋ 最長行` に収まる。
- 極端に長い1行（minify 済みファイル等）では文脈が膨らむ。**黙って膨らませない**ため、
  `facts` に実測の文字数を出し、切り詰めない選択をしたことが観測できるようにする。

この方針でまずいようなら差し戻してください。
