## 問いへの答え — 検査器が作れるのは「接地できる性質」だけ

検査器の正しさは、最終的に2つのどちらかに接地していないと決まらない。

- **実行可能な現実** — ファイルが在る／exit 0／URL が 200／ハッシュ一致
- **人間が既に知っている答え** — テストの期待値

コーディングで検査器（テスト）が成立するのは**答えを人間が知っているから**である。
リサーチは**答えを知らないから調べている**。ここが本質的な非対称で、
「答えを知らないタスクの検査器は、答えの*性質*しか検査できない」。

| | 例 | 検査器 |
|---|---|---|
| **接地できる** | 出典 URL が実在する／固有名詞が出現する／件数が N 以上 | 作れる。正しさが定まる |
| **接地できない** | 妥当性・網羅性・洞察の質・「判断に効くか」 | **決定論の検査器にしてはいけない** |

014 の `Tool1` / `View1` 事件は、接地できない性質（5観点の網羅）を機械検査に押し込んだ結果、
**代理指標に化けて成果物がそれに最適化された**——グッドハートの法則そのものだった。

## 師匠の決定（2026-08-07 協議）

| 論点 | 決定 |
|---|---|
| ① 接地できない性質の担い手 | **QA が見る。ただし検査自体を「文脈を共有していない LLM」に委ねる。** QA がサブタスクとして、他の LLM に**要件だけ**を渡して検査させる。**検査器そのものが LLM で実装される** |
| ② 操作的定義 | **PdM に接地を課す**。「網羅されている」→「SPEC が列挙した5語が各々出現する」のように、接地可能な形まで落とすことを PdM の責務にする |
| ③ 未検査項目があるときの完遂判定 | **明示して達成可**。未検査 N 件を結果に添えたうえで achieved を返す。自立実行を止めず、偵察可能性だけ上げる |

## 設計

### A. `judge` — LLM で実装された検査器（①）

決定論の検査器が書けない基準のための道具。**QA だけが持つ**。

```
judge(requirement, path) -> ToolResult
  content: "PASS / FAIL / UNCERTAIN + 理由"
  facts:   {action: "judge", verdict: ..., requirement: ..., path: ..., model: ...}
```

**文脈非共有が本体である。** 渡すのは「要件テキスト」と「対象ファイルの中身」だけ。
走行の履歴・SPEC 全文・実装者の言い分・これまでの失敗は**渡さない**。
判定者は経緯を知らないので、「頑張ったから」も「前回こう言われたから」も効かない。

AI の判断（要・事後確認）:

- ~~**QA 専用にする**~~ → **全役割が持つ**（2026-08-07 訂正。師匠決定）

  当初 AI は「実装者に渡すと自分の成果物を自分で判定させることになり独立性が消える」として
  QA 専用を提案したが、**実装中にこの判断が誤りだと分かった**。judge の独立性は
  「誰が呼ぶか」ではなく**文脈非共有**から来る。実装者が自分の成果物を judge にかけても、
  返るのは経緯を知らない判定者の意見であり、QA の判定の独立性は損なわれない。
  `roles/implementer.md` には既に「実装後、必ず自分で検証コマンドを実行して確かめる
  （品質ゲート実行）」があり、judge を持たせるのは**その意味版**になる。

  実装上も、QA 専用にするには `tools:` 省略＝全許可の権限モデルに逆らって
  implementer / architect に明示リストを書く必要があり、**今後ツールを足すたびに
  その役割だけ静かに新ツールを失う**保守リスクを生む。`roles/qa.md` にだけ
  `judge` を足す（QA は明示リストなので必要）。他は現状のまま。
- **モデルは呼び出し側が注入する。ただし別モデルを前提にしない**（師匠の補正）:

  > モデルは呼び出し側が注入　は同意なのだが別モデルが使える環境かどうかは環境依存なので
  > 同モデルでも正しく判定されることが理想

  `make_judge(l0, model=None)` とし、**省略時は走行の既定モデル**を使う。別モデルが使えるなら
  使えばよいが、**それを前提にした設計にしない**。したがって「**同一モデルでも、文脈を共有しない
  だけで判定が成立する**」ことを設計要件に置く。そのために要るもの:

  | 要素 | 内容 |
  |---|---|
  | 文脈非共有 | 走行履歴・SPEC 全文・実装者の言い分・過去の失敗を渡さない。**要件と対象の中身だけ** |
  | 役割の分離 | judge 専用の system を与える。実装者・PjM の視点を持ち込まない |
  | 既定を fail 側に置く | 「要件を満たす**証拠が対象の中に実際にあるか**。無ければ fail、読み取れなければ uncertain」。LLM は pass に倒れやすいので、**証拠が無いことを合格にしない** |
  | 構造化出力 | 3値＋理由＋**根拠の引用**（対象のどこを見たか）。引用を強制すると、証拠なしの合格が作りにくくなる |

  同一モデルで実際に判定できるかは**測る**（下記 Phase 1 の完了条件）。理想であって自明ではない。
- **判定は3値**（pass / fail / uncertain）。「判定できない」を潰さない
  （QA の既存規範「確認できないことは確認できないと書く」と揃える）
- **床は動かさない** — judge の結果は QA の判断材料であって、コードの完遂判定を直接変えない。
  決定論 check（実体に接地した床）と、LLM 判定（確率的）を混同しない

### B. 未検査の可視化（③）

現状、`run` が空の受入基準は `_run_criteria_checks` に拾われず、**結果にも実況にも現れない**。
「検査されたのか、検査項目が無かったのか」が外から区別できない——010 で潰した
「見えない部分が残る」と同じ形である。

検査の状態を**3分類**にして結果に出す:

| 分類 | 意味 |
|---|---|
| `machine` | 決定論 check が通った（実体に接地） |
| `judged` | LLM 検査器が見た（QA が judge を使った。確率的） |
| `unverified` | **誰も機械的に見ていない** |

`unverified` があっても achieved は返す（③の決定）。ただし件数と項目名を結果に添える。

### C. PdM に接地を課す（②）

`roles/pdm.md` の操作的定義の規範を強化する。「曖昧語を定義せよ」は既にあるが、
**「定義は接地可能な形まで落とせ」**を明示する。落とせないものは `run` を空にしてよい
（既存の規範）が、そのときは**接地できないと分かって空にした**ことが分かるようにする。

## やらないこと

- 014 で挙げた「検査器が間違っているときの逃げ場」— **取り下げる**。対症療法であり、
  書き換え経路を再び開く。筋は「接地できないものに検査器を作らせない」（VERIFIER FIRST の発火条件を絞る）
- 決定論 check の廃止 — 床は床のまま残す
- 複数モデルの投票 — コストが倍以上になる。judge の文脈非共有で足りるかをまず見る
