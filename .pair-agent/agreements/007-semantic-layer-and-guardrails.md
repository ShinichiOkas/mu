## 対象（4件）

### C1. PdM が検出した矛盾を独断解決する（重大・H3 実観測）

欠けているのは「**検出した矛盾は解決せず上げる**」という規範または機構。対策候補:

- (a) specify プロンプトに「充足不能を検出したら仕様を作らず escalate」の規範を足す（確率的ガード）
- (b) QA の必須検査項目に「SPEC が目的の制約を弱めていないか」（目的の**原文**と照合）を足す
- (c) (a)+(b) 両方
- (d) **specify の structured output に申告フィールドを足し、分岐はコードに置く** — 例
  `{feasible: bool, conflicts: [...]}` を `_SPECIFY_SCHEMA` に追加し、`feasible=false` なら
  PjM を起動せず即 escalate。006 決定4「判断は structured output、実行はコードの決定論」と同型。
  確率が残るのは「矛盾を検出できるか」だけになり、**検出後に握り潰す経路が消える**（H3 では
  検出は成功していた）

**決定（2026-08-02 師匠）: (c) に (d) を加えた三重。** 師匠:「(d)のほうが決定的でこの場合は
適切な対応になるね。入れましょう」。(a) は「申告させる」規範であり **(d) の schema がその受け皿**に
なるため、3案は競合せず1つの機構に組み上がる。

実装の実体:

- **(a) 規範**: `_SPECIFY_SYSTEM` / `_RESPECIFY_SYSTEM` に足す——「PURPOSE の制約が同時に
  満たせないと判断したら、制約を弱めた仕様を作るな。矛盾を申告せよ」。
- **(d) 申告＋コード分岐**: `_SPECIFY_SCHEMA` に `feasible: bool` と
  `conflicts: [string]`（矛盾する制約の組）を追加。Director は `feasible=false` を見たら
  **PjM を起動せず即 escalate**（conflicts を assessment に載せて人間へ）。
  006 決定4「判断は structured output、実行はコードの決定論」と同型。
  *小さな実装判断*: `feasible` の**欠落は true 扱い**（＝従来動作）。欠落を escalate に倒すと
  申告できないモデルで常に止まり、自律の到達距離を測れなくなる（決めたこと4）。
  明示的な `false` だけを分岐条件にする。
- **(b) 二重化**: `roles/qa.md` の必須検査項目に「SPEC が PURPOSE の制約を弱めていないか」を追加。
  そのために**コード側で QA タスクの IN に PURPOSE の原文を接地する**（現在 QA が見るのは
  SPEC＋成果物のみ）。005 の証拠グラウンディング・006 の env preamble と同型の
  「呼び出し側が事実を前置する」形。(d) が検出漏れしたときの受け皿。
- (b) 経路の escalate は既存機構で足りる: QA が検出 → verdict no/uncertain →
  PjM decide → respec/escalate。新しい分岐は (d) の1本だけ。

これにより確率が残るのは「**矛盾に気づけるか**」のみ。H3 では気づけていた（SPEC に明記していた）
ので、**気づいた後に握り潰す経路が消える**。

### B1. 役割別ツール制限（QA の自己修正→自己承認を権限で止める）

f1×12b r2 で QA が成果物を自分で修正してから合格判定した。role プロンプトの「実装しない」は
確率的にしか効かない。

**決定（2026-08-02 師匠）: role=qa 限定でなく全役割へ一般化する。** 権限は役割定義に属する
データとして持ち、コードが適用する。

- 置き場: `roles/*.md`（既存のナレッジベース）に許可を宣言する。形式は実装で確定するが、
  想定は frontmatter（例 `tools: read_file, list_dir, execute_command, write_file` ＋
  `write_scope: own | any`。`own` ＝自タスクの出力ファイルのみ書ける）。
- 適用点: `Director._execute` が1タスクを L3 に渡すところ（役割プロンプトを system に
  前置しているのと同じ場所）で、渡す `tools` を役割の許可で絞る。
- **PjM は権限を書き換えられない**: PjM の structured output に出せるのは `role` 名だけであり、
  権限表はコードがディスクから読む。人間は `roles/*.md` を直接編集して変えられる（006 の
  「role 定義は人間が直せる artifact」の延長）。未決2 の懸念はこの非対称で解消。
- 拒否は既存の steering 形（`_protected_result` と同型のエラー ToolResult）で返し、
  **拒否したこと自体をログに残す**（決めたこと4: 塞ぐが観測は殺さない）。
- 既知の抜け: `execute_command` はシェル経由で書けるので QA の書き込みを完全には塞げない。
  QA から execute_command を外すことはしない（検証の実行が職掌の中核）。B2 と同じ穴であり、
  「防ぐ」でなく「見える」で受ける。

### B2. 保護の意味論（新規ファイル作成・シェルリダイレクト）

現在の `tools.protect()` はファイル単位の書き込み禁止。抜けが2つ実観測されている:
H4 の新規ファイル作成によるスコープ逸脱（ディレクトリ不変が守れない）と、
execute_command のシェルリダイレクト。

**方針（決めたこと4 の適用で慎重側に倒す）**: 保護を強くして能力を先回りで絞ることはしない。
H4 は「正直に escalate に上がった」走であり致命的でない。本スプリントでやるのは
**意味論を決めて文書化すること**と、**破れたときに見えること**まで:

- `protect()` の意味論を「列挙したファイルの内容不変」と明記する（ディレクトリ不変ではない）。
- ディレクトリ不変が要るなら別の道具（例: 実行前後のスナップショット差分を log に出す）
  として分ける。実装するかは B1・C1 の進捗を見て判断（やらない場合は理由を合意に書く）。
- シェルリダイレクトの穴は塞がない（塞ぐには execute_command の解析が要り、能力を削る）。
  代わりに**保護対象ファイルの改変が起きたことを検出してログ／verdict に出す**方向を検討する。

## 先に規定した失敗点（既知リスク）

- **矛盾検出そのものは確率的**。(d) を採っても「矛盾に気づかない PdM」は救えない。
  H3 は検出に成功していたので今回の対処範囲だが、「気づかない」ケースが次の穴として残ることを明記しておく。
- **ツール制限が実装者の正当な作業を殺す恐れ**。QA の verdict 以外の書き込み禁止は自明だが、
  一般化（未決2）に踏み込むと役割ごとの許可設計を誤って正常系を壊しうる。
- **保護の意味論を強くしすぎると escalate が増える**。H4 は「正直に上がった」走であり、
  現状が致命的でないことは踏まえる。
- **入力グラウンディングの前置が PURPOSE を汚す**。大きい入力の先頭だけ添える等、
  截断の設計を誤ると証拠デッドロック（LONGTERM_TODO）と同じ問題に触れる。
