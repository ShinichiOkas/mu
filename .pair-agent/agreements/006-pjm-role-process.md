## 診断 — なぜこの形か

### 役割の欠けと観測済みの失敗が1対1に対応する

| 役割 | 現在の mu での居場所 | 対応する観測済みの失敗 |
|---|---|---|
| PdM | L4 specify（SPEC.md）— 存在する | — |
| PjM | L3 plan/replan と L4 rounds 管理に分散 | 3単位同一ファイル計画、rounds 予算の場当たり |
| アーキテクト | **不在** | 入力データ破壊（「入力は読み取り専用」の設計規則を誰も定めない）、パス混乱、no-op selftest（品質特性の定義者不在） |
| 実装者 | L2＋L1 — 存在する | — |
| QA | L2 Reflect / L4 assess に癒着（作業文脈と同居） | 偽・完遂（作業の物語を読んで判定） |

役割表は組織論の輸入ではなく、**実際に踏んだ穴の裏返し**である。エージェントで役割分割を
正当化する利得は3つに還元される: **文脈の隔離（汚染防止）／モデルの非相関／成果物ドキュメント
という契約**。この3つに還元できる分割は採り、還元できない儀式は採らない。

### mu は既にこの構造を8割持っている

- **文脈の独立**: L3 は単位ごとに L2 をまっさらな messages で起動している。サブエージェントは
  今も毎単位生まれては消えている。欠けているのは役割を着せる仕組みだけ。
- **役割スロット**: L3→L2 の `system` は役割プロンプトの差し口としてそのまま使える。
- **通信路**: ファイル・グラウンディング。design.md → 実装者の IN、成果物 → QA の IN は
  「単位が成果物ファイルを生み次の単位の文脈になる」の言い換え。

**変更の実体は unit スキーマの拡張だけ**:

```
現在:  unit = {task, file, criterion, check}
提案:  task = {role, task, file, criterion, check, model?}   ← 役割と人選が増えるだけ
```

### 並列は「だけ」

タスク間の依存はファイルで表現済み。依存が交差しないタスクの並列実行は後から足せる
ループ最適化であり、**本スプリントのスコープ外**。逐次が先である理由: 決定論ループは
デバッグ可能で、失敗の観測（ハーネスの穴探し）は逐次のほうが読める。並列はクラウド
モデル前提（ローカル VRAM では並列できない）で、リソースプールの話と噛み合う。

## 構造

- **PdM**（L4 既存の specify）: 目的 → SPEC.md（操作的定義・**受入基準**・仕様）。
- **PjM**（L4 に足す機能）: SPEC を受けて**プロセス＝役割注釈付きタスク列**を structured output で
  編む。難易度・規模に応じて役割を inline にするか独立タスク（サブエージェント）に分けるかを決め、
  **人選（モデル割り当て）**も行う。人員リソース（モデル・並列数・rounds 予算）は PjM の管理下。
  呼び出し側は PjM に**予算の封筒**を渡す（「上限は呼び出し側が規定」は封筒として保存）。
- **プロセス表は artifact**（体制表を兼ねる）: 誰が・どの役割で・どのモデルで・何を作るかが
  1枚に見え、人間が直せる。
- **実行ループ（コード・決定論）**: プロセスの1タスクずつを **L3 に役割を着せて**実行する。
  L3 の中身（単位分解→L2→check ゲート）は無変更。役割＝タスク属性（データ）であり
  role プロンプトを system に前置するだけ。
- **アーキテクト**: プロセス内の1タスク。OUT＝design.md（構造・品質特性・**設計規則**。
  例:「入力ファイルは読み取り専用」）。後続タスクの IN に入る。
- **QA**: プロセス内の1タスク。IN＝SPEC＋成果物、OUT＝verdict.md。**別文脈・別ファミリー
  モデル可**（[[verification-models-by-role]] のプールから PjM が人選）。
- **人間はプールの外**。PjM が管理する人員ではなく、escalate で依頼する相手（再帰の底）。

## 決めたこと（口頭協議 2026-07-31〜08-01）

1. **マルチエージェントは新フレームワークでなく、役割注釈付きプロセスの逐次ループとして作る。**
   並列実行は後続の最適化であり本スプリントに含めない。
2. **所有権の分離**: 受入基準（何が満たされれば目的達成か）＝**PdM** の持ち物（SPEC）。
   予算・打ち切り・エスカレーション条件＝**PjM** の持ち物（プロセスと封筒）。QA は前者に照らして検証する。
3. **QA inline 化の条件（設計規則）**: 受入が決定論的 check で完全に覆えるときだけ QA を inline に
   してよい。散文的判定が残るなら **role=QA の独立タスクを必ず立てる**（別文脈、できれば別ファミリー）。
   これは PjM の裁量に任せない規則とする。
4. **staffing 判断（確率的）へのガード**: 体制はプロセス表として artifact 化し人間が直せる。
   実行ループとガード（予算超過で止まる・check 不合格は done にしない）はコードの決定論に置く。
   PjM は判断だけを structured output で行う。
5. **決定論の床は置き換えない**: check ゲート・escalate 設計は役割分離後もそのまま残る。
   役割分離が改善するのは確率的判定の側（非相関化・能動的証拠集め）。
6. **PjM の A ＝部分再実行**（2026-08-01 追加）: プロセスの各タスクは状態
   （done / failed / invalidated）を持ち、失敗や verdict を受けた PjM の判断は
   「**どのタスクを無効化して再実行するか**」（計画だけ・実装だけ 等）とする。
   判断は structured output、**無効化の依存伝播と再実行はコードの決定論**
   （依存はファイルで表現済み）。これは L3 `_carry_done` とファイル・グラウンディングの一般化であり、
   部分再実行を駆動する依存グラフは並列可能性を判定するグラフと同一物——逐次のうちに
   この機構を入れておけば、並列化は「無効でない独立タスクの同時実行」だけになる。
   **ガード（005 の `_carry_done` の穴の教訓）**: タスク同一性キーの一意性検証はコード側に置き、
   どのタスクを再実行した後でも**最終 QA タスクは必ず再実行する**（検証タスクは carry しない。
   部分再実行の経路から「検証を飛ばして完遂」に到達できなくする）。

## 未決の解消（2026-08-01 師匠の判断）

1. **PjM の置き場所 = L4**（決定）。L3 の planner は「役割の一つ」としてそのまま残す
   （役割を着た L3 が自タスク内の分解を計画するのは職掌内）。逐次処理の段階では PjM の仕事は
   少なく見えるが、**マルチエージェント（並列）になった時に真価が発揮される**——
   将来の並列化を見据えた配置として L4 に置く。
2. **role 定義は PjM の仕事**（決定）。役割プロンプトはコード内定数ではなく **role 定義書
   （artifact ファイル群）として PjM に渡すナレッジベース**とする。人間が直接直せ、
   PjM が人選・任命時に参照する。置き場は実装で決める（repo の `roles/` を想定）。

3. **既存 L4 assess は QA タスクに置き換える**（2026-08-01 決定）。プロセス末尾に必ず
   role=QA タスクを置き、assess の一発 LLM 呼び出しは廃止。L4 は verdict.md を機械的に
   読んで accept / respec / escalate を決める。QA は能動的に証拠を集められ、
   別ファミリーの人選も可能になる（005 で L3 overall を同時に縮めた判断と同型）。
4. **入力保護は今回「設計規則＋QA で観測」、機構化は保留**（2026-08-01 決定）。
   design.md の設計規則（入力は読み取り専用）を役割構造が守れるか・QA/check が破壊を
   検出できるか自体を本スプリントの検証対象とする（probe は使い捨てディレクトリで安全）。
   **解除条件**: 実走で設計規則が破られ QA/check も検出できない事例を観測したら、
   tools 側の保護リスト（コード側・決定論）を実装する（[[defer-with-release-condition]]）。

## 先に規定した失敗点（既知リスク）

- **staffing 判断の誤り** — PjM が「自分でやれる」と誤認して inline に倒すと問題が静かに再生産される。
  ガードは決めたこと3・4。それでも誤るケースの観測が本スプリントの学びになる。
- **role プロンプトという新たな確率面** — 役割を着せても LLM が役割を守る保証はない
  （ガードは確率的にしか効かない、の既知実証）。守られたかを QA/check が拾えるかを観測する。
- **実行時間の増大** — タスク数×L3 実行になる。31b-cloud（15倍）が前提。12b 実走は穴探査に限定。
- **プロセス生成の壊れ** — LLM 生成のプロセスが空・重複・循環依存でありうる。
  スキーマ検証と決定論ループ側の防御（005 の `_carry_done` と同類の穴を想定）。
- **概念増との緊張** — 増えるのは task の `role`/`model` 属性とプロセス artifact。コード構造の
  増殖（役割ごとのクラス等）はしない。1ファイル原則は維持（置き場は未決1に依存）。
