# 合意 031 — 並列スケジューラ（無効でない独立タスクの同時実行）

status: executing（師匠合意 2026-08-12）
created: 2026-08-12

## 師匠の受け入れの枠（原文 2026-08-12）

> これで行きましょう。おそらく速くならないとは思っていますが副作用で悪化しないことの
> 確認も必要なのでまずはこれで行きましょう。

**このスプリントの主デリバラブルは「速くなること」ではなく「並列機構を入れても悪化しない
ことの確認」**——逐次回帰（既定 parallel=1 が 030 と同一挙動）と、並列有効時の
非悪化（正しさ・所要）を数字で示す。速くならない観測はそれ自体が成果として記録する。

## 背景

並列化の目的は**速度**（師匠 2026-08-12:「待たずにできることはやっておくというスタンス。
今はローカルだがローカルで運用し続けることは前提じゃない」）。前提となる床は 030 で敷設済み:

- **依存グラフは構成的に真**（needs 宣言＋ゲート＋tray の読み取り閉じ込め。実走で
  needs 未充足 0・lint 0 ＝宣言グラフ完全を確認）
- **作業空間は分離済み**（tray は per-task の closure で実装——`os.chdir` を使っていないので
  並列化がそのまま載る形）
- **single-writer は発行ゲートで強制**（共有空間を書けるのは所有ロールだけ）

残るは 006 が言った「並列化は『無効でない独立タスクの同時実行』だけになる」の実装。
006 の確定どおり**並列化は L4 の中の最適化**であり、L5 は無変更で恩恵を受ける。

## 設計（案）

### 1. 並列化するのは L4 の D だけ

PjM の P（プロセス）・A（decide）と決定論の C（checks・verdict 機械読み）は逐次のまま。
`_execute` の「pending を順に1つずつ」を「dispatch 可能なタスクを同時に最大 N」に置き換える。

### 2. dispatch 規則（コードの決定論。判断は入らない）

タスクが dispatch 可能 ＝ pending かつ:

- **(a) needs ゲート通過**（030 の `unmet_needs` と同じ述語: 産出タスク done／外部実在）
- **(b) WAW**: 同じ file を書く**先行**タスクがすべて done（改稿チェーンは列挙順で直列）
- **(c) WAR**: 自分の file を needs に宣言している**先行**タスクがすべて done
  （読み手が写しを取る前に上書きしない。読み手は snapshot なので開始後は干渉しない）
- **(d) QA バリア**: QA タスクは非 QA タスクが全部 done になるまで待つ
  （「検証を飛ばして完遂に到達できない」床を並列でも保つ）

空きスロットへは**列挙順**に詰める（決定論）。copy-in / publish は排他（lock）——
写しの途中に発行が重ならない。

### 3. 失敗・締切・破れの扱い

- タスクが失敗したら**新規 dispatch を止め、実行中を drain**（完走を待つ）。PjM に報告する
  failure は列挙順で最初のもの（逐次と同じ申告形。部分結果は tasks の done に残る）
- guard / deadline は **dispatch 境界**で見る。実行中タスクは中断しない——外部 kill が
  finally を飛ばして観測ゼロを生む轍（017）を、内部でも踏まない

### 4. 同時実行数は呼び出し側が規定・コード既定は 1

- `Manager.run(parallel=N)`。**既定 1 ＝完全に従来の逐次**（既存の測定基準を動かさない床。
  029「装備ゼロなら1文字も変わらない」と同じ型）
- CLI は `MU_PARALLEL`（無指定＝1。起動表示に出す）。レートを上げるのは環境変数での
  明示＝暫定上書き（[[observe-then-accelerate]]: コード既定は保守的、加速は観察後に上書きで）

### 5. 実装は threads（I/O bound）＋観測の並列対応

- タスク実行は threading（LLM 呼び出し待ちが支配的）。tray ツールは per-task closure で
  既に並列安全形
- **フェーズ0で L0（ollama クライアント）の並列安全性を実測プローブ**してから設計を確定する
  （[[probe-external-behavior-before-design]]。ダメなら L0 インスタンスをタスクごとに持つ）
- log コールバック・VerboseL0 の実況は**タスクタグ＋行単位 lock**——並列で観測を殺さない
  （006 の懸念「失敗の観測は逐次のほうが読める」への答え。読みにくければ MU_PARALLEL=1 で
  いつでも逐次観測に戻れる）
- `_PROTECTED`（合意023 の再訪）: guard は共有空間の原本の照合だけ・タスクは写しに触る——
  並列でも読み取り専用で原理上安全。tools の他の大域状態（`_REPORTED` 等）はフェーズ0で検査

## スコープ（フェーズ＝コミット単位）

0. **プローブ**: L0 並列呼び出しの実測（同一インスタンス・スレッド2本）・tools 大域状態の検査
1. **A — スケジューラ（TDD）**: dispatch 規則 (a)〜(d)・drain・境界検査・lock。
   FakeL3 で並列発火と直列化の全経路をユニットで固定
2. **B — 観測**: タスクタグ付きログ・起動表示（MU_PARALLEL）・PROCESS.md の done 更新
3. **C — 実測・クローズ**: 幅のある課題で並列発火を実走（31b-cloud 基準＋ローカル 12b の
   `OLLAMA_NUM_PARALLEL` 1回実測）・逐次回帰（MU_PARALLEL=1 が 030 と同一挙動）・
   runs/ 記録・README 更新

## やらないこと（スコープ外）

- **幅の促し**（PjM に独立タスクを分けて編ませる規範・skill）——実走の PROCESS はほぼ一本道
  であり、幅が無ければ並列は発火しない。まず機構と実測で「幅があれば速くなる」を確かめ、
  幅を促すかは観測を持って次に協議する
- タスク**内**（L3 の単位）の並列化／L5 respec サイクルの並列化
- 分散実行（複数マシン・キュー）——クラウドモデルへの同時リクエストまで

## AIの懸念

> [2026-08-12] severity: medium
> **幅が出ないと速くならない。** 既存実走 61 本の PROCESS はほぼ一本道（2〜4タスクの直列）。
> スケジューラが正しくても、PjM が幅を編まなければ実測は「変化なし」になる可能性が高い。
> それは失敗ではなく観測として記録する（幅の促しは次の協議材料）。

> [2026-08-12] severity: medium
> **ローカルの同時実行は逆に遅い可能性。** 同一 GPU で 12b×2 は VRAM・スループット次第で
> 直列より遅くなりうる。クラウドが本線（師匠確定）だが、1回は実測して数字で残す。

> [2026-08-12] severity: low
> **並列ログは読みにくい。** タスクタグで帰属は保つが、混線の読みにくさ自体は残る。
> 失敗の調査時は MU_PARALLEL=1 で逐次再現できることを担保に置く。
