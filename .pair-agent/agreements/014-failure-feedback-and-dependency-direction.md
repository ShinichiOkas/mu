## 調査結果 — 穴は L4 → 実行者の1箇所

| 経路 | 理由は届くか | 実装 |
|---|---|---|
| L2 内（Reflect → 次の周） | **○** | `reason` / `next` が `[L2]` フィードバックとして messages に入る |
| L3（ユニット check NG → 再計画） | **△** | `analysis`（reason＋suggestion）が**再計画プロンプト**へ（`l3.py:165-172`）。新しいユニットの task 文に残るかは LLM 次第で、決定論的な保証がない |
| **L4（受入基準 NG → rerun → 実行者）** | **✗ 届かない** | PjM の `decide` には `FAILED CHECKS` が渡る（`l4.py:247-249`）。しかし再実行されるタスクの goal を組む `process.task_goal()` は task / role / file / criterion / check / 参照ファイルだけで、**前回の失敗が1文字も入らない** |
| L5（respec → PdM） | **△** | PjM の `reason` は渡るが、**checks の事実（detail）は渡っていない** |

013 で起きたことがこれで説明できる。実行者は「検証コマンドの出力に必ず含めるべき文字列: PASS」とだけ
言われ、**なぜ PASS が出ないのか**（日本語マーカーが文字化けしている）を知らされないまま再実行された。
だから成果物ではなく**検査器の方を直した**。

## 併せて見つけた原因 — 依存伝播が逆流していた（013 分析の訂正）

`invalidate()`（`process.py:140-147`）は「無効化されたファイル名に**言及している**タスク＝依存」と判定する。
検査器タスクの task 文は `checks if 'comparison_report.md' contains...` と成果物に言及しているため、
PjM が `invalidate=['comparison_report.md']` を指示した瞬間、**検査器タスクまで巻き込んで無効化・再生成**された。

依存が**逆流**している。検査器は成果物を*参照*するが、成果物に*依存*してはいない（先に作られる側）。
**PjM は凍結を守る判断をしていた**（invalidate は成果物のみ）のに、コードがそれを覆した。

→ 013 の「破ったのは実行層」という分析は不正確だった。**きっかけはコード側**である。

## 師匠の決定（2026-08-07 協議）

| 論点 | 決定 |
|---|---|
| ① NG 理由の中身 | **コードの事実だけ**（実行した検査コマンド・期待マーカー・実際の出力）。LLM の解釈（PjM の判断・QA の GAP）は混ぜない——「判定を表象でなく実体に寄せる」（合意005）に一貫させる |
| ② 履歴の深さ | **直近1回だけ**。文脈を肥大させない（013 は L1 思考 1,033 回）。反復は実況ログと周回数で見える |
| ③ 凍結機構 | **1・2 を入れて再走してから判断**。検査器いじりは「理由が届かない」＋「巻き添え無効化」の合わせ技の可能性が高く、消えるなら 3 は要らない |

## 設計

### A. 失敗の事実をタスクに持たせる（1）

タスク構造に `last_failure: str | None` を足す。中身は**コードが実行した事実のみ**:

```
前回の失敗（コードが実行した事実）:
  検査: powershell -ExecutionPolicy Bypass -File verify_report.ps1
  期待: PASS
  実際: FAIL
```

- **L4**: 受入基準の check が失敗したら、`invalidate()` で無効化されたタスクに事実を書き込む。
  QA タスクにも入る（前回の検査結果は判定材料になる）
- **L3**: ユニット check が失敗したら、そのユニットに事実を持たせ、**再計画後も同じ file のユニットへ引き継ぐ**。
  再計画プロンプト頼みにしない
- **L5**: respec の FEEDBACK に、PjM の reason に加えて**失敗した checks の事実**を添える
- **L2**: 既に Reflect の reason/next が届いている。変更しない
- `task_goal()` / `_unit_goal()` が `last_failure` を goal に載せる。成功したら消す（次の周に古い失敗を持ち越さない）

### B. 依存伝播を後続方向に限定する（2）

`invalidate()` の言及ベース伝播を、**そのファイルを産むタスクより後ろにいるタスク**にだけ適用する。

- PjM プロンプトは既に「依存（ファイル経由）が先に来るよう並べよ」と指示している。
  **前段のタスクは定義上、後段に依存しない**——この契約が根拠になる
- タスク列に存在しないファイル名への言及は、従来どおり依存とみなす（保守的側）
- QA タスクを必ず無効化する既存規則は維持する（検証を飛ばして完遂させない）

### C. 凍結機構（3）— 設計だけ決めて実装は保留

実装するときの形（③の判断が「要る」になった場合）:

- **宣言はデータ、適用はコード**（既存の権限機構と同じ形）。タスクに凍結の宣言を持たせ、
  そのタスクが done になった時点で `tools.protect([file])` をコードが呼ぶ
- 保護の意味論は合意007 B2 のまま（内容不変を守る／破れは `protection_violations()` で検出）

## やらないこと

- 検査器の凍結機構の実装（③の決定。再走の結果を見てから）
- QA の作業場（`write_scope` の scratch）— 013 の宿題だが本スプリントの2件とは別物。次に回す
- ロール定義の変更 — 013 の変更を維持して、コード側の効果だけを測る
