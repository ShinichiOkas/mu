mu が新しいドメインに入るとき、**作業側（成果物を作る側）は案外正しく動く**。
本命の失敗は**検証側の語彙**——そのドメインで「一致」「再現」「証跡」「出典」が
何を意味するか——の未整備から出る。

**Why:** 3ドメインの実測（2026-08-11）:

- リサーチ（026）: 出典 URL は報告書の**表象**であり、実際に読んだかは表象から見えない
  （未取得 URL の引用・単一ソース収束）。
- 研究開発（027 rnd r1）: 報告書の数値は記録生データと完全一致（作業は正しい）なのに、
  QA が benchmark を**再実行**して新しい計測値との完全一致を要求し FAIL——計測において
  「再現」は数値の同一ではなく結論の再現。
- 書籍執筆（027 book r1）: 物語の中身は要件を満たした（作業は良い）のに、「改稿の証跡」が
  検証不能——改稿とは同一原稿の連続的修正であり、別作品の提出では連鎖が追えない。

いずれも escalate（正直な失敗）で終わっており骨格の床は機能したが、走行を消費した。
コーディングの「表象への判定」（実験 2026-07-20 の統一診断）の各ドメイン版と読める——
検証は常に表象を通して行われ、表象と実体の結び方はドメインごとに定義し直しが要る。

**How to apply:**

- 新ドメインの初走では、成果物の出来と同じ以上に**SPEC の検査設計と QA の判定方法**を観る:
  そのドメインの「一致」は何と何を結ぶべきか・「再現」は何のレベルか・「証跡」は
  どの成果物に残るべきか。
- 失敗が出たら、修正先は作業役だけと思い込まない——pdm（基準の操作化）・qa（照合方法）・
  pjm（defective check の診断）に跨がることが多い（027 rnd は4役同時修正だった）。
- 検証語彙が2ドメイン以上で同型に壊れたら、構造対処（コード・仕様欄）の候補として
  LONGTERM に上げる（例: 言語クラス3ドメイン目→成果物言語の必須欄）。
